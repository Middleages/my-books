# 네트워크 교재 시각 설명 보강 계획

작성일: 2026-10-17 (KST)
상태: **배치 A(08~09)·B(01~03)·C(10~11) 구현·검증 완료. D1(04~06) 구현·검증 완료. D2(07·12) 구현·검증 완료.**

## 1. 목적과 범위

이미 공개한 네트워크 01~15장의 설명을 그림·애니메이션·직접 조작으로 보강한다.
기존 본문·실험을 먼저 검토하고, 독자가 머릿속으로 상상해야 했던 관계와 과정을 실제 화면에 나타낸다.
핵심 장면을 본문 흐름 안에 배치하며 입력 폼·결과 카드·긴 로그만으로 시각 설명을 대신하지 않는다.

기존 링크·chapterId·readId·읽음 저장 키와 기록, 컴퓨터 교재, 새로 추가되는 다른 교재를 보존한다.
돈 교재 구현과 별도의 작업으로 진행한다. 동시에 다른 세션이 작업할 수 있으므로 최신 main에서 시작하고,
자기 변경 파일만 반영하며 공통 catalog/style 등의 다른 변경을 덮어쓰지 않는다.
13~14장 k3s는 짧은 연결 설명이라는 기존 범위를 유지한다.

관련 지침: [콘텐츠 작성 기준](CONTENT-AUTHORING.md), [기존 네트워크 계획](NETWORK-TEXTBOOK-PLAN.md).

## 3. 배치 A: 08~09장의 핵심 장면

### 3.1 PEM 파일 안의 블록을 직접 보기

- 가상의 leaf·중간 CA·루트 CA를 서로 구별되는 인증서 블록으로 표시한다.
- `fullchain.pem`에 leaf 뒤로 중간 CA를 추가하면 파일에 블록이 이어 붙는 모습을 보여 준다.
- 블록은 개별 인증서로 남는다. 합쳐진 새 인증서가 발급되거나 서명 내용이 바뀌는 그림을 쓰지 않는다.
- 개인키는 별도 요소로 둔다. 서버가 일반 클라이언트에 보내는 인증서 목록에 개인키를 넣지 않는다.
- 실제 인증서·키를 업로드하거나 복사해 입력하게 하지 않고, 비밀이 아닌 가상 라벨·축약 PEM만 쓴다.

### 3.2 서버가 보낸 것과 클라이언트가 신뢰하는 것을 분리하기

| 화면 요소 | 의미 | 조작 후 관찰 |
| --- | --- | --- |
| 서버의 인증서 목록 | 이 연결에서 서버가 제공하는 leaf와 중간 CA 등 | 중간 CA를 빼면 경로에 빈칸이 남음 |
| 클라이언트의 CA bundle / trust store | 클라이언트가 관리 경로를 통해 신뢰하도록 설정한 기준 | 루트 CA를 신뢰 목록에 넣어야 신뢰 조건이 달라짐 |
| 두 목록 사이의 인증 관계 | 발급 관계와 신뢰 경로 | 서버가 루트를 보내도 클라이언트 목록에 자동 등록되지 않음 |

‘중간 CA 누락’과 ‘신뢰 CA 없음’을 먼저 각각 관찰한 뒤 둘이 동시에 있는 사례로 확장한다.
신뢰 CA 추가로 이름 불일치·만료가 해결되지 않는 결과도 같은 장면에서 비교한다.

### 3.3 한 PEM으로 여러 서버를 검증한다는 말

CA A와 CA B의 인증서를 한 클라이언트 CA bundle에 담고, 각 CA에 이어지는 가상 서버를
하나씩 선택해 검증 결과를 본다. ‘목록에 있는 어느 루트를 신뢰 기준으로 사용할 수 있는가’를 보여 준다.
기존 고정 단일 CA 모델을 확장해야 한다면 UI와 독립적인 명시적 발급 관계 데이터로 정의하고 테스트한다.
이름·유효기간 등 다른 조건도 맞아야 한다. CA bundle에 여러 CA를 넣었다고 모든 서버를 신뢰하지는 않는다.

이를 다음 두 경우와 그림으로 나란히 구분한다.

- **서버 fullchain:** 한 서버의 leaf와 필요한 중간 인증서들을 보내기 위한 목록.
- **여러 SAN을 가진 인증서:** 발급 시 여러 이름이 포함된 하나의 인증서. PEM 파일을 이어 붙여 SAN이 늘어나지는 않음.

새로운 실물 X.509 파서나 임의 인증서 편집 기능은 만들지 않는다. 고정 시나리오를 눈으로 설명하는 것이 목표다.

### 3.4 검증 과정을 한 단계씩 관찰하기

SNI에 따른 가상 서버 인증서 선택 → 서버 목록 수신 → 중간 CA·신뢰 경로 관찰 →
접속 이름·유효기간·신뢰 조건 확인 → 종합 결과와 수정 위치를 단계별로 보여 준다.
이는 교육상의 관찰 순서이며 모든 TLS 구현의 내부 검증 순서를 재현한다고 설명하지 않는다.
복수 실패는 종합 결과에서 모두 보이고, 한 조건을 고쳐도 남아 있는 실패를 확인할 수 있어야 한다.

09장에서는 브라우저·호스트 curl·Python·컨테이너·프록시의 가상 신뢰 상태를 독립적으로 유지한다.
호스트 신뢰를 켜도 컨테이너까지 같이 바뀌지 않는 모습을 보여 준다.
중간 CA 캐시가 서버 누락을 가리는 기존 사례도 신뢰 루트와 구분해 표시한다.

## 4. 표현과 구현 기준

- 시작 화면에서 서버·클라이언트의 위치, 각 인증서의 역할, 현재 실패 조건이 보이게 한다.
  긴 설정 목록을 읽거나 여러 번 눌러야만 전체 구도를 알 수 있게 하지 않는다.
- 그림은 SVG/HTML을 우선 고려한다. 실제 수치·이름·인증 관계·검증 결과는 수정 가능한 코드 요소로 만든다.
- 인증서의 이동은 ‘공개 인증서 정보 전달’, 연결선은 ‘발급·검증 관계’임을 직접 라벨로 표시한다.
  개인키 이동·파일 결합으로 새 서명 생성·서버 루트 전송으로 신뢰 획득 같은 오해를 만들지 않는다.
- 애니메이션과 결과 표·텍스트는 같은 모델을 사용한다. 별도의 화면용 성공/실패 로직을 중복 작성하지 않는다.
- 재생·일시정지·한 단계 진행·다시 보기·초기화를 제공한다. 조건 변경 시 단계·예측·결과를 일관되게 초기화한다.
- 첫 구도와 단계별 고정 상태만으로도 의미가 통해야 한다. reduced-motion은 전후 프레임·강조 표시로 대체한다.
- 드래그를 제공하더라도 클릭·선택·버튼으로 같은 조작을 할 수 있어야 한다. 색과 hover만으로 역할을 전달하지 않는다.
- 모바일은 서버/클라이언트 패널을 세로로 읽게 재구성하고 각 단계의 대응 항목을 함께 강조한다.
  작은 화면에 데스크톱 전체 그림을 축소해 글자를 못 읽게 만들지 않는다.

기존 `WebLabs.tsx`와 `simulations/network/web.mjs`를 먼저 읽고 재사용할 상태·판정과 부족한 관계 데이터를 구분한다.
새로운 시각 컴포넌트는 UI/상태와 계산·판정을 분리한다. 설명을 크게 편집하는 본문은 MDX로 옮기되
내용·주소·읽음 ID를 보존한다. 시각 자료만 삽입하는 기존 TSX의 일괄 전환은 필수가 아니다.

## 5. 정확성과 조사 범위

새 장면을 구현할 때 RFC 9846(TLS 1.3), RFC 5280(인증서 경로), RFC 9525(서비스 이름),
Certbot fullchain, OpenSSL·curl·Requests의 공식 설명을 다시 확인한다.
기존 본문의 출처를 출발점으로 삼되 새로 추가하는 기술 주장도 근거와 대조한다.

모델은 실제 암호 검증을 수행하지 않는다. 정상 서명·개인키 소유 증명과 고정된 CA 관계를 가정하고,
실제 핸드셰이크·키 교환·폐기 확인·교차서명·name constraints 등을 어디까지 생략하는지 표시한다.
TLS 1.3을 서버 공개키로 세션키를 암호화해 전달하는 구식 RSA 키 교환 그림으로 설명하지 않는다.
이번 배치는 인증서 구분과 검증을 시각화하며 전체 TLS 암호 과정을 별도 대형 실험으로 확장하지 않는다.

## 6. 완료 조건

1. 독자가 서버 목록과 클라이언트 신뢰 목록을 구분하고, PEM 결합의 서로 다른 용도를 그림으로 설명할 수 있다.
2. 중간 CA 누락·신뢰 없음·이름 불일치·기간 오류·복합 오류·환경별 신뢰·캐시 사례가 기존 판정과 일치한다.
3. 여러 CA bundle 사례는 CA별 발급 관계와 다른 검증 조건을 함께 반영한다. 하나의 CA 추가가 무관한 서버까지 통과시키지 않는다.
4. 재생·정지·진행·뒤로 보기 또는 재시작·입력 변경·초기화가 일관되게 작동한다. 연속 클릭·중복 타이머도 확인한다.
5. 그림의 블록·선·단계와 텍스트·표가 같은 상태를 나타내고, 키보드·모바일·reduced-motion 대안도 유지한다.
6. 관련 모델 테스트와 `npm test`, `npm run build`, 변경 검사를 통과한다.
7. 데스크톱·모바일 폭의 가독성·가로 넘침·콘솔 오류를 검증한다. 기존 컴퓨터·네트워크 핵심 실험과 읽음 기록도 회귀 확인한다.
8. main 반영과 GitHub Pages 배포 성공·실제 배포 버전을 확인한다. 미검증 기기·브라우저는 명시한다.

### 구현과 모델

- `httpJourney`는 기존 `requestTrace`의 실패/HTTP 응답 판정과 `certificateResult`를 재사용한다.
  DNS/UDP 53 질의·응답 → 새 TCP SYN/SYN-ACK/ACK → HTTPS이면 SNI·공개 인증서·클라이언트 검증 →
  HTTP 요청·반환 응답을 관찰한다. 주소·포트·프로토콜·전달 내용·확인/미확인 증거·노드 강조는 같은 프레임이다.
  HTTP는 TLS를 생략하고 HTTPS 정상 경로도 보여 준다. DNS·TCP·TLS 실패 뒤 HTTP를 보내지 않는다.
  Host만 바꾸는 진단은 URL 이름·DNS·SNI와 독립이며 브라우저 fetch에서 Host를 자유 설정한다는 뜻이 아니다.
- 200/404/421/500은 HTTP 응답으로, 하위 단계 실패와 구분한다. 기존 원인 사례는 고정 가정이며
  실제 오류 코드를 원인 하나로 단정하지 않는다. #summary는 클라이언트에 남긴다.
- 12 `CorsVisual`은 페이지 코드·브라우저 정책 검사·API를 공간으로 나눈다. 내부 정보 전달선과

- `corsJourney`는 기존 `corsResult`를 OPTIONS 허용과 본 응답 공유에 각각 재사용한다.
  기본은 두 응답에 같은 정책이며, 독립 정책으로 OPTIONS 통과/본 응답 차단과 그 반대를 비교한다.
  JSON POST, safelist GET, credentials include/와일드카드, same-origin, mixed content를 보존했다.
  모델의 요약 설명도 프레임에서 만들어 서로 다른 메서드/허용 결과가 섞이지 않게 했다.
