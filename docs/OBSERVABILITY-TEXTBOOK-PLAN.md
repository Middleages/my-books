## 목적·독자·권차

작은 React/FastAPI 서비스를 두 사람이 개발·운영하며 Compose에서 Kubernetes로 이동을 검토하고 폐쇄망을 사용하는 상황을 중심으로 한다. 완독 목표는 “느리거나 실패했을 때 어떤 신호를 어느 경계에서 찾아야 하며 그 증거로 어디까지 말할 수 있는가”다. 관측성은 신호로 내부 상태를 이해하는 능력, 모니터링은 정한 상태를 계속 확인하는 활동으로 먼저 풀어 설명한다.

최신 카탈로그의 IT·기술 컴퓨터1/네트워크2/쿠버네티스3/DB4는 보존한다. 요청의 ‘2·3권’은 직전 다음 주제 목록의 두 번째·세 번째를 뜻하므로 이 책은 **IT·기술 5권 제안**, 인증·SSO는 6권 제안이다. `bookId: observability`, `categoryId: technology`, `volume: 5`, URL `#/observability/<id>`, readId `observability/<id>`를 예약한다. [배치별 실행 프롬프트](OBSERVABILITY-SESSION-PROMPTS.md)를 별도로 제공한다.

## 사례·학습 경로·도입의 크기

가상 `study-web`의 React→프록시→FastAPI→DB 요청만 사용한다. 기존 DB `study-shop` 업무 의미와 충돌하지 않도록 주문 확정은 교육상 요청 결과일 뿐 결제/실매출이 아니다. 10개 합성 요청(req-01…10), 정상8/실패2, 합성 trace와 단위가 있는 고정 ms를 A에서 fixture로 확정한다. 원시 요청·발생한 신호·보관된 신호·조회 결과를 분리한다. 실제 개인정보·토큰·사내주소는 없다.

- 설치 없는 기본 경로: 결정적 브라우저 모델로 전 장을 완결한다. Grafana/PromQL/LogQL/OTel SDK를 브라우저에 완전 재구현하지 않는다. 선택 가능한 제한 쿼리/필터를 사용하며 지원 범위를 표시한다.
- 최소 도입 설명: 앱의 안전한 구조화 로그와 최소 지표부터 시작하고 필요에 따라 수집·조회·trace를 추가한다. Alloy/Loki/Grafana/Tempo/Mimir 전체는 **역할 연결을 배우는 지도**이지 두 사람 팀에 모두 필요한 기본 설치가 아니다. Prometheus 단독 지표 저장과 Mimir 확장을 구별한다.
- 선택 실습: 별도 승인된 일회용 Compose 환경의 합성 FastAPI 요청→Alloy→신호별 backend→Grafana를 검증하고, Kubernetes는 같은 질문의 배치/발견/권한 차이로 비교한다. 버전별 공식 구성 확인 전 복사 실행 명령을 완성품으로 제공하지 않는다.
- G에서 `examples/observability/` 후보 README, fixture, compose/config, 예상 관측, 실패 주입·정리 범위를 설계/검토한다. 설치·실행은 별도 허가/환경이 있을 때만 한다. 실제 사내 서버·방화벽·CA·운영 로그를 변경/반출하지 않는다.
- 제외: 대규모 HA/SaaS 비용 최적화, 완전한 LogQL/PromQL 강좌, 서비스 메시 설치, eBPF·profiling 심화, 실시간 외부 전송, 실제 장애 자동 수정. 로그의 장기 보관/열람권한은 책임을 설명하되 임의 정책을 회사 규칙으로 단정하지 않는다.

## 공통 제작·접근성·범위 계약

이 문서는 계획이다. **본문·모델·카탈로그·표지·CI를 구현하지 않았고, 원격 push·PR 생성·main 반영·배포·실제 서비스 설치를 하지 않았다.** 이후 구현과 원격 반영은 별도 요청 범위에서 진행한다. 계획 문서가 미래 행동을 자동 승인하지 않는다.

- 시작 시 최신 main과 독립 worktree 상태를 확인하고 병행 작업을 보존한다. [AGENTS.md](../AGENTS.md), [작성 기준](CONTENT-AUTHORING.md), [홈 정보 구조](HOME-INFORMATION-ARCHITECTURE.md), [DB 계획](DATABASE-TEXTBOOK-PLAN.md), [K8s 계획](KUBERNETES-TEXTBOOK-PLAN.md), [강화 시각 검증](KUBERNETES-VISUAL-IMPROVEMENTS-VERIFICATION.md)을 기준으로 한다.
- 목표 → 그림과 짧은 설명 → 예측 → 조작/관찰 → 이유 → 실제 확인 위치 → 확인 문제와 해설·출처 순서다. 약어보다 일상 질문을 먼저 쓴다. 설치 매뉴얼·도구 목록으로 개념을 대체하지 않는다.
- 장면마다 발견할 관계, 기하/경계/선 의미, 고정 조건, 변경 조건, 전후 차이, 모델 필드를 명시한다. 모든 요소를 같은 카드로 만들거나 단계 제목만 바꾸지 않는다. 3D는 필요 없으며 정확한 2D/SVG·HTML을 우선한다.
- 본문 `src/content/<bookId>/*.mdx`, UI `src/components/<bookId>/`, 순수 모델 `src/simulations/<bookId>/*.mjs`와 `.d.mts`, 기존 Node 테스트로 나눈다. MDX에서 임의 코드·원격 문서를 평가하지 않는다.
- `scenario → events → frames`의 결정적 모델을 그림·표·해설·판정이 함께 읽는다. 실제 데이터가 없는 단계는 unknown이다. 숨은 정답을 UI에 주입하지 않는다. 표시 반올림과 계산을 분리하며 시간·단위·관측 위치를 붙인다.
- 관계선은 실제 끝점과 방향이 보여야 한다. 제어/조회/데이터 이동은 선 종류와 라벨로 구별한다. 사라진 객체는 현재 경계에서 제거하고 이력은 별도 점선 영역에 둔다. 비례축은 초과값을 잘라 차이를 없애지 않는다.
- 재생은 사용자 선택으로만 시작한다. 정지·이전·다음 한 단계·다시 보기·전체 초기화 제공. 조건 변경 시 재생·예측·프레임 초기화, unmount 시 타이머 정리. 움직임 속도는 실제 지연을 뜻하지 않는다.
- 모바일 390/320px에서는 lane을 세로 재배치하고 경계·방향도 함께 바꾼다. SVG 통째 축소 금지. 현재 장면과 조작을 인접하게 둔다. 색뿐 아니라 형태·라벨·선 종류로 구별하고 드래그/hover 전용 조작을 금한다.
- 각 장의 정적 대안은 같은 모델의 시작/핵심 분기/끝 스냅샷과 사건표다. reduced-motion은 이동 없이 현재 위치·전후 차이를 유지한다. 키보드·포커스·읽을 수 있는 결과 문장도 제공한다. 보조 원문 표만 이름 있는 가로 스크롤을 허용한다.
- 최초 구현 시 제안 권차의 중복 여부를 다시 확인한다. 기존 책 권차·URL·chapter/readId·`my-books:read:v1` 및 알 수 없는 읽음 ID는 보존한다. 소개는 읽음 분모에 넣지 않고 실제 구현한 장만 공개한다. 계획 단계에서는 홈 카드나 빈 책을 추가하지 않는다.

## 검증과 완료 판정

A–F는 두 장씩 소스·모델·production·직접 시각 검토까지 순차 진행한다. 선행 검토 통과 뒤 다음 배치 로컬 준비는 가능하지만 승인 없는 게시를 하지 않는다. G는 전체권 통합/편집 점검이다. 실제 실습·공개는 별도의 승인 및 환경이 필요하다.

1. 모델: 정상/실패/경계값/누락/재실행·초기화, 각 장 불변식과 판정 근거를 검사한다. 시간은 고정 fixture와 논리 시계이며 실시간 또는 난수 의존을 금한다.
2. 코드 변경 시 전체 `npm test`, `npm run build`, `git diff --check`. 이번 변경 장과 영향받은 홈·권차·읽음 기능에 브라우저 검사를 집중하고 G에서 넓은 회귀를 실행한다. 필수 실패를 삭제/skip해서 통과시키지 않는다.
3. 실제 production 1440/390/320px의 초기·분기·실패·완료 캡처를 직접 연다. 역할/관계/불변 조건/조작 차이/선 끝점/비례/라벨/controls 근접성을 기능 검사와 별도로 기록한다. reduced-motion·키보드·정지·초기화·새로고침·콘솔·MDX 문단 중첩도 검사한다.
4. 검증 문서에는 기준 SHA·변경 파일/ID·공식 자료 확인일·모델 가정·명령/환경/결과·실제 실습 여부·미검증을 남긴다. 구현 완료, 테스트 통과, 실제 스택 동작, 원격 공개는 서로 다른 상태다. Safari·실기기·스크린리더는 실제 확인하지 않으면 미검증이다.
5. 나중에 게시가 별도 승인되면 최신 main과 병행 변경을 보존 통합하고 정확한 commit의 Actions·Pages URL·게시 JS/CSS byte 일치까지 확인한다. 현재 계획 작성에는 해당하지 않는다.
6. 계획만 바뀐 지금은 파일 경로·링크·목차/배치 대응·권차·범위·`git diff --check`를 검사한다. UI 테스트나 실제 스택 실행을 했다고 쓰지 않는다.

### 01. 서비스에 무슨 일이 일어났을까? · `signals` · 배치 A

- **핵심 질문/목표:** 로그·지표·트레이스는 같은 사건에서 무엇을 다르게 남길까?
- **눈으로 발견할 관계·시각 속성:** 요청 원본을 가운데 두고 로그 사건점·지표 집계통·트레이스 시간막대로 갈라지는 세 투영을 그린다. 전체 모집단과 관측 표본 경계를 표시한다.
- **고정 조건/조작/전후 차이:** 동일 10요청 중 오류2·지연1을 고정하고 신호 하나씩 숨긴다. 숫자 요약으로 특정 요청의 이유를 복원할 수 없음이 보인다.
- **공유 모델·검증:** signalFrames: requestIds, eventRefs, aggregates, spanRefs. 오류율 2/10과 로그 건수는 다른 단위다.
- **반례·모델 경계:** 로그가 많으면 관측이 완전하다는 반례. 샘플링/수집 누락을 정상 요청으로 취급하지 않는다.
- **모바일·정적 대안:** 세 투영을 세로로 펼치고 같은 요청 강조를 유지; 정적 원본-투영 대응표.
- **확인 문제:** 조작한 조건 하나 때문에 달라진 관계와 아직 알 수 없는 사실을 설명한다. 위 반례의 정답과 이유를 본문에 포함한다.
- **공식 근거:** S01.

### 02. 수집·저장·조회는 다른 일 · `pipeline` · 배치 A

- **핵심 질문/목표:** Alloy와 Loki·Tempo·Mimir·Grafana는 어떻게 연결될까?
- **눈으로 발견할 관계·시각 속성:** 앱/collector/신호별 저장소/조회 화면의 역할을 모양으로 구별한다. 로그→Loki, trace→Tempo, metric→Mimir로 분기하고 Grafana의 조회 왕복은 별도 점선이다.
- **고정 조건/조작/전후 차이:** 기본은 앱→Alloy→각 저장소, Grafana→각 데이터소스. 한 저장소 또는 수집 경로를 끊어 다른 신호는 남게 한다.
- **공유 모델·검증:** pipelineFrames: edges, accepted, queued, persisted, queryable. 수집 수신과 영속 저장·조회 성공을 분리한다.
- **반례·모델 경계:** Grafana가 모든 원시 신호를 저장하거나 Alloy가 장기 저장소라는 오해. 필수 전제품 설치가 아님을 명시.
- **모바일·정적 대안:** 좁은 화면은 신호 탭+공통 구성도; 정적 신호별 두 경로.
- **확인 문제:** 조작한 조건 하나 때문에 달라진 관계와 아직 알 수 없는 사실을 설명한다. 위 반례의 정답과 이유를 본문에 포함한다.
- **공식 근거:** S02,S03,S04,S05,S06.

### 03. 사건을 읽을 수 있게 남기기 · `logs` · 배치 B

- **핵심 질문/목표:** ERROR 한 줄만으로 원인을 알 수 있을까?
- **눈으로 발견할 관계·시각 속성:** 시각·서비스·사건·route·trace_id 필드를 가진 합성 사건띠를 요청 경계와 연결한다. 발생 시각과 수집 시각을 두 축에 둔다.
- **고정 조건/조작/전후 차이:** 지연 도착·중복·로그 레벨 변경·토큰 필드 포함/제거를 비교. allowlist 변환 전후에서 민감값이 수집 경계 전에 사라진다.
- **공유 모델·검증:** logFrames: eventTime, observedTime, eventId, safeFields. 로그 행 수를 요청 수로 세지 않으며 값은 모두 합성이다.
- **반례·모델 경계:** 같은 ERROR가 재시도로 두 줄; 성공 로그 부재는 실패 증거가 아님. 스택트레이스에도 비밀정보가 섞일 수 있음.
- **모바일·정적 대안:** 원문은 접기; 필드별 세로 비교와 단계별 정적 안전처리표.
- **확인 문제:** 조작한 조건 하나 때문에 달라진 관계와 아직 알 수 없는 사실을 설명한다. 위 반례의 정답과 이유를 본문에 포함한다.
- **공식 근거:** S01,S07.

### 04. 숫자로 상태의 변화를 읽기 · `metrics` · 배치 B

- **핵심 질문/목표:** 누적 요청 수가 줄었을 때 서비스가 좋아진 것일까?
- **눈으로 발견할 관계·시각 속성:** counter의 계단·재시작 경계, gauge 순간 수위, duration 분포를 별도 축으로 그린다. 100ms/1000ms 요청을 같은 공통 눈금에서 비교한다.
- **고정 조건/조작/전후 차이:** counter reset·scrape 누락·느린 꼬리·요청0을 바꾼다. 전체 분포와 평균만 남긴 그림을 비교한다.
- **공유 모델·검증:** metricFrames: samples, resetMarkers, bucketCounts, count, sum. rate 근사는 관측 간격 가정을 표시; 분모0은 미정이다.
- **반례·모델 경계:** 평균이 낮아도 일부는 느림; p95의 평균은 전체 p95가 아님. 버킷 추정 분위수와 정확한 fixture 분위수를 구분.
- **모바일·정적 대안:** 그래프와 정적 표에 축/초/요청 단위; 모바일 두 그래프 세로 비교.
- **확인 문제:** 조작한 조건 하나 때문에 달라진 관계와 아직 알 수 없는 사실을 설명한다. 위 반례의 정답과 이유를 본문에 포함한다.
- **공식 근거:** S08.

### 05. 이름표가 너무 많아질 때 · `labels` · 배치 C

- **핵심 질문/목표:** 사용자 ID를 라벨로 넣으면 무엇이 늘어날까?
- **눈으로 발견할 관계·시각 속성:** service×route×status의 조합 격자를 만들고 실제 관측된 조합만 채운다. 라벨 집합당 series/stream 공간이 갈라짐을 보인다.

- **모바일·정적 대안:** 격자 일부+전체 개수/분포를 세로 표시; 잘라 숨긴 칸 수 표시, 정적 tuple 목록.
- **확인 문제:** 조작한 조건 하나 때문에 달라진 관계와 아직 알 수 없는 사실을 설명한다. 위 반례의 정답과 이유를 본문에 포함한다.

### 06. 한 요청의 여행을 따라가기 · `traces` · 배치 C

- **핵심 질문/목표:** 느린 부모 span의 시간은 자식 시간을 모두 더한 값일까?
- **눈으로 발견할 관계·시각 속성:** 브라우저/프록시/API/DB lane과 공통 ms 축, 부모-자식 span 막대 및 겹치는 시간을 그린다. trace context 이동을 별도 표식으로 표시.
- **고정 조건/조작/전후 차이:** 직렬/병렬 호출·전파 누락·수집 누락을 바꾼다. 100ms와 150ms 자식이 겹치는 예를 첫 화면에 둔다.
- **공유 모델·검증:** traceFrames: start,end,parentId,traceId,received. elapsed=maxEnd-start이며 병렬 span 단순합 금지. 없는 span은 unknown.
- **반례·모델 경계:** 트레이스가 없다고 요청이 없었던 것은 아님. 시간 오차/비동기 link는 parent-child 트리만으로 완전히 표현되지 않음.
- **모바일·정적 대안:** 세로 lane에서도 동일 축 비교 유지; 정적 waterfall과 시작/끝/부모표.
- **확인 문제:** 조작한 조건 하나 때문에 달라진 관계와 아직 알 수 없는 사실을 설명한다. 위 반례의 정답과 이유를 본문에 포함한다.

### 07. 앱에 관측 지점을 심기 · `instrumentation` · 배치 D

- **핵심 질문/목표:** FastAPI에 자동 계측을 붙이면 업무 의미도 모두 알까?
- **눈으로 발견할 관계·시각 속성:** 업무 요청 경로 옆에 SDK→processor→exporter→Alloy 경로를 배치. React 브라우저와 FastAPI 서버 경계를 분리한다.
- **고정 조건/조작/전후 차이:** 자동 HTTP span / 주문 검증 수동 span, 중복 계측, traceparent 전파 차단을 비교. 서비스 이름·환경을 바꿔도 원래 업무 요청을 바꾸지 않는다.
- **공유 모델·검증:** instrumentationFrames: resources, instrumentationScope, spans, propagation. OTel은 저장 제품이 아니며 프로토콜 OTLP와 SDK 역할을 분리한다.
- **반례·모델 경계:** 모든 header/body 자동 수집 금지. 브라우저 계측은 전파 허용 origin·CORS·민감정보를 따로 검토; 공개 collector에 무인증 노출하지 않음.
- **모바일·정적 대안:** 업무/관측 경로 전후 그림을 세로로; 정적 계측 책임표.
- **확인 문제:** 조작한 조건 하나 때문에 달라진 관계와 아직 알 수 없는 사실을 설명한다. 위 반례의 정답과 이유를 본문에 포함한다.

### 08. 놓친 신호와 늦게 온 신호 · `sampling-and-delivery` · 배치 D

- **핵심 질문/목표:** 대시보드가 비었는데 앱은 정상일 수 있을까?
- **눈으로 발견할 관계·시각 속성:** 생성→대기열→전송→저장→조회 시간선에 retained/dropped/retry를 구분한다. head 결정과 완료 후 tail 결정 위치가 다름을 보인다.
- **고정 조건/조작/전후 차이:** 고정 10trace 중 보관3, 큐 용량3/생성5, 저장소 중단/복구를 선택. 재시도 중복 가능성을 남긴다.
- **공유 모델·검증:** deliveryFrames: generated=queued+delivered+dropped(고유 사건 기준). 재시도 attempts는 별도 수량; sample mask는 결정적.
- **반례·모델 경계:** 샘플링한 trace 오류율을 전체 오류율로 단정하지 않음. retry는 영구 무손실 보장이 아니며 tail 결정에는 대기/자원 비용이 듦.
- **모바일·정적 대안:** 큐 슬롯과 초과 영역을 세로 표현; 정적 사건별 최종 위치표.
- **확인 문제:** 조작한 조건 하나 때문에 달라진 관계와 아직 알 수 없는 사실을 설명한다. 위 반례의 정답과 이유를 본문에 포함한다.

### 12. 증거로 장애 범위 좁히기 · `diagnosis` · 배치 F

- **핵심 질문/목표:** 느림·500·빈 대시보드 중 무엇부터 확인할까?
- **눈으로 발견할 관계·시각 속성:** 요청 경로와 관측 경로를 겹치지 않게 나란히 두고 조사한 경계만 확정한다. API 지연·DB 대기·collector 중단·쿼리 필터 오류의 증거를 단계 공개.

- **확인 문제:** 조작한 조건 하나 때문에 달라진 관계와 아직 알 수 없는 사실을 설명한다. 위 반례의 정답과 이유를 본문에 포함한다.
- **공식 근거:** S01,S07,S11.
