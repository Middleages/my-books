## 일하는 경로와 기록하는 경로

주문 요청은 브라우저에서 서버로 들어가 규칙을 검사하고 응답합니다. 계측은 이 업무를 다시 실행하는 것이 아니라 무엇이 언제 일어났는지 관측 자료를 남기는 일입니다. 자동 HTTP 계측이 있다고 주문 검증 내부의 모든 업무 의미까지 자동으로 알려지는 것은 아닙니다.

SDK는 앱의 기록을 처리하고 exporter를 통해 내보냅니다. OTLP는 전송에 사용하는 규약이고 Alloy는 수집 경로의 구성요소입니다. OpenTelemetry를 붙였다는 말만으로 데이터가 저장·조회됐다고 판단하지 않습니다.

## 기록의 주체와 계측 도구를 구별합니다

resource의 service.name은 어떤 서비스의 자료인지 구별하는 데 쓰입니다. instrumentation scope는 어떤 계측 코드나 라이브러리가 기록했는지 구별합니다. 둘을 같은 이름표로 합치면 앱의 정체와 계측 도구를 혼동합니다. 이 실험의 resource 선택은 서버용이며 브라우저 앱은 별도 프로세스·SDK를 갖습니다.

수동 업무 span은 HTTP 구간 안의 주문 검증을 하나의 관찰 가능한 작업으로 나타냅니다. 어디를 감싸고 어떤 이름과 속성을 남길지 결정해야 합니다. 모든 함수에 span을 추가하면 비용과 읽기 어려움도 증가할 수 있으므로 진단 질문에 필요한 의미를 선택합니다.

전파 누락은 기록 사이의 연결을 끊을 수 있지만 실제 요청이 실행되지 않았다는 증거는 아닙니다. 중복 계측도 요청량 증가의 증거가 아닙니다. 업무 원본과 관측 기록 수를 나란히 읽어야 합니다.

## 안전한 계측의 시작점

요청 header/body를 전부 기록하는 방식으로 시작하지 않습니다. 비밀번호·Cookie·Authorization·개인정보는 제외하고, 허용한 속성과 안전한 상관 식별자만 사용합니다. 브라우저에서 trace context를 보낼 origin도 의도적으로 제한하고 CORS와 전파 설정을 구별합니다. 수집 endpoint를 인터넷에 무인증 노출하는 설정을 이 교재는 만들지 않습니다.

**확인 문제:** 중복 계측 모드에서 server span이 늘었습니다. 주문 처리량도 늘었다고 보고해도 될까요?

**해설:** 아닙니다. 고정 업무 요청은 한 번입니다. 계측 중복과 실제 중복 요청은 원본 요청 식별자·수집 경계·업무 결과를 함께 확인해 구별해야 합니다.
