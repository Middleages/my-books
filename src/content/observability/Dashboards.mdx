## 네 숫자가 같은 요청을 보고 있을까요?

대시보드는 질문에 답하기 위해 모아 둔 화면입니다. 요청량, 오류율, 지연, 자원 포화를 나란히 놓으면 바쁜 시간과 느려진 시간을 비교하기 쉽습니다. 하지만 오류 분자는 운영 환경인데 분모는 시험 환경이라면 그 비율은 의미가 없습니다. 이 장에서는 **기간·환경·route가 같은지**를 먼저 확인하고, 알려진 0과 모르는 값을 구별합니다.

오류율은 같은 조건의 오류 요청 수를 전체 요청 수로 나눕니다. p95는 지연을 작은 순서로 놓았을 때 약95%까지 포함하는 위치입니다. 포화도는 자원의 여유가 얼마나 남았는지 묻습니다. 지연이 높다고 CPU가 꽉 찼다고 단정할 수는 없습니다. 아래에서는 별도로 주어진 예약 슬롯의 busy/capacity를 사용합니다.

## 창과 분모부터 읽습니다

기본 lab의 /orders에는 최근6분 요청6건 중 오류2건이 있습니다. 최근2분에는 R9와 R11만 들어와 오류1/2입니다. 오래된 정상 요청을 제외하니 요청량은 줄고 오류율은 커집니다. 기간을 바꿔 놓고 그래프 높이만 비교하면 잘못된 결론을 내릴 수 있습니다. 고정 눈금과 요청 ID 목록을 함께 봅니다.

/health는 오류가 없는 자료입니다. 반면 일치하지 않는 route는 정상 조회했지만 요청 자체가0건입니다. 이 경우 오류 수도0이지만 오류율의 분모가 없으므로 비율은 계산하지 않습니다. 수집 누락은 요청 수조차 알 수 없고, 조회 오류는 대시보드가 답을 받지 못한 상태입니다. 조회 실패를 앱 요청 오류율로 섞지 않습니다.

## 숫자에서 원본으로 내려가는 길

집계 그래프의 특정 요청 표식에 trace ID가 보관되어 있다면 관련 trace로, 그 trace ID와 로그 연결 정보가 있다면 로그로 좁혀 볼 수 있습니다. 이런 대표 연결 표식을 exemplar라고 부릅니다. 모든 지표에 반드시 있는 것은 아닙니다. trace가 있어도 log ID가 없을 수 있고, 샘플링·보관 기간·필터·시계 차이 때문에 찾지 못할 수도 있습니다.

여기서는 R9의 T9·L9처럼 fixture에 실제로 있는 ID만 보여 줍니다. 상관 ID 사용을 끄면 숫자는 같아도 연결은 사라집니다. 연결된 사례 하나가 전체 오류의 원인이라고 확정하지도 않습니다. “이 요청에서 무슨 일이 있었나?”라는 다음 질문의 출발점입니다.

## 실제 적용과 실습 경계

운영 화면을 설계할 때 패널마다 시간창·시간대·환경·서비스·route·분모·단위를 기록합니다. React 화면의 실패, FastAPI 요청의 실패, DB 질의의 실패가 같은 사건인지 먼저 정의합니다. Grafana 화면이 잘 열린다는 사실은 앱이나 수집 경로의 정상 증거가 아닙니다.

이 브라우저 실습은 원본12요청을 필터링하는 교육 모형입니다. 실제 histogram 집계의 분위수 추정, PromQL/LogQL/TraceQL, 데이터 소스 인증과 연결 설정은 실행하지 않습니다. 슬롯도 별도 합성 자료이며 실제 서버 성능 수치가 아닙니다.

### 확인 문제

1. 요청0건에서 오류율0%라고 쓸 수 있나요? 아니요. 오류 분자는0이지만 분모도0이므로 비율은 정의하지 않습니다. 정상 요청이 있었다는 뜻으로 바꾸면 안 됩니다.
2. 지연900ms와 높은 CPU가 동시에 보이면 CPU가 원인인가요? 아직 아닙니다. 같은 요청·기간인지, DB 대기나 네트워크 등의 다른 증거를 더 확인해야 합니다.
3. 집계값만 있으면 trace ID를 복원할 수 있나요? 아니요. 실제 상관 정보와 보관 자료가 있어야 합니다.
