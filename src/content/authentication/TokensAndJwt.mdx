## 읽을 수 있는 주장과 신뢰할 수 있는 주장

JWT는 여러 주장을 담는 형식입니다. 흔히 보는 서명된 JWS 형태는 header·payload·signature의 세 부분으로 표현됩니다. 내용을 읽는 것은 서명을 검증하는 것과 다릅니다. 서명은 내용 변경을 검증하는 수단이지 내용을 숨기는 암호화가 아닙니다. 비밀번호나 비밀정보를 payload에 넣어도 서명 때문에 숨겨지지 않습니다.

아래에서는 토큰을 실제로 만들거나 받지 않습니다. 같은 내용이 읽혀도 서명 검증이 실패하면 수락하면 안 된다는 관계만 합성 표본으로 관찰합니다. 알고리즘과 키는 신뢰하는 검증 설정으로 제한해야 하며, 제출된 header의 주장만 따라 선택하지 않습니다.

## 검증에는 서로 다른 질문이 있습니다

구조를 읽을 수 있는지와 허용한 algorithm인지, 서명이 맞는지, 예상한 issuer인지, 이 API가 audience에 포함되는지, 시간 조건이 맞는지, 의도한 종류와 용도의 토큰인지를 따로 확인합니다. 이 그림의 모든 칸이 통과해야 표본을 수락합니다. 실제 검증 라이브러리의 안전한 구성·키 출처·실패 처리는 그림보다 더 많은 검토가 필요합니다.

기본 변조 표본은 내용을 읽을 수 있지만 서명이 거절됩니다. 다른 audience 표본은 서명이 통과해도 대상 API가 달라 거절됩니다. 만료 표본은 now=600, exp=600이므로 더 이상 유효하지 않습니다. 이600은 교육용 숫자이고 운영 만료시간 권장값이 아닙니다. 실제 시간 검증에서는 nbf와 허용 시계 오차 등 정책도 검토합니다.

## ID Token과 access token을 바꾸어 쓰지 않기

ID Token은 OIDC 클라이언트가 인증 결과를 확인하는 용도입니다. API용 access token과 같은 것으로 취급하지 않습니다. 용도 표본에서는 다른 검사 조건을 의도적으로 맞춰 두고 마지막 용도 검사만 실패시켜, 서명 하나로 수락하지 않는 이유를 보여 줍니다. 실제 ID Token의 audience 등은 클라이언트 맥락에서 별도로 검증합니다.

access token은 항상 JWT인 것이 아닙니다. 불투명한 형식도 있습니다. JWT를 사용한다는 사실만으로 SSO가 생기지도 않습니다. SSO는 발급자와 여러 앱의 신뢰·로그인 흐름·세션 관계를 설계하는 문제이며 뒤 장에서 단계별로 연결합니다.

## 토큰 수락 뒤에도 인가가 남습니다

이 API에 사용할 토큰이라는 검증과 이 문서를 수정해도 된다는 정책은 다른 질문입니다. 앞 장의 역할·객체 소유권 검사를 떠올려 보세요. 토큰에서 읽은 scope나 역할도 서버가 의도한 정책에 맞게 해석해야 합니다.

실제 디버깅에서 토큰 원문을 웹 검색창·공개 decoder·로그·스크린샷에 붙여 넣지 않습니다. 이 교재가 제공하는 것은 검사 단계와 실패 범주이지 실제 자격 증명 처리 도구가 아닙니다. 안전한 로그에는 검사 주체·단계·합성 또는 안전한 상관 ID를 쓰고 민감한 원문은 제외합니다.

**확인 문제:** 모든 서명 검사가 맞는 ID Token을 API access token 대신 보내도 될까요?

**해설:** 아닙니다. 서명 일치와 목적·수신 대상 일치는 별도 조건입니다. 검증 종류를 혼동하지 말고 의도한 토큰 종류·issuer·audience·시간 등을 확인해야 합니다. 표본 수락 후에도 자원별 인가는 남습니다.

## 근거와 한계

확인일2026-10-20. [RFC8725 JWT Best Current Practices](https://www.rfc-editor.org/rfc/rfc8725.html)의 algorithm·issuer/audience·유형별 검증 원칙과 [OIDC Core](https://openid.net/specs/openid-connect-core-1_0.html)의 ID Token 정의·검증을 참고했습니다. 암호 연산·키 조회·키 회전·실제 로그인/SSO는 구현하거나 실행하지 않았습니다. 그림은 코드로 만든 교육용 도식이며 실제 JWT 문자열이 아닙니다.
