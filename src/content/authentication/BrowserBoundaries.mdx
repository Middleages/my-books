## 주소의 경계가 하나만 있는 것은 아닙니다

브라우저에서 앱 화면을 열고 API를 호출한다고 생각해 봅시다. 같은 회사가 운영하는 두 주소여도 브라우저의 origin은 다를 수 있습니다. origin은 scheme·host·port의 조합입니다. HTTPS의 기본 포트는443입니다. app.example.test와 api.example.test는 host가 다르므로 서로 다른 origin입니다.

site는 origin보다 다른 기준의 경계입니다. 여기서는 같은 scheme의 example.test 아래 두 호스트를 같은 site로, other.test를 다른 site로 고정합니다. 실제 site 판단에는 public suffix 등의 규칙이 관여하므로 문자열 끝만 비교해서 구현하지 않습니다. 같은 site라는 사실이 JavaScript의 응답 읽기를 자동 허용하지는 않습니다.

쿠키에는 또 다른 범위가 있습니다. host-only 쿠키는 설정한 호스트에만, Path=/api 쿠키는 그 경로에 맞는 요청에만 붙을 수 있습니다. Domain을 지정한 쿠키와 host-only 쿠키는 같지 않습니다. 아래는 host-only로 고정한 예시이며 Path는 접근 통제 장치가 아닙니다.

## 세 결과를 한 단어로 뭉치지 않기

기본 사례를 끝까지 보내면 요청 전송과 서버 처리는 예이지만 JS 응답 읽기는 아니요입니다. preflight 없는 요청은 서버에 도착한 뒤 브라우저가 응답 접근을 막을 수 있습니다. 따라서 화면의 CORS 오류만으로 서버가 처리하지 않았다고 단정할 수 없습니다. 변경 작업을 무턱대고 재시도하면 중복 처리 위험도 따로 검토해야 합니다.

반면 JSON POST 사례에서는 먼저 보내는 OPTIONS 검사에서 거절되어 실제 POST는 보내지 않습니다. 이 예시의 전송 칸은 OPTIONS가 아니라 실제 앱 요청을 뜻합니다. 네트워크 오류·preflight 거절·응답 접근 거절을 같은 실패로 읽지 않는 것이 핵심입니다.

## 각 옵션은 서로 다른 질문에 답합니다

- credentials는 fetch가 자격 정보를 포함할 조건입니다. 기본 same-origin과 include를 구별합니다. include도 쿠키의 Secure·SameSite·범위를 무시하지 않습니다.
- Secure 쿠키는 이 예시의 일반 HTTP 요청에 붙지 않습니다. 이것만으로 앱 전체의 보안이 완성되지는 않습니다.
- HttpOnly는 JavaScript의 직접 쿠키 접근을 제한합니다. 브라우저가 인증 요청을 보내는 기능까지 멈추는 것은 아니므로 XSS 방어를 대신하지 않습니다.
- SameSite=Lax는 이 예시의 교차 site fetch에서는 쿠키를 보내지 않습니다. 최상위 탐색 등 다른 맥락은 별도 규칙입니다. 모든 교차 site 요청의 단일 결과로 일반화하지 마세요.
- 자격 정보를 포함한 교차 origin 응답을 읽으려면 서버의 정확한 origin 허용과 credentials 허용이 필요합니다. wildcard만 넣는 것으로 해결되지 않습니다.

CORS는 서버 인가나 CSRF 방어의 대체가 아닙니다. 서버는 요청마다 자원·행동 정책을 검사하고, 쿠키 인증의 상태 변경에는 적절한 CSRF 방어를 별도로 설계해야 합니다. 내부망이라고 이 경계가 사라지는 것도 아닙니다.

## 실제 문제를 좁히는 순서

주소·메서드·credentials·쿠키 속성과 브라우저의 차단 사유를 확인합니다. preflight와 실제 요청을 나누고, 서버 도달 여부와 응답 읽기 가능 여부를 따로 봅니다. 진단을 위해 Cookie나 Authorization 원문을 복사해 공개 로그에 남기지 마세요. 안전한 요청 식별자와 결과 범주로 연결합니다.

**확인 문제:** 요청이 처리됐지만 CORS로 응답을 못 읽었습니다. HttpOnly를 끄면 해결될까요?

**해설:** 아닙니다. 직접 쿠키 읽기와 응답 접근은 서로 다른 경계입니다. HttpOnly를 없애는 대신 정확한 요청·응답 정책을 확인해야 합니다. 꺼서 비교하는 조작은 교육용이지 운영 보안 설정 변경 권장이 아닙니다.
