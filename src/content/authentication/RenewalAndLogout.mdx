## 지워진 화면과 남아 있는 사용 권한

로그아웃 버튼을 누르면 화면은 로그인 전으로 돌아갑니다. 그 순간 이미 발급한 access token도 모든 API에서 바로 거절될까요? 이 장은 **access·refresh·앱 세션·IdP 세션의 수명과 철회 범위**를 나눕니다.

access token은 API에 제시하는 표식이고 refresh token은 새 access를 받는 교환에 쓰는 표식입니다. refresh를 API 요청의 대체 증명으로 보내는 것이 아닙니다. 앱 로그인 상태와 IdP 로그인 상태도 각각 별도 기록입니다. 같은 사용자에게 관련되어 있어도 모두 하나의 타이머는 아닙니다.

### 먼저 예측해요

access가5분에 만료되지만 앱 세션은15분까지라면5분의 API 요청이 그대로 성공할까요? 로그아웃으로 앱 세션만 없어졌다면, API가 그 사실을 어떻게 알 수 있을까요?

## 갱신은 새 표식을 받는 교환입니다

기본 표본은5분에A1이 만료되고6분에 한 번 갱신합니다. A1의 만료 시각을 늘리는 대신 새 A2와 R2를 받습니다. 이전 refresh R1을 사용 종료로 바꾸는 것이 회전(rotation)의 핵심입니다. 화면의 이름은 상태 구분을 위한 합성 ID이며 실제 token 형식이나 값이 아닙니다.

두 탭이 같은 이전 R1을 각각 보내면 한쪽 교환 뒤 다른 쪽이 이미 사용된 표식을 제시할 수 있습니다. 이 실험은 재사용을 감지하면 해당 refresh 묶음을 철회하는 엄격 정책을 택했습니다. 서버는 재사용이 정상 탭의 경합인지 탈취자의 시도인지 자동으로 알아맞히지 못합니다. 실제 동시 갱신 조정과 재사용 탐지 정책을 확인해야 합니다.

교환이 거절되면 한 번의 실패 뒤 재인증 안내로 멈춥니다. 무한 재시도는 로그인 장애를 더 키울 수 있습니다. 이 모형은 동시 요청 잠금이나 실제 네트워크 재시도 구현을 제공하지 않습니다.

## JWT 자체에 철회 연락망은 없습니다

로그아웃 사례에서1분에 앱 세션과 refresh family를 종료합니다. 그런데 기존A1의 exp는5분입니다. API가 서명과 수명만 확인하고 추가 철회 상태를 읽지 않는 모형에서는2분의 A1이 시간 검사를 통과합니다. 추가 조회 정책은 같은 요청을 철회 상태 때문에 거절합니다.

실제 설계에는 짧은 access 수명, 철회 상태 전달, 세션 버전 확인 등 여러 선택이 있습니다. 필요한 상태 저장과 조회 비용, 장애 시 정책, 캐시·전파 지연을 함께 고려합니다. 이 실습의 온라인 확인은 즉시 최신 상태를 받는 가정이지 모든 API의 즉시 철회를 보장한다는 뜻이 아닙니다. IdP까지 종료할 것인지도 별도 logout 연동 범위입니다.

### 확인 문제

1. now와 exp가 같으면 유효한가요? 이 실험은 허용 시계 오차0이므로 만료입니다. 실제 허용 오차는 명시적으로 설계해야 합니다.
2. refresh를 철회하면 기존 access도 형식만으로 자동 무효가 되나요? 아니요. API의 철회 확인·관련 token 취소 정책을 따로 확인합니다.
3. 앱 세션과 IdP 세션은 항상 같이 끝나나요? 아니요. 이 표본의 로컬 로그아웃은 IdP를 유지합니다.

### 출처와 실습 범위

2026-10-20 공식 문서 확인. [RFC9700 refresh token 보호](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14), [RFC7009 token 철회와 구현 고려](https://www.rfc-editor.org/rfc/rfc7009.html). 실제 token·refresh·세션·암호·API는 실행하지 않으며 운영 권장 수명 값을 제시하는 실험도 아닙니다.
