## 새 요청에서도 서버는 나를 어떻게 알아볼까요?

목표는 **쿠키의 보유·전송 조건과 서버 세션 기록·유효기간을 각각 설명하는 것**입니다.

HTTP 요청이 새로 왔다고 서버가 앞선 요청의 사람을 저절로 기억하는 것은 아닙니다. 한 가지 설계는 로그인 확인 뒤 서버에 세션 기록을 만들고, 그 기록을 찾는 불투명한 식별자를 브라우저 쿠키로 전달하는 것입니다. 다음 요청에서 브라우저가 범위에 맞는 쿠키를 보내면 서버는 식별자로 기록을 조회합니다.

쿠키는 브라우저가 데이터를 보관하고 요청에 실어 보내는 방식입니다. 세션은 요청 사이의 상태를 관리하는 설계입니다. 둘은 동의어가 아닙니다. 쿠키에는 설정값을 담을 수도 있고 토큰을 운반할 수도 있습니다. 이 장에서는 **서버 기록을 찾는 식별자**만 담는 구조를 고정합니다.

### 먼저 예측하세요

브라우저에는 표식이 남아 있는데 서버의 유효기간이 끝나면 로그인 상태가 유지될까요? 요청이 다른 서버 프로세스로 가면 그곳에도 같은 세션 기록이 있을까요?

## 표식이 있거나 도착했다고 끝이 아닙니다

쿠키가 없으면 실어 보낼 식별자가 없습니다. b.example.test용 호스트 전용 쿠키는 a.example.test 요청에 붙지 않습니다. 이 예제는 호스트 범위만 비교하며 실제 브라우저의 Domain·Path·SameSite 등 세부 규칙은 아직 구현하지 않습니다.

올바른 식별자가 도착해도 서버 기록이 없거나 만료됐으면 로그인 상태를 이어 갈 수 없습니다. 실험의 599초는 유효하지만 만료 경계인 600초부터는 거절됩니다. 화면의 브라우저 표식은 그대로 남아 있으므로 “보유”와 “서버 유효”가 다른 축임을 볼 수 있습니다. 쿠키 자체의 만료도 별도 설정이며 서버 세션 수명과 항상 같지는 않습니다.

프로세스 A의 메모리에만 세션이 있는데 요청이 B로 가면 B는 기록을 찾지 못할 수 있습니다. 공유 세션 저장소는 가능한 설계 중 하나지만 그 저장소의 가용성·접근 권한·만료·일관성도 관리해야 합니다. 그림의 공유 체크 하나가 실제 운영 문제를 모두 해결하지는 않습니다.

## 로그인 전후에도 지켜야 할 경계

실제 세션 식별자는 다른 사람이 추측하거나 재사용하지 못하도록 설계해야 합니다. 로그인 등 중요한 상태 변화에서는 세션 식별자를 재발급하고, 서버에서 만료와 무효화를 관리해야 합니다. 브라우저를 닫았다는 사실만으로 모든 서버 세션이 사라졌다고 가정하지 않습니다.

Secure·HttpOnly·SameSite는 서로 다른 보호 조건입니다. 예를 들어 JavaScript에서 쿠키 값을 읽지 못하게 하는 것과 브라우저가 요청에 쿠키를 보내지 못하게 하는 것은 다릅니다. 이 장의 그림은 그 속성을 실제로 설정하지 않습니다. CSRF·XSS·TLS·비밀번호 저장·SSO·토큰 검증은 추가 설계와 확인이 필요합니다.

세션 식별자와 쿠키 원문은 비밀번호처럼 계정 접근에 쓰일 수 있으므로 로그에 남기거나 이 교재에 붙여 넣지 마세요. 교육 그림의 SIM-SESSION-A는 실제 값이 아닌 표식입니다. 실제 앱의 진단에는 요청 상관 ID·검사 주체·오류 범주 같은 안전한 정보를 사용합니다.

## 확인해 보세요

- 쿠키가 있으면 로그인 상태인가요? 전송 범위·서버 기록·유효기간까지 확인해야 합니다.
- 서버가 다른 프로세스여도 기록이 자동 복제되나요? 아닙니다. 저장소 설계를 명시해야 합니다.
- 서버 세션이 유효하면 문서를 수정할 수 있나요? 주체 확인 뒤에도 01장의 인가가 남습니다.
