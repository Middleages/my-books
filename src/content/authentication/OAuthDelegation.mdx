## 비밀번호를 맡기는 대신 범위를 맡깁니다

가람이 문서 도우미에게 문서 읽기를 맡겼습니다. 도우미가 가람의 비밀번호를 받아 모든 일을 대신할 필요는 없습니다. OAuth는 클라이언트가 제한된 자원 접근 권한을 얻는 틀입니다. 이것만으로 클라이언트가 사용자의 신원을 안전하게 확인한 로그인 규격이 되는 것은 아닙니다.

네 역할을 구별합니다. 자원 소유자는 가람, 클라이언트는 문서 도우미, authorization server는 허가에 따라 access token을 발급하는 서버, resource server는 토큰과 정책을 검사하는 document API입니다. 논리적 역할이므로 반드시 네 대의 서버를 뜻하지 않습니다.

## 같은 토큰도 요청에 따라 거절됩니다

기본 상태는 read scope로 write를 요청해 거절됩니다. scope를 늘리면 가람의 문서 수정은 통과하지만 소유자를 누리로 바꾸면 객체 정책에서 다시 거절됩니다. audience를 다른 API로 바꾸면 이 자원 서버용 표식이 아니므로 거절됩니다. 한 문을 통과한 사실을 나머지 문이 열린 증거로 쓰지 않습니다.

scope는 위임 범위를 표현하는 문자열입니다. read 같은 이름과 조합의 실제 의미는 서비스가 정의합니다. scope가 세부 객체 권한 전부를 대신하지 않으며, API는 실제 자원과 행동에 맞는 인가를 수행해야 합니다. 예시는 서명·만료 등 기본 토큰 검증을 이미 통과했다고 가정했습니다. 운영에서는 이 가정을 검사로 바꾸어야 합니다.

## access token과 ID Token의 수신자가 다릅니다

access token은 자원 API 접근을 위한 표식이며 반드시 JWT인 것도 아닙니다. OIDC의 ID Token은 클라이언트가 인증 결과를 검증하기 위한 것입니다. ID Token을 API용 access token처럼 바꿔 쓰거나, API가 받은 access token을 아무 클라이언트의 로그인 증명으로 재사용하지 않습니다.

브라우저 앱에 client secret을 넣어 배포해도 비밀이 되지 않습니다. 공개 클라이언트와 서버에서 비밀을 보관할 수 있는 클라이언트를 나누어 설계해야 합니다. 다음 장은 거래·교환을 서버 BFF가 맡는 한 가지 구조를 선택합니다. 모든 React 앱이 반드시 같은 구조여야 한다는 뜻은 아닙니다.

**확인 문제:** scope와 audience가 맞으면 누리의 문서 수정도 허용해야 할까요?

**해설:** 아닙니다. 토큰의 대상과 위임 범위가 맞아도 자원별 정책은 따로 검사합니다. 또한 이 실험의 API 허용은 앱 로그인 세션 생성과 별개입니다.
