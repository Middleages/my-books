## 브라우저가 운반한 것과 서버가 확인한 것은 다릅니다

로그인 버튼을 누르면 화면이 IdP로 이동했다가 앱으로 돌아옵니다. 이 왕복만 보면 브라우저가 로그인 전체를 끝낸 것처럼 보입니다. 하지만 code를 받아 서버끼리 교환하고, 받은 인증 결과를 검증하고, 앱 세션을 만드는 경계가 남아 있습니다.

여기서는 React 화면 앞에 FastAPI BFF가 있는 구조를 고릅니다. BFF는 로그인 거래와 PKCE verifier를 보관하고 token endpoint와 교환합니다. 브라우저는 code와 state를 callback으로 운반하지만 access token·ID Token 원문을 보관하지 않습니다. 실제 IdP의 사용자 확인과 필요한 BFF 클라이언트 인증은 정상이라고 가정해 생략했습니다.

## 여섯 단계에서 멈추는 위치가 다릅니다

1. BFF가 로그인 거래를 시작하고 요청과 연결할 state·nonce·PKCE 자료를 준비합니다.
2. 브라우저가 등록된 redirect와 code challenge를 포함한 인증 요청을 IdP로 전달합니다. 사용자 확인과 허가 과정을 거쳐 code가 발급됩니다.
3. IdP가 브라우저를 통해 code와 state를 callback으로 돌려보냅니다. BFF는 시작한 거래와 돌아온 응답의 연결을 확인합니다.
4. BFF가 code와 verifier로 token endpoint에 교환을 요청합니다. PKCE 연결과 code의 일회 사용 조건이 맞아야 합니다.
5. BFF가 ID Token의 서명·issuer·audience·시간 및 사용한 nonce를 검증합니다. 내용을 읽는 것과 수락하는 것은 다릅니다.
6. 검증을 마친 BFF가 앱 세션을 만들고 브라우저에 해당 세션 쿠키를 설정합니다. API 자원별 인가는 별도로 남습니다.

브라우저를 거치는 front channel과 서버 간 back channel은 경로 구분입니다. back channel이라는 이름이 TLS·키 관리·대상 검증을 생략해도 안전하다는 뜻은 아닙니다.

## state·nonce·PKCE를 한 칸으로 합치지 않기

state는 돌아온 응답을 시작한 거래와 연결하는 데 사용합니다. nonce는 이 예시에서 ID Token을 해당 인증 요청과 연결합니다. PKCE는 authorization request에 보낸 challenge와 code 교환 때 제시한 verifier를 연결합니다. 모두 중요하지만 서로의 검사 위치와 대상이 다릅니다. 이 모형은 세 장치를 함께 쓰는 code flow를 선택했고, 모든 흐름에 같은 필드가 무조건 필수라는 주장은 아닙니다.

등록 redirect는 엄격히 일치하도록 검증해야 하며 임의 주소로 code를 보내면 안 됩니다. code는 짧은 수명과 일회 사용 조건을 가진 교환 자료이지 장기 로그인 토큰이 아닙니다. 실패 후 무조건 교환을 반복하지 말고 거래 상태와 재사용 여부를 확인합니다.

## 구현하지 않은 경계를 기억합니다

화면은 이름표와 미리 정한 판정만 계산합니다. 암호학적 난수 생성·PKCE 해시·서명 검증·discovery·JWKS·TLS·실제 HTTP·쿠키는 실행하지 않습니다. 운영에서는 검증된 라이브러리와 IdP 지침을 따르고, 거래 자료의 보관·수명·재사용 방지 및 세션 고정 방어 등을 별도로 구현해야 합니다. code·token·쿠키·verifier 원문을 URL 분석 로그나 공개 디버그 기록에 남기지 않습니다.

**확인 문제:** token 응답은 정상인데 ID Token nonce가 다릅니다. 로그인 완료 화면을 먼저 보여도 될까요?

**해설:** 아닙니다. 이 거래의 인증 결과로 수락할 수 없으므로 앱 세션을 만들지 않습니다. 성공한 네트워크 교환과 성공한 인증 검증은 다른 결과입니다.
