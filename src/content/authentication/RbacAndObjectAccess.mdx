## 역할표의 한 칸만으로 끝나지 않습니다

editor가 수정 버튼을 눌렀습니다. 역할표에 수정이 허용되어 있으면 어떤 문서든 고칠 수 있을까요? 업무 권한은 역할뿐 아니라 요청한 자원·조직·소유 관계에도 달려 있습니다. 여기서는 서버가 매 요청의 현재 정책을 확인하도록 고정합니다.

정책은 합성 예시입니다. viewer는 같은 조직 문서를 읽고, editor는 여기에 본인 문서 수정을 더합니다. admin은 같은 조직 문서를 읽고 수정·삭제하지만 다른 조직 문서는 허용하지 않습니다. 실제 서비스마다 관리자의 범위가 다르므로 이 표를 일반 정책으로 복사하지 않습니다.

admin을 고르면 다른 조직 문서도 수정할 수 있을까요? 역할을 viewer로 바꿨는데 예전 token에 editor라는 claim이 남아 있다면 서버는 무엇을 기준으로 판단해야 할까요?

## 기본 거절과 독립된 검사

알 수 없는 역할이나 행동은 허용 목록에 없으므로 기본 거절합니다. 역할 검사를 통과해도 tenant가 다르면 거절하고, editor의 수정은 본인 소유인지도 확인합니다. 클라이언트가 보낸 문서 ID나 숨겨진 메뉴를 믿고 서버 검사를 생략하지 않습니다.

UI의 메뉴 숨김은 사용 경험을 바꿀 뿐 권한을 만들거나 없애지 않습니다. 다른 경로에서 같은 요청을 보낼 수 있으므로 서버가 매 요청 검사해야 합니다. Kubernetes의 Role·RoleBinding은 클러스터 API 자원에 대한 권한이고, 이 앱의 문서 수정 정책과 동일한 저장소가 아닙니다.

## 서명이 맞아도 권한 정보는 오래될 수 있습니다

역할 변경 반례에서는 현재 서버 정책 v2가 viewer인데 발급 당시 claim v1에는 editor가 남습니다. 서명과 시간 검증이 유효하다는 사실은 그 claim이 현재 권한과 같다는 보장이 아닙니다. 이 실험의 실제 판정은 현재 서버 권한 조회 결과를 사용하고, 점선은 옛 claim만 사용했을 때의 차이를 보여 줍니다.

운영에서는 현재 권한 조회, 캐시 수명, 권한 버전 확인, token 수명과 갱신·취소 정책 등을 요구사항에 맞게 선택합니다. 버전 숫자 하나를 화면에 붙였다고 권한 회수가 구현되는 것은 아닙니다. 중요한 권한 변경이 언제 어느 요청에 적용되는지 검증해야 합니다.

**확인 문제:** 과거 editor claim이 서명 검증을 통과했습니다. 현재 viewer로 변경된 사용자의 수정 요청을 무조건 허용해야 할까요?

**해설:** 아닙니다. 서명은 발급 당시 내용의 신뢰 문제이고 현재 인가는 별도 정책 문제입니다. 이 모형은 현재 정책을 조회해 수정 요청을 거절합니다.
