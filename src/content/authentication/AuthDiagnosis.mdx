## 증상을 원인으로 바꾸지 않기

사용자는 “로그인이 안 돼요”라고 말합니다. 앱 개발자는 로그인으로 반복 이동하는지, callback에서 거절되는지, 로그인 뒤 API 접근이 거절되는지부터 나눠야 합니다. **같은401이라도 audience와 만료 문제는 다른 질문**이고, 로그인 성공 뒤403은 별도의 인가 정책 문제일 수 있습니다.

이 장에서는 실패 경계를 증거로 좁히고, 조사를 돕는 기록과 남겨서는 안 되는 원문을 분리합니다. correlation ID는 한 조사 흐름을 묶는 식별자입니다. 아래 SIM-CORR은 특정 사람이나 실제 요청과 관계없는 가상 표식입니다.

## 한 경계에서 확인한 것만 말합니다

시작·callback·교환·로그인 검증·앱 session·API 인가는 논리적으로 이어지지만, 한 단계의 오류 기록이 앞의 모든 단계를 검증했다는 뜻은 아닙니다. 그림은 선택한 경계 외에는 물음표를 유지합니다. 실패 뒤 실행되지 않은 단계도 정상으로 칠하지 않습니다.

API의 access token audience 검사는 그 API를 위한 표식인지 묻는 질문입니다. 앞서 로그인에서 검증한 ID Token과 구분해야 합니다. 만료 표본은04장의 now=exp 거절, 권한 표본은08장의 현재 viewer에 update가 없는 판정을 다시 씁니다. 재로그인했다고 자동으로 권한이 생기지는 않습니다.

callback의 state 불일치는 시작한 로그인 거래와 응답이 연결되지 않는 증거입니다. 잘못된 저장·동시 거래·공격 등 원인은 추가 조사해야 합니다. 단순히 state 검사를 끄거나 곧바로 공격자를 확정하지 않습니다. JWKS 표본도 새 kid의 검증 키를 확보하지 못했다는 범위까지만 말합니다.

로그인 반복 표본은 앱 session을 다음 요청에서 찾지 못한 기록까지만 있습니다. Cookie 전송 범위인지, 서버 session 저장소인지, 만료인지 확인해야 하며 이 기록 하나로 IdP 장애를 확정하지 않습니다.

## 원문을 모으지 않아도 조사할 수 있습니다

단계·결과·제한된 이유 범주·가상 연결 ID로 사건을 연결합니다. Authorization과 Cookie header, authorization code, access/refresh/ID token, client secret, password 원문을 로그·URL·스크린샷·오류 추적 서비스에 넣지 않습니다. 토큰을 붙여넣어 확인하는 입력창도 이 교재에는 없습니다.

이 그림의 제외 영역은 필드 이름만 표시합니다. 민감 원문을 먼저 생성한 뒤 화면에서만 가리는 구현이 아닙니다. 실제 서비스는 allowlist로 기록 필드를 정하고, 프록시·앱·분석 도구까지 전송 경로를 확인해야 합니다. 오류 문자열이나 URL query가 자동 수집되는지도 점검합니다. 기록의 접근 권한·보존 기간·삭제 정책, 공격자가 넣은 개행 등 로그 주입도 별도로 고려해야 합니다. 가린 값이라고 무조건 개인정보가 아닌 것도 아닙니다.

## 작은 팀의 조사 순서

1. 증상이 나타난 경계와 시점을 적습니다. 실제 비밀값은 복사하지 않습니다.
2. 한 경계의 안전한 결과 범주를 확인하고 미확인 부분은 그대로 남깁니다.
3. DNS/TLS/키·시간 문제인지, 로그인 거래 문제인지, 앱 session인지, API 인가인지 다음 질문을 정합니다.
4. 원인을 확인한 뒤 별도 절차로 수정하고 같은 조건을 재검증합니다. 검증 기능을 끄거나 자동으로 권한을 늘리지 않습니다.

확인 문제: API403을 본 뒤 IdP와 token 원문을 모두 수집하면 가장 안전한 진단일까요?

해설: 아닙니다. 필요한 인가 경계와 현재 정책부터 확인합니다. 원문 수집은 노출 위험을 늘리고, 현재 역할·객체·tenant 정책 문제를 대신 설명하지 못합니다. 실제 HTTP 상태와 오류 범주의 대응은 서비스 구현에 따라 달라지므로 공급자 문서와 안전한 서버 기록을 함께 봅니다.
