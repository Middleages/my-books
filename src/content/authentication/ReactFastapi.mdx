## 기능이 같아도 신뢰 경계는 다릅니다

React 화면에서 FastAPI를 호출하는 앱에 SSO를 붙이려고 합니다. 브라우저가 OAuth client 역할을 맡을지, 서버가 대신 맡을지 먼저 정해야 합니다. 이 장에서는 **token 저장 위치, 로그인 책임, API 호출 경로, 남는 보안·운영 책임**을 같은 기준으로 비교합니다.

SPA는 화면 전환과 상당한 로직을 브라우저에서 처리하는 앱입니다. 브라우저로 내려간 코드는 사용자가 읽을 수 있으므로 client secret을 숨길 수 없는 public client입니다. BFF는 이 화면을 위한 서버 구성 요소로 OAuth 책임을 맡는 방식입니다. 서버에서 client 인증 수단을 보호하는 confidential client와, 브라우저의 앱 세션을 나눌 수 있습니다.

### 먼저 예측해요

client secret을 React 환경 변수로 빌드하면 비밀이 될까요? token을 서버에 보관하고 HttpOnly cookie를 쓰면 악성 JS의 모든 위험이 사라질까요?

## 무엇이 어디를 지나가는지 봅니다

BFF 방식에서는 브라우저가 앱 세션 cookie로 BFF를 호출하고, BFF가 서버에 보관한 access를 붙여 API를 호출합니다. SPA 방식은 브라우저가 code+PKCE 교환을 맡고 access를 API에 직접 제시합니다. PKCE는 브라우저에 client secret을 안전하게 숨겨 주는 기술이 아닙니다. 두 방식 모두 로그인 거래의 검증과 API의 역할·객체 인가는 남습니다.

그림의 BFF와 API는 책임을 나누어 그린 것입니다. 반드시 서로 다른 장비에 둬야 한다는 뜻은 아닙니다. FastAPI가 BFF 역할과 자원 서버 역할을 같이 맡는 경우에도 각각의 검증과 저장 경계를 설명할 수 있어야 합니다.

## token 읽기와 요청 대행은 다릅니다

BFF는 OAuth token을 브라우저 JS에 직접 노출하지 않는 경계를 만듭니다. 그렇다고 HttpOnly가 XSS 자체를 막는 것은 아닙니다. 악성 JS가 앱의 origin에서 실행되면 사용자 브라우저를 통한 요청 대행 위험이 남습니다. SPA의 메모리 보관도 악성 JS에 대한 완전한 방어가 아닙니다.

cookie를 쓰는 경계에서는 SameSite뿐 아니라 서비스에 맞는 Origin 확인과 CSRF 방어를 설계합니다. bearer를 직접 붙이는 API라도 로그인 거래와 다른 cookie 경계를 무시하지 않습니다. 앞 장의 CORS는 응답 읽기 경계이며 인증·인가나 모든 CSRF 방어를 대신하지 않습니다. 여기서는 위험을 비교할 뿐 실제 공격 요청이나 성공 판정을 실행하지 않습니다.

## 작은 팀이 적어 볼 결정표

- 보호할 자료와 사용자 영향은 무엇인가요?
- 누가 세션·token 저장과 갱신을 운영하나요?
- 여러 서버 인스턴스에서 상태와 철회를 어떻게 공유하나요?
- 로그인·API·갱신 장애를 어떻게 구별하고 복구하나요?
- 브라우저 노출, CSRF/XSS 방어, 로그 제거, 키 갱신을 누가 검토하나요?

BFF가 필요로 하는 서버 운영을 감당할 수 있는지, SPA의 브라우저 노출과 갱신 책임을 검토할 수 있는지 함께 판단합니다. 임의의 안전 점수로 우승 구조를 고르지 않습니다. 폐쇄망에서도 내부 IdP·DNS·TLS·시각·키 갱신 의존성을 확인해야 합니다.

FastAPI의 password JWT 튜토리얼은 비밀번호 검증과 bearer 사용을 배우는 예시이지 OIDC SSO 통합 완성본이 아닙니다. 신규 SSO에 password grant나 implicit flow를 기본으로 붙이지 않습니다. 실제 공급자의 code+PKCE/OIDC 안내와 지원 라이브러리를 확인해야 합니다.

### 확인 문제

1. React 빌드에 들어간 client secret은 안전한가요? 아니요. public client에는 보호 가능한 secret이 없다고 설계합니다.
2. BFF가 있으면 API의 객체 인가를 없애도 되나요? 아니요. 로그인된 사용자가 이 자원에 이 행동을 할 수 있는지는 서버에서 확인해야 합니다.
3. BFF의 HttpOnly cookie는 악성 JS가 요청을 보내는 것도 막나요? cookie 직접 읽기 제한과 요청 대행 방지는 다릅니다.

### 출처와 확인일

2026-10-20 확인. [IETF browser-based apps draft27](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-browser-based-apps-27)은 진행 중인 문서이며 확정 RFC가 아닙니다. [RFC9700 보안 권고](https://www.rfc-editor.org/rfc/rfc9700.html), [FastAPI password와 JWT 튜토리얼](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/). [OWASP XSS 방어](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)와 [CSRF 방어](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)도 확인했습니다. 이 장은 교육용 지도이며 실제 SSO 연결·배포·보안 인증을 수행하지 않습니다.
