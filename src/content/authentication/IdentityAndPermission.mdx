## 로그인 성공은 모든 문서의 열쇠일까요?

목표는 **인증된 주체와 자원별 허용 판단을 구분하고, 화면 버튼과 서버 정책의 경계를 설명하는 것**입니다.

인증(authentication)은 요청한 쪽이 누구인지 확인하는 과정입니다. 인가(authorization)는 확인한 주체가 특정 자원에 어떤 행동을 해도 되는지 판단하는 과정입니다. 문서 조회와 수정은 다른 행동이며, 같은 수정이라도 누구의 문서인지에 따라 판단이 달라질 수 있습니다.

가람은 편집자(editor), 누리는 열람자(viewer)입니다. 가상 문서함의 규칙은 “같은 팀의 문서는 조회 가능, 수정은 편집자인 소유자만 가능”입니다. 역할의 이름 자체가 권한은 아닙니다. 그 역할에 허용 행동을 연결한 정책과 자원 조건이 있어야 합니다.

### 먼저 예측하세요

편집자인 가람이 로그인한 뒤 누리의 문서를 수정하려고 합니다. 인증 문은 열려도 인가 문이 닫힐 수 있을까요? 소유자를 가람으로 바꾸면 어느 검사 결과가 달라져야 할까요?

## 두 번째 문에도 두 질문이 있습니다

역할 검사는 “이 역할에 수정 행동이 있는가”를 봅니다. 객체 정책은 “이번 문서의 소유자인가”를 봅니다. 기본 장면에서 가람은 첫 검사에 통과하지만 다른 소유자 문서라 두 번째 검사에서 거절됩니다. 로그인했다는 사실을 그대로 허용으로 바꾸지 않습니다.

누리는 자기 문서여도 viewer이므로 수정이 거절됩니다. 반대로 이 예제에서는 같은 팀 문서의 조회를 허용합니다. 실제 앱의 공유 문서·관리자 예외·조직 간 경계·비공개 문서는 별도 정책으로 설계해야 합니다. 실험은 같은 팀만 고정하므로 다른 조직의 접근까지 안전하다고 증명하지 않습니다.

주체는 표시이름만으로 구분하지 않습니다. 같은 “가람”이라도 어느 인증 제공자가 발급한 어떤 subject인지가 다를 수 있습니다. 실험은 id.example.test와 sim-garam 같은 합성 식별자를 사용하고 이메일만 같다고 계정을 합치지 않습니다.

## 버튼을 숨겨도 서버 검사는 남습니다

React 화면에서 수정 버튼을 감추는 것은 사용자 경험을 돕지만 요청을 보낼 수 없게 만드는 보안 경계는 아닙니다. 화면을 거치지 않고 API에 요청할 수도 있기 때문입니다. FastAPI 같은 서버에서는 요청마다 주체와 대상 자원·행동을 확인하고 허용되지 않은 요청을 거절해야 합니다. 프레임워크를 사용한다고 올바른 객체 정책이 자동으로 생기는 것은 아닙니다.

401과 403 같은 HTTP 상태는 진단의 단서입니다. 일반적으로 인증 문제와 접근 거절을 구별하는 데 쓰이지만 프록시·제품·자원 존재 숨김 정책에 따라 응답이 달라질 수 있습니다. 상태 코드 하나만 보고 실제 원인을 확정하지 말고 서버의 안전한 오류 범주와 정책 검사를 확인하세요. 내부망도 잘못된 계정·권한·요청에서 자유롭지 않으므로 인증과 인가를 생략할 근거가 되지 않습니다.

## 확인해 보세요

- 가람이 로그인했지만 누리 문서 수정이 거절됩니다. 로그인 실패인가요? 아닙니다. 주체 확인은 성공하고 객체 정책이 거절한 것입니다.
- 누리 문서의 소유자가 누리면 언제나 수정 가능한가요? 이 정책에서는 viewer 역할에 수정 권한이 없어 거절됩니다.
- 화면 버튼을 없애면 API 검사도 생략해도 되나요? 아닙니다. 서버는 별도로 요청마다 확인해야 합니다.
