## 다시 입력하지 않았다고 왕복이 없었던 것은 아닙니다

앱 A를 쓰다가 앱 B를 열었는데 비밀번호를 다시 묻지 않습니다. B가 A의 쿠키를 복사한 것일까요? SSO에서는 IdP에서 이미 확인한 상태를 활용할 수 있지만, 각 앱이 자기 로그인 거래를 검증하고 세션을 만드는 경계는 남습니다.

IdP와 앱 A·B의 세션은 같은 물건이 아닙니다. 수명과 로그아웃 범위도 다를 수 있습니다. 여기서는 세 주소의 저장소를 따로 그리고 전역 로그아웃 연동은 끈 고정 환경을 사용합니다.

### 먼저 예측해요

A에서 로그아웃하면 B의 세션도 바로 사라질까요? IdP의 세션이 만료됐는데 B는 이미 유효한 자기 세션을 가지고 있다면 어떨까요?

## 세 섬을 따로 읽습니다

IdP만 로그인한 상태에서 B를 처음 방문하면 B의 로그인 왕복이 필요합니다. 이 표본은 IdP가 기존 인증 상태를 재사용할 수 있어 자격증명 재입력을 생략하지만, B의 결과 검증과 새 세션 생성은 그대로 수행합니다. 실제 서비스는 추가 인증·동의·정책 때문에 다시 물을 수도 있습니다.

A 로컬 로그아웃은 A 세션만 지웁니다. 이것을 모든 앱·모든 token의 전역 무효화와 같다고 말하면 안 됩니다. IdP 세션이 만료됐어도 이미 유효한 B 세션을 계속 허용하는 정책이 있을 수 있습니다. 반대로 세션 변경 알림이나 logout 연동을 구현한 시스템은 다른 결과를 만들 수 있으므로 실제 정책을 확인해야 합니다.

OpenID Connect에는 세션 상태 확인과 여러 로그아웃 방식에 관한 별도 규격이 있습니다. ‘SSO 사용 중’이라는 말만으로 어떤 방식이 구현되어 있고 통지가 성공했는지까지 알 수 없습니다. 앱 세션 종료, IdP 로그아웃, access/refresh token 처리를 나눠 설계해야 합니다.

**확인 문제:** B에서 비밀번호 입력을 생략했습니다. B가 인증 결과 검증도 생략해도 될까요?

**해설:** 아닙니다. 입력 생략과 검증 생략은 다릅니다. B는 자기 요청에 대한 결과를 올바르게 검증한 뒤 자신의 세션을 만들어야 합니다.

## 근거와 한계

확인일2026-10-20. [OIDC Session Management](https://openid.net/specs/openid-connect-session-1_0.html), [RP-Initiated Logout](https://openid.net/specs/openid-connect-rpinitiated-1_0.html)를 참고했습니다. 특정 iframe 구현이나 제품의 기본 동작을 그대로 재현하지 않습니다. 세션 값·순서·상태는 자체 합성 fixture이며 실제 계정·쿠키·SSO·logout 요청은 없습니다.
