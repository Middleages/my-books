차트는 리소스를 만드는 문서 재료입니다. 차트만 반입해도 이미지가 함께 들어오는 것은 아닙니다. 이 책의 chart는 외부 의존성이 없지만 일반 chart는 subchart·hook Job·initContainer까지 포함해 실제 렌더에서 필요한 이미지 목록을 확인해야 합니다. 운영 환경의 아키텍처와 버전에 맞는 파일인지도 확인합니다.

## 2. 기본 경로 하나를 먼저 완결하기

[첫 배포 부록](#/kubernetes/lab-first-deployment)의 단일 VM 기본은 **고정 k3s 바이너리 + 같은 버전의 airgap 이미지 묶음 + 직접 만든 앱 이미지 tar**를 반입하는 경로입니다. 외부에서 다운로드할 때 버전·아키텍처·체크섬·획득일·라이선스/배포 조건·검토한 설치 스크립트 해시를 함께 기록합니다. OS 패키지·커널·cgroup·호스트 route·시간 서비스·DNS도 반입 파일 밖의 전제 조건입니다.

```sh
# 새 일회용 Linux VM. 검증한 파일을 이미 반입한 뒤의 경로 예시.
# k3s와 k3s-airgap-images-amd64.tar.zst는 반드시 동일 release에서 받음.
sudo install -m 755 ./k3s /usr/local/bin/k3s
sudo install -d /var/lib/rancher/k3s/agent/images
sudo install -m 600 ./k3s-airgap-images-amd64.tar.zst /var/lib/rancher/k3s/agent/images/
# 검토·해시 확인한 공식 install.sh만 실행. 다운로드 생략은 이미지 전체 제공을 대신하지 않음.
sudo env INSTALL_K3S_SKIP_DOWNLOAD=true sh ./install.sh
sudo k3s --version
sudo k3s crictl images
sudo k3s kubectl get pods -n kube-system
```

직접 만든 `study-web-images.tar`는 별도 `k3s ctr images import` 대상입니다. 첫 설치 뒤 시스템 이미지와 앱 이미지가 모두 있어야 합니다. 모든 노드가 실행 후보라면 노드마다 반입합니다. 조건부 이미지 import 캐시는 삭제된 이미지가 자동 복원되지 않을 수 있으므로 기본 입문 경로에서는 켜지 않습니다. 이 명령은 안내이며 제작 환경에서 실제 설치하지 않았습니다.

## 3. registry를 사용하는 별도 경로

노드 runtime이 내부 registry를 호출합니다. 노드의 `/etc/rancher/k3s/registries.yaml`에 mirror endpoint·인증·CA를 설정하고 해당 노드에 적용한 뒤 k3s 재시작과 pull 관측을 검토합니다. 아래는 **설명용 가상 주소·파일**이며 그대로 접속 가능한 환경이 아닙니다. 실제 자격 증명을 이 사이트에 입력하지 않습니다.

```yaml
mirrors:
  docker.io:
    endpoint:
      - "https://registry.example.test"
configs:
  "registry.example.test":
    tls:
      ca_file: /etc/rancher/k3s/registry-ca.pem
```

인증이 필요하면 registry가 정한 계정/토큰 또는 imagePullSecret의 전달 범위를 따로 정하고 파일 접근을 제한합니다. CA 파일이 있어도 이미지 경로·태그·권한·SAN·시간·registry 내부 콘텐츠가 틀리면 pull은 실패합니다. mirror에는 이미지 이름과 태그가 실제로 준비돼 있어야 합니다.

containerd는 기본 endpoint로도 재시도할 수 있습니다. 완전 폐쇄망은 `--disable-default-registry-endpoint`와 mirror 목록을 함께 검토하며, 이 옵션은 registries.yaml에 mirror로 설정한 registry에 적용된다는 범위를 지킵니다. 방화벽 정책 전체를 대신하지 않습니다. TLS 검증 끄기를 기본 해법으로 안내하지 않습니다.

이 경로로 앱 이미지를 제공한다면 manifest·chart의 `image`를 **실제로 게시하고 확인한 내부 주소/digest**로 바꾸고 `imagePullPolicy`도 의도에 맞춰 변경합니다. 기본 패키지의 `Never`는 로컬 import 경로 전용입니다. 가상 registry 주소로 바꾼 YAML을 실행 검증 완료라고 쓰지 않습니다.

## 4. 프록시·DNS·시간은 어느 위치의 설정인가?

<div className="k8-table" role="region" aria-label="호출 주체별 접속 조건" tabIndex={0}>

| 호출 주체 | 확인할 조건 | 다른 검증으로 대신할 수 없는 것 |
| --- | --- | --- |
| 설치 도구·노드 runtime | 호스트 DNS·outbound proxy·registry CA·인증 | 브라우저의 인증서 성공 |
| Pod 안 앱 | CoreDNS·Pod route·앱 CA·DB 권한·앱 proxy 환경 | 노드 curl 성공 |
| NGINX upstream | upstream DNS·SNI·검증 이름·CA·포트 | 사용자 PC OpenSSL 성공 |
| 사용자 브라우저 | 접속 도메인·SAN·브라우저 신뢰·시각 | runtime의 registry CA |

</div>

서비스 프록시 환경에는 내부 노드·Pod/Service CIDR·클러스터 DNS suffix·내부 registry 등의 NO_PROXY 계획이 필요합니다. 실제 CIDR과 DNS 이름을 확인해 지정하며 배포판/도구의 NO_PROXY 처리 차이도 검사합니다. 프록시 주소를 Pod 전체에 무작정 복사하지 않습니다. K3s는 일부 내부 범위를 자동 추가하지만 조직의 내부 주소 전체를 자동으로 알지는 못합니다.

DNS는 호스트와 Pod 안 양쪽에서 확인합니다. 시간은 NTP/내부 시간원으로 맞추고 서버·클라이언트의 UTC 시각과 인증서 유효기간을 비교합니다. kubelet resolv-conf 같은 옵션은 실제 상위 DNS 구성을 확인한 뒤 선택합니다. 한 줄 DNS 또는 CA 설정으로 모든 사내 환경이 해결된다고 가정하지 않습니다.

## 5. 기존 443 NGINX를 유지하며 앱 하나씩

<article><h3>시험한 내부 입구</h3><p>NGINX → controller 전용 포트 → Service</p><strong>기본 80/443 점유와 다른 계획 필요</strong></article>
<article><h3>앱과 DB 경계</h3><p>Pod :8080 → 기존 외부 DB</p><strong>DNS·CA·권한·스키마·복구 책임 유지</strong></article>
</div>

이 그림은 포트 계획입니다. 실행 가능한 공존 설치 YAML은 아니며 기존 NGINX를 제거하라는 뜻도 아닙니다. 기본 k3s의 Traefik LoadBalancer Service를 ServiceLB가 받아 노드 80/443을 사용할 수 있으므로, 기존 리스너와 겹치는 기본 설치를 진행하지 않습니다.

05장의 30080/30443은 controller Service를 NodePort로 **별도 구성한 경우의 예시**입니다. 기본 설치가 자동으로 그 포트를 제공하지 않습니다. controller 차트의 고정 버전 값과 Service 타입, ServiceLB의 적용 여부, 노드 접근 범위·방화벽을 먼저 검토합니다. ServiceLB를 끄는 것만으로 요청 경로가 완성되는 것도 아닙니다. 앱을 직접 hostPort로 열어 우회하기보다 실제로 어떤 리스너가 경계를 맡는지 확인합니다.

시험 경로에서 HTTP와 HTTPS upstream을 구분합니다. NGINX에서 TLS를 끝내고 backend를 HTTP로 쓰면 그 구간은 암호화되지 않습니다. 다시 HTTPS를 쓰면 NGINX가 검증하는 이름·SNI·CA를 별도로 맞춥니다. 외부 인증서 성공은 이 내부 검증을 대신하지 않습니다.

외부 DB는 같은 주소라도 Pod의 네트워크·CA·인증 조건이 달라집니다. 운영 DB를 시험 중 바꾸지 말고 격리된 테스트 DB나 읽기 전용 확인부터 계획합니다. 시험 앱의 성공 뒤 라우팅 한 개를 전환하고, 원래 경로·오류 기준·되돌릴 담당자와 데이터 호환성 조건을 기록합니다. 최종 선택은 [12장 전환 계획](#/kubernetes/troubleshooting)과 연결합니다.
