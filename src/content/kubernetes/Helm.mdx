## 1. 완성된 문서 여러 벌 대신, 틀과 값을 나누기

앞 장까지 Deployment·Service·ConfigMap을 각각 살펴봤습니다. 앱 하나의 설치에는 이 리소스들이 함께 필요할 수 있습니다. **Helm**은 이런 Kubernetes 리소스의 명세를 묶고, 설정을 넣어 생성하며, 설치와 변경의 이력을 관리하는 도구입니다.

<strong>차트(chart)</strong>는 명세를 만드는 파일 묶음입니다. `Chart.yaml`은 이름·차트 버전 같은 정보를, `templates/`는 출력할 명세의 틀을, `values.yaml`은 기본 설정값을 담습니다. 설정값을 별도 파일로 덮어쓰면 같은 틀에서 다른 YAML을 만들 수 있습니다. 모든 values 키가 자동으로 Kubernetes 필드가 되는 것은 아닙니다. **템플릿이 참조한 값**이 출력에 반영됩니다.

요리법과 재료 분량을 생각해 보세요. 요리법이 chart, 선택한 분량이 values, 실제 작업 지시서가 렌더링 YAML에 가깝습니다. 하지만 출력된 지시서가 음식을 만들지는 않습니다. API 적용과 controller·scheduler·kubelet의 실행 책임은 02장의 구조 그대로입니다.

<div className="k8-table" role="region" aria-label="같은 차트의 환경 값 비교" tabIndex={0}>

| 같은 chart 0.1.0 | 개발 values | 운영 values | 출력에서 바뀌는 곳 |
| --- | --- | --- | --- |
| Pod 개수 | replicas: 1 | replicas: 2 | Deployment.spec.replicas |
| 일반 안내 문구 | 개발 안내 | 운영 안내 | 별도 ConfigMap의 APP_MESSAGE |
| 앱 이미지 라벨 | v1 | v1 | 두 환경에서 동일 |
| 연결 포트 | 80 → 8080 | 80 → 8080 | 이 예에서는 동일 |

</div>

숫자는 비교용입니다. 운영에 2개면 충분하다는 권장이 아니며 같은 VM의 두 Pod가 VM 장애에 대비해 주지도 않습니다. 실제 비밀값을 values 예제나 Git에 넣지 않습니다. Helm 출력과 릴리스 저장 정보에도 민감한 값이 남을 수 있으므로, Secret 보호는 06장의 권한·저장 보호와 함께 설계합니다.

## 3. 네 가지 동사는 무엇을 바꿀까?

<strong>렌더링(rendering)</strong>은 틀과 값을 합쳐 구체적인 문서를 만드는 과정입니다. <strong>릴리스(release)</strong>는 차트를 설치해 Helm이 관리하는 한 설치 단위입니다. 같은 차트를 서로 다른 이름·namespace로 설치하면 별도 릴리스가 될 수 있습니다. 이 장의 가상 릴리스 이름은 `study`, 리소스 이름은 `study-web`, namespace는 `books-lab`입니다. 이 세 이름이 항상 같아야 하는 것은 아닙니다.

<div className="k8-table" role="region" aria-label="Helm 명령별 변경 범위" tabIndex={0}>

| 작업 | 읽는 것 | 결과와 확인할 경계 |
| --- | --- | --- |
| template | chart + values | 기본 로컬 렌더 결과 출력. 설치·릴리스 기록 없음 |
| install | chart + values | 새 릴리스와 리소스 적용. 실제 준비·업무 동작은 관측 필요 |
| upgrade | 기존 release + 새 chart/values | 설치된 묶음 변경과 새 릴리스 revision |
| rollback | 보관된 과거 release revision | 과거 명세를 대상으로 다시 변경. 되돌리기 자체도 새 이력 |

</div>

`helm template`이 출력에 성공해도 실제 클러스터의 API 지원·권한·admission 정책·이미지 접근·자원 여유를 검증한 것은 아닙니다. 반대로 Helm이 설치를 수행해도 이후의 앱 상태를 계속 조정하는 주체는 Kubernetes controller입니다. Helm은 scheduler를 하나 더 설치하는 개념이 아닙니다.

CLI 설명 기준은 **Helm 4.3.1 공식 명령 문서**입니다. 이 화면은 브라우저 모델입니다. 실제 CLI의 로컬 렌더 확인과 클러스터 실행의 차이는 [선택 실습 부록](#/kubernetes/lab-first-deployment)에서 구분합니다. 아래 `./study-web`과 `values-dev.yaml`은 완전한 로컬 차트와 설정 파일을 준비했다는 전제의 **명령 형태 예시**이며 이 장에서 제공되는 실행 패키지가 아닙니다.

```sh
# 관리 터미널: 대상 확인과 로컬 출력 (변경 전)
helm version
kubectl config current-context
helm template study ./study-web -n books-lab -f values-dev.yaml

# 아래는 클러스터를 변경함: 일회용 실습환경과 파일을 준비한 뒤 검토
helm install study ./study-web -n books-lab -f values-dev.yaml --wait
helm upgrade study ./study-web -n books-lab -f values-dev.yaml --wait

# 관리 터미널: 관측과 이력 확인
helm history study -n books-lab
helm status study -n books-lab
kubectl rollout status deployment/study-web -n books-lab

# 실제 변경: history에서 확인한 revision 1이 복원 대상인 경우만
helm rollback study 1 -n books-lab --wait
```

`--wait`는 정해진 리소스 준비를 기다리는 옵션이며 업무의 정상 동작까지 증명하지 않습니다. Helm 4의 기다림 방식과 실패 처리 옵션을 Helm 3 예제와 섞지 마세요. Helm 4.3.1에는 명시적인 `--rollback-on-failure` 정책도 있습니다. 이 장에서는 자동 실패 복구를 켜지 않은 네 동작을 비교하며, Helm이 있다는 사실만으로 실패 시 자동 복원을 약속하지 않습니다.

## 4. revision이라는 이름이 같아도 다른 이력이다

실험에서 `upgrade`와 `ConfigMap 내용만`을 고르고 끝까지 진행하세요. Helm revision은 1 → 2가 되지만 Deployment revision은 1입니다. ConfigMap이 Helm 릴리스에 속하므로 변경 이력은 생기지만, 이 차트는 ConfigMap 내용 해시를 Pod template에 주입하지 않아 Pod template이 바뀌지 않습니다. 기존 프로세스가 새 문구를 읽는지는 06장의 환경변수·파일·재읽기 조건에 달렸습니다.

`replicas만 +1`도 Pod template 변경은 아닙니다. 반면 이미지 v1 → v2는 template을 바꾸므로 Deployment controller가 이를 관측하면 Deployment revision도 변합니다. 실험에서 초기화해 두 변경을 비교하세요. 차트의 `version`, 정보용 `appVersion`, 이미지 태그, Helm revision, Deployment revision을 하나의 버전 번호로 취급하지 않습니다.

`rollback`은 revision 2에서 시작해 보관된 1의 명세를 적용하고 Helm revision 3으로 기록합니다. 이미지 변경 사례에서는 이전 Pod template을 다시 쓰더라도 Deployment 이력 번호가 새로 부여될 수 있습니다. 이전 UID의 Pod와 시간을 복원하는 것이 아닙니다. 번호는 기존 이력과 보존 정책에 따라 달라지므로 실무에서는 두 history를 직접 봅니다.

## 5. 차트 신뢰와 되돌리기의 경계

차트는 보기 좋은 설정 화면 이상의 권한을 행사할 수 있습니다. 출처·고정 버전·의존 차트·렌더 결과·요구 권한을 검토하세요. <strong>hook</strong>은 설치·업데이트 등의 시점에 추가 작업을 실행하는 장치입니다. hook이 DB를 변경했다면 명세 rollback만으로 그 작업의 결과가 되돌아간다고 볼 수 없습니다.

<strong>CRD</strong>는 Kubernetes에 새 리소스 종류를 정의합니다. Helm의 `crds/` 처리는 일반 템플릿과 다르며 CRD 업그레이드·삭제를 일반 리소스처럼 자동 처리한다고 기대하지 않습니다. 해당 차트의 관리 절차를 따로 확인합니다. 이 실험에는 hook·CRD·의존 chart를 넣지 않았습니다.

07장의 PVC 데이터, 외부 DB, 별도 서비스의 상태는 Helm revision 번호의 범위 밖입니다. 차트에 ConfigMap이 포함되면 그 명세를 되돌릴 수 있어도 **앱이 읽은 값과 외부 데이터까지 같은 시점으로 복구되는 것은 아닙니다.** 이전 코드와 현재 데이터의 호환성을 확인한 뒤 되돌립니다.
