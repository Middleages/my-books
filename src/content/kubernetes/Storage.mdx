## 1. 같은 메모를 세 곳에 써 보기

설정을 바꾸는 [06장](#/kubernetes/configuration)과 달리 이번에는 앱이 실행 중에 **새로 쓴 파일**을 봅니다. 가상의 파일 저장 앱 `study-data`는 한 번에 Pod 하나만 실행합니다. 무상태 웹앱 `study-web`과 별개의 사례입니다.

메모 A를 `/app/note.txt`, `/scratch/note.txt`, `/data/note.txt`에 각각 씁니다. 경로 이름만 보면 비슷하지만 연결한 저장 방식이 다릅니다.

- **writable layer(쓰기 계층):** 컨테이너 실행 중 이미지 위에 변경을 기록하는 공간입니다. 새 컨테이너를 만들 때 이전 실행의 변경을 지속 데이터로 가져오는 곳이 아닙니다. 이미지를 다시 받아도 런타임에 쓴 메모는 이미지에 들어 있지 않습니다.
- **emptyDir:** Pod가 노드에서 사용하는 임시 볼륨입니다. 같은 Pod의 컨테이너끼리 공유할 수 있고 컨테이너가 다시 시작해도 남습니다. Pod가 제거되면 그 수명도 끝납니다. 여기서는 메모리형이 아닌 디스크형을 선택합니다.
- **PVC로 연결한 저장소:** Pod보다 긴 수명을 가진 볼륨을 요청하고 연결합니다. 이 실험에서는 그 저장소도 같은 노드의 디렉터리입니다. 수명이 길다는 것과 다른 장비에 복제됐다는 것은 다릅니다.

먼저 ‘컨테이너 재시작’을 끝까지 관찰한 뒤 ‘Pod 교체’로 바꿔 보세요. **메모가 남았는지와 새 앱이 읽을 수 있는지를 함께** 확인합니다.

## 2. PVC와 PV는 파일의 위치를 연결한다

**PVC(PersistentVolumeClaim)**는 앱이 필요한 저장 공간을 요청하는 namespace 안의 객체입니다. **PV(PersistentVolume)**는 제공된 저장 자원을 나타내는 클러스터 범위의 객체입니다. PVC가 PV와 연결되는 상태를 **Bound**라고 부릅니다. Pod는 PVC를 참조해 자신의 경로에 볼륨을 마운트합니다. 마운트는 그 저장 공간을 앱의 파일 경로로 사용할 수 있게 연결하는 일입니다.

그림의 점선 API 상자에는 연결 정보가 있고, 디스크 상자에 파일 바이트가 있습니다. PVC 객체를 백업했다고 파일 내용까지 백업되는 것은 아닙니다. 반대로 디스크에 파일이 남아 있어도 알맞은 PV/PVC·마운트와 앱 설정이 없으면 앱이 읽지 못합니다.

**StorageClass**는 저장 공간을 어떤 provisioner(공간을 마련하는 구성 요소)와 정책으로 제공할지 정하는 기준입니다. 이 책의 k3s 후보는 `local-path-provisioner v0.0.37`입니다. 기본 local-path 방식은 선택한 노드의 디렉터리를 사용합니다. 여러 노드가 공유하는 원격 디스크라고 생각하면 안 됩니다. 이 실험은 이미 Bound인 상태에서 시작하므로 최초 PVC 생성·노드 선택·공간 준비 순서는 생략합니다.

## 3. 무엇을 지웠는지에 따라 결과가 다르다

| 사건 | writable layer의 메모 | 디스크형 emptyDir의 메모 | local-path PVC 데이터 |
| --- | --- | --- | --- |
| 같은 Pod의 컨테이너 재시작 | 새 실행에 이어지지 않음 | 유지 | 유지 |
| 같은 정상 노드에서 Pod 교체 | 이어지지 않음 | 이전 Pod의 데이터 제거 | 기존 PVC 재마운트 성공 시 읽음 |
| 노드 접근 불가 | 지금 읽을 수 없음 | 지금 읽을 수 없음 | 지금 읽을 수 없음; 데이터 삭제 여부는 별도 확인 |
| 노드 디스크 영구 상실 | 상실 | 상실 | 같은 디스크의 데이터도 상실 |
| PVC 삭제와 사용 Pod 제거 | Pod 제거로 수명 종료 | Pod 제거로 수명 종료 | PV reclaim 정책과 정리 결과에 따름 |

노드가 잠시 응답하지 않는 것과 디스크가 영구적으로 사라진 것은 다른 사건입니다. 그래서 실험도 두 선택으로 나눴습니다. 단일 VM이 멈추면 API도 함께 멈출 수 있습니다. 이때 화면의 Bound는 **마지막 기록**이며 저장소가 지금 정상이라는 실시간 증거가 아닙니다.

## 4. Delete와 Retain은 백업 정책이 아니다

**reclaim policy(회수 정책)**는 PVC 사용이 끝난 뒤 PV와 연결된 저장 자원을 어떻게 처리할지 정합니다. 일반적인 local-path 기본 설정은 Delete이지만, 실제 운영에서는 **해당 PV의** `persistentVolumeReclaimPolicy`를 읽어 확인해야 합니다. StorageClass 설정만 바꿨다고 이미 생성된 모든 PV가 함께 바뀌었다고 가정하지 않습니다.

- **Delete:** provisioner가 정상적으로 정리를 끝내면 PV와 연결된 저장 공간이 삭제됩니다. 실험의 마지막 단계는 정리 성공 후입니다. 삭제 요청과 물리적 삭제 완료는 같은 순간이 아닙니다.
- **Retain:** PVC가 사라져도 PV와 데이터는 남습니다. PV는 Released 상태가 되고 관리자가 내용을 확인해 재사용·정리할 수 있습니다. 앱이 자동으로 재연결되거나 백업에서 복원된 상태가 아닙니다.

사용 중인 PVC는 보호 장치 때문에 삭제가 보류될 수 있습니다. 실험은 **삭제 요청 → 사용 Pod 제거 → PVC 삭제 완료 → 정책에 따른 정리**를 나눕니다. 보호 장치는 우발적 사용 중 삭제를 지연시키는 것이며, 데이터를 영구 보존하는 백업은 아닙니다.

Retain을 선택하고 PVC 삭제 실험을 끝까지 진행해 보세요. 파일은 남지만 앱이 없고 PVC 연결도 없습니다. “데이터가 남는다”와 “서비스가 복구됐다” 사이에 관리 작업이 있다는 것을 보여 주는 사례입니다. 실제 삭제·복구 명령은 이 장에서 실행하지 않습니다.

## 5. 데이터의 복구 책임을 따로 정하기

단일 replica는 여러 파일 작성자가 충돌하는 문제를 단순화하려는 교육 조건입니다. replica를 늘린다고 같은 로컬 파일이 자동 동기화되지 않습니다. `ReadWriteOnce` 역시 일반적으로 한 노드에서 읽고 쓰는 접근 모드이지, 앱 수준의 단일 작성자 잠금이나 데이터 복제 기능이 아닙니다.

외부 PostgreSQL 같은 DB를 쓰는 웹앱은 또 다른 경계를 가집니다. 웹앱 Pod를 다시 만들더라도 **외부 DB의 데이터 수명과 백업·복구·접근 권한은 그 DB 운영 영역**에 있습니다. 앱의 PVC나 Kubernetes Deployment가 외부 DB를 대신 백업하지 않습니다. 연결 주소·자격 증명·DNS/TLS는 앞 장의 개념으로 확인하고, 데이터 일관성·백업 시점·복원 시험은 DB에 맞게 설계합니다.

일회용 실습환경에서 읽기 중심으로 확인할 항목은 다음과 같습니다. 아래 명령은 관리 터미널 예시이며 **이번 제작에서 실제 클러스터 실행은 하지 않았습니다.** PV·StorageClass는 namespace 사용자에게 조회 권한이 없을 수 있으므로 관리자와 확인합니다.

```sh
kubectl config current-context
kubectl get pods -n books-lab -o wide
kubectl get pvc -n books-lab
kubectl get pv
kubectl get storageclass
kubectl describe pvc data -n books-lab
```

Pod UID·실행 노드·마운트 참조, PVC의 Bound 여부·PV 이름, PV의 실제 노드/경로·회수 정책을 연결해서 봅니다. `Bound` 하나만 보고 파일 존재·권한·앱의 읽기 성공까지 확정하지 않습니다. 이벤트와 앱 오류도 함께 확인합니다.
