## 1. 규칙을 적는 것과 요청을 받는 것은 다르다

04장의 ClusterIP Service는 내부 접점입니다. 인터넷의 브라우저가 그 주소에 바로 들어온다고 가정하지 않습니다. 외부 주소에서 클러스터까지 연결할 경로와 요청을 처리할 프로그램이 필요합니다.

**Ingress 리소스**는 “이 host와 path의 HTTP 요청을 어느 Service로 보낼까?”라는 규칙을 적은 API 객체입니다. **Ingress controller**는 그 규칙을 읽어 실제 프록시에 반영하고 요청을 전달하는 소프트웨어입니다. 규칙만 만들고 controller를 준비하지 않으면 웹서버가 생기지 않습니다. `ingressClassName`은 어떤 구현이 처리할 규칙인지 연결하는 단서입니다.

k3s의 기본 사례에서는 **Traefik**이 그 역할을 합니다. **ServiceLB**는 LoadBalancer Service를 노드의 포트에서 접근할 수 있게 만드는 k3s 구성 요소입니다. HTTP 경로를 선택하거나 인증서를 검증하는 역할과 구분하세요. 기본 Traefik의 LoadBalancer Service는 80/443을 사용하며 ServiceLB가 그 포트를 노드에서 사용합니다.

아래 그림의 점선 상자는 규칙입니다. 요청 경로의 상자는 실제 연결의 구간 또는 논리적 대상 선택입니다. 규칙 객체를 패킷이 통과하는 서버처럼 읽지 않습니다.

## 2. host·path·인증서 이름은 어떻게 다를까?

`https://study.example.test/health/ready`에서 브라우저는 먼저 이름을 주소로 찾고 HTTPS 연결을 맺습니다. TLS에서 서버 인증서를 검증한 뒤 HTTP 요청의 host와 path를 사용해 분기합니다. TLS의 서버 이름 전달인 **SNI**와 HTTP **Host**는 서로 다른 단계의 정보입니다.

실험은 `study.example.test`에서 `/` Exact와 `/health` Prefix 두 규칙을 사용합니다. **Exact**는 정확히 같은 경로, **Prefix**는 `/`로 나뉜 경로 요소의 접두 관계입니다. `/health/ready`는 `/health` 규칙에 맞지만 `/healthier`는 맞지 않습니다. 두 규칙 모두 이 책의 `study-web:80`으로 연결합니다. 여러 앱을 운영할 때는 규칙별 Service를 달리 지정할 수 있습니다.

경로 매칭은 URI 재작성과 다릅니다. `/health/ready`를 선택했다고 자동으로 `/ready`로 잘라 보내지 않습니다. 실험에서는 Host와 경로를 보존합니다. 실제 프록시의 Host 전달·rewrite 설정을 따로 확인해야 합니다.

## 3. 기존 NGINX를 유지하려면

이미 호스트 NGINX가 여러 앱을 443으로 받고 있다면 기본 구성을 그대로 추가하기 전에 **같은 노드의 주소·포트를 누가 사용하는지** 확인합니다. ServiceLB의 hostPort 처리와 호스트 프로세스의 리스너가 섞이면 단순히 “두 프로그램 중 나중 것이 항상 bind 실패한다”로 설명할 수 없습니다. 포트 점유·예약과 네트워크 규칙 충돌을 함께 점검해야 합니다.

<div className="k8-table" role="region" aria-label="외부 진입 구성 비교" tabIndex={0}>

| 구성 | 외부 443 | controller 접근 | 확인할 것 |
| --- | --- | --- | --- |
| 빈 실습 노드의 기본 k3s | ServiceLB → Traefik | 기본 LoadBalancer Service | 기존 80/443 사용 없음 |
| 기존 NGINX + 기본 설정 추가 | 사용 계획 겹침 | 미정 | 충돌부터 해결, 임의 제거 금지 |
| NGINX 유지 + 별도 NodePort | NGINX | 노드 주소:30080 또는 30443 | 기본 80/443 사용을 피한 controller 노출 설정 |
| 노드나 외부 LB를 분리 | 기존 또는 별도 입구 | 분리한 주소·포트 | 라우팅·방화벽·TLS·비용 |

</div>

실험의 공존 사례는 **controller의 Service를 별도 NodePort로 구성하고 기본 ServiceLB의 80/443 점유를 피한 상태**를 전제로 합니다. NGINX가 노드의 도달 가능한 주소로 전달합니다. 30080/30443은 학습 예시이지 자동 생성되는 값이 아닙니다. NodePort는 노드 인터페이스에 노출될 수 있으므로 호스트 NGINX가 사용한다고 loopback 전용이라고 단정하지 않습니다. 허용 출발지·방화벽·실제 노출 주소를 확인하세요.

기존 호스트 프록시를 제거할 필요는 없습니다. 앱 하나의 도메인만 새 경로로 보내면서 기존 서비스를 유지할 수 있습니다. k3s의 자동 생성 `traefik.yaml`을 직접 고치면 재시작 시 덮어쓸 수 있으므로, 지원하는 HelmChartConfig 등 관리 경로를 사용합니다. 여기서는 기존 서버 변경 명령을 실행하거나 범용 설치 설정을 제공하지 않습니다.

## 4. 자물쇠 하나가 전체 경로를 보호하지 않는다

기본 사례는 브라우저의 TLS가 controller에서 끝나고 앱까지는 HTTP입니다. 공존 HTTP 사례는 NGINX에서 끝납니다. 공존 HTTPS 사례는 **브라우저→NGINX**와 **NGINX→controller** 두 TLS 연결입니다. 후자의 클라이언트는 NGINX이므로 NGINX가 신뢰하는 CA, 검증할 이름, SNI, 상대 인증서 체인·유효기간을 확인합니다.

실험에서 ‘NGINX 유지 → HTTPS NodePort’를 고른 뒤 내부 검증만 실패로 바꿔 보세요. 브라우저의 검증은 성공해도 controller에 HTTP 요청을 전달하지 못합니다. 브라우저의 CA 저장소를 바꿔서 해결할 문제가 아닙니다. 반대로 내부가 정상이어도 외부 인증서 오류를 해결하지 못합니다. 실제 NGINX에서 upstream 검증을 활성화하고 이름·CA를 맞추는 설정은 별도이며, HTTPS 주소만 쓴다고 모든 검증이 자동 활성화됐다고 가정하지 않습니다.

TLS Secret의 인증서와 개인 키, 클라이언트의 CA 신뢰 저장소는 역할이 다릅니다. 서버가 인증서를 보내는 것과 클라이언트가 신뢰하는 것은 별개입니다. [인증서 검증 교재](#/network/verify)와 [프록시의 두 연결](#/network/proxy)에서 실패 종류를 더 나눠 볼 수 있습니다. 이 장의 실패 스위치는 실제 암호 검증 엔진이 아닙니다.

## 5. Service는 반드시 패킷이 들르는 별도 서버일까?

아닙니다. Ingress의 backend는 Service 이름과 포트로 정의되지만 controller 구현에 따라 EndpointSlice의 Pod 주소로 직접 연결하거나 Service 가상 IP를 사용할 수 있습니다. 그림의 Service 상자는 **backend와 ready 대상의 논리적 관계**입니다. 실제 Traefik 설정에서 native load balancing 등 사용 여부를 확인해야 합니다. Service와 controller를 각각 별도 앱 프록시 Pod로 세지 않습니다.

## 6. 실제 환경에서 볼 증거

관리 터미널에서 다음 정보를 읽습니다. 실제 클러스터에는 실행하지 않은 관측 예시입니다.

```sh
kubectl config current-context
kubectl get ingressclass
kubectl get ingress -n books-lab -o yaml
kubectl get service -n kube-system
kubectl get pods -n kube-system -o wide
kubectl get endpointslice -n books-lab -l kubernetes.io/service-name=study-web
```

노드의 리스너는 해당 Linux 노드에서 `ss -ltnp`로 확인할 수 있습니다. 다만 이것만으로 ServiceLB·NodePort의 패킷 처리 규칙 전체를 볼 수는 없습니다. controller Service의 type·ports·nodePort, ServiceLB Pod의 배치·이벤트도 함께 봅니다. 브라우저 오류, NGINX 로그, controller 로그, 앱 로그는 **관측하는 연결이 서로 다릅니다**. 502나 404 하나만으로 원인을 확정하지 않습니다.

**Ingress API의 안정성과 controller 지원 상태도 별개**입니다. Kubernetes v1.35의 Ingress API는 안정 API이며 제거 예정이라는 뜻은 아니지만 기능 개발은 동결돼 있습니다. Kubernetes는 후속 설계에 Gateway API를 권고합니다. Gateway API는 GatewayClass·Gateway·HTTPRoute 등으로 인프라와 라우팅 책임을 더 분리하며 지원 controller가 필요합니다. 특정 ingress controller 프로젝트의 유지보수 종료를 Ingress API 전체의 종료로 해석하지 마세요. 이 책은 기존 환경 이해와 k3s 사례를 위해 Ingress를 다루며 Gateway 설치까지 확장하지 않습니다.
