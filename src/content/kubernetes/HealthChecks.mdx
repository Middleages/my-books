## 1. 가게 문이 열렸다고 주문을 받을 수 있을까?

불이 켜진 가게라도 재료 준비가 끝나지 않았으면 주문을 받기 어렵습니다. 반대로 주문을 잠시 멈췄다고 건물을 새로 지을 필요는 없습니다. 앱에서도 **실행 중**, **시작 완료**, **요청 처리 준비**를 구분해야 합니다. 가게 비유는 역할을 나누기 위한 것이고 실제 판정은 앱이 제공한 응답을 검사합니다.

<strong>probe(상태 검사)</strong>는 kubelet이 컨테이너에 수행하는 점검입니다. HTTP 응답, 명령 실행 결과 등 정해진 방법으로 검사합니다. 여기서는 가상 앱 `study-web`의 HTTP 검사를 생각합니다. Ingress를 통해 외부 사용자가 접속하는 경로 전체를 검사하는 것은 아닙니다.

- **startup:** 시작을 마쳤는가? 설정했다면 성공 전에는 liveness와 readiness 검사를 실행하지 않습니다. 성공 뒤에는 해당 컨테이너의 시작 검사가 끝납니다.
- **liveness:** 앱 자체가 멈춰 재시작이 필요한가? 설정한 연속 실패 임계값에 도달하면 kubelet이 해당 컨테이너를 종료하고 restartPolicy에 따라 다시 시작합니다.
- **readiness:** 지금 요청을 받을 준비가 됐는가? 준비되지 않았다고 판정하면 일반 Service의 새 요청 전달 후보에서 제외합니다. **이 실패 자체는 재시작 명령이 아닙니다.**

03장에서 본 것처럼 같은 Pod의 컨테이너 재시작과 새 Pod 생성은 다릅니다. 아래 실험에서는 `pod-a`는 유지되고 컨테이너 번호와 재시작 횟수가 바뀝니다. 04장의 ready 대상도 이 준비 결과와 연결됩니다.

## 2. 먼저 예측하고 실패 종류를 바꾸기

기본 ‘준비 실패 → 회복’을 끝까지 진행하세요. Ready가 된 뒤 첫 실패가 나도 바로 제외되는지, 두 번째 실패에서 무엇이 바뀌는지 봅니다. 마지막에는 **같은 컨테이너가 재시작 없이** 요청 대상에 돌아옵니다.

그다음 ‘앱 멈춤 → 생존 실패’로 바꿉니다. 이번에는 요청 대상 변화에 더해 컨테이너 재시작이 생깁니다. ‘시작 검사 계속 실패’에서는 나머지 검사 두 개가 대기하는 동안 startup의 실패 횟수만 쌓입니다.

## 3. 한 번 실패와 실패 판정은 다르다

`failureThreshold`는 몇 번 **연속 실패**해야 실패로 판정할지 정합니다. 중간에 성공하면 해당 검사의 연속 실패 횟수는 0으로 돌아갑니다. readiness는 실패 판정 뒤에도 검사를 계속하며, 다시 성공하면 준비 상태를 회복할 수 있습니다.

그림의 빈 칸과 ×는 실패를 세는 도구이지 시간 눈금이 아닙니다. `periodSeconds`는 검사 주기, `timeoutSeconds`는 한 번의 응답을 기다리는 제한, `initialDelaySeconds`는 검사 시작 전 지연입니다. `successThreshold`는 실패 이후 성공으로 인정할 연속 성공 횟수이며 이 모델은 1로 고정했습니다. startup과 liveness는 successThreshold가 1이어야 합니다.

아래는 앱 컨테이너 명세에 들어갈 **설명용 조각**입니다. 전체 Deployment가 아니며 실행하지 않았습니다. 포트는 앞 장의 컨테이너 8080 계약을 유지합니다. startup이 `/health/live`를 쓰는 예는 이 응답이 초기화 완료 뒤에 성공하도록 앱을 설계했다는 조건입니다.

```yaml
startupProbe:
  httpGet: { path: /health/live, port: 8080 }
  periodSeconds: 5
  timeoutSeconds: 1
  failureThreshold: 12
livenessProbe:
  httpGet: { path: /health/live, port: 8080 }
  periodSeconds: 10
  timeoutSeconds: 1
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /health/ready, port: 8080 }
  periodSeconds: 5
  timeoutSeconds: 1
  failureThreshold: 2
  successThreshold: 1
```

위 값은 용도를 구분하는 가상 예이며 실험의 공통 임계값과 다릅니다. 실제 설정은 앱의 시작 시간·응답 지연·일시적인 부하를 관측해 정합니다. 화면의 1.6초 재생 간격을 실제 probe 주기로 해석하지 않습니다. 실패 판정 뒤 종료 유예와 재시작 지연도 있어 단순 곱셈으로 정확한 재시작 시각을 예언할 수 없습니다.

## 4. DB가 멈췄는데 앱을 계속 재시작하면?

앱 프로세스는 정상인데 외부 DB가 응답하지 않는다고 생각해 봅시다. 이 앱은 DB 없이는 해당 업무를 처리하지 못한다는 조건입니다. 준비 검사에서 DB 상태를 반영하면 요청 전달을 잠시 막을 수 있지만, 생존 검사까지 DB에 묶으면 멀쩡한 앱도 재시작하게 됩니다.

실험에서 ‘외부 DB 장애 지속’을 고르고 liveness 포함 여부만 바꿔 보세요. 두 경우 모두 요청을 처리할 준비는 안 되지만, DB까지 생존 조건에 넣은 쪽만 재시작 횟수가 늘어납니다. **앱 재시작은 외부 DB의 복구 작업이 아닙니다.** 많은 앱이 동시에 다시 시작하면 연결 재시도와 초기화 부하가 더해질 수도 있습니다.

그렇다고 모든 앱의 readiness에 무조건 DB 검사를 넣는 것이 정답도 아닙니다. 캐시로 처리할 수 있는 요청이 있는지, 필수 의존성인지, 일부 기능만 저하되는지에 따라 판정을 설계해야 합니다. 여기서는 DB가 필수라는 조건을 고정해 비교합니다.

## 5. 실제 장애에서 세 가지 증거를 같이 보기

관리 터미널에서 먼저 context와 namespace를 확인한 뒤 관측합니다. 아래 `POD_NAME`은 실제 Pod 이름으로 바꿔야 하며 여기서 실행하지 않았습니다.

```sh
kubectl config current-context
kubectl get pods -n books-lab
kubectl describe pod POD_NAME -n books-lab
kubectl logs POD_NAME -n books-lab --previous
kubectl get endpointslices -n books-lab -l kubernetes.io/service-name=study-web
```

Pod의 Ready, 컨테이너 재시작 횟수, probe 이벤트를 함께 보세요. `--previous`는 이전 컨테이너 인스턴스 로그가 남아 있을 때 유용합니다. 재시작 원인은 probe 외에도 프로세스 종료·OOM 등이 있으므로 횟수만 보고 liveness를 원인으로 확정하지 않습니다.

EndpointSlice에서 주소 기록이 존재하는 것과 ready 전달 후보에 포함되는 것은 다릅니다. 이 장은 일반 ClusterIP와 정상 상태 전파를 가정합니다. 준비 실패가 기존 연결을 모두 즉시 끊거나, 다른 준비된 Pod가 없는데도 요청을 성공시키는 것은 아닙니다.
