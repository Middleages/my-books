## 1. 사용할 환경과 하지 않은 검증

기준 후보는 Ubuntu 24.04 LTS amd64의 단일 VM, k3s `v1.35.9+k3s1`(Kubernetes v1.35.9), 기본 SQLite·containerd·Flannel·local-path·Traefik 구성입니다. VM은 최소 2 CPU·2GB RAM에 앱과 이미지용 여유를 더합니다. 이 값은 운영 용량 보장이 아닙니다. 여기에는 기존 서비스·데이터·NGINX가 없어야 합니다. 개발 PC는 기존 로컬/Compose 환경을 유지해도 됩니다.

**실제 확인 구분:** 제공 환경에서 앱 HTTP 응답·모델 테스트와 Helm 4.3.1 로컬 렌더를 검사했습니다. k3s 설치·컨테이너 이미지 빌드/실행·클러스터 배포·실제 복원은 수행하지 못했습니다. 명령을 따라간 독자는 아래 기대 관측과 자신의 결과를 별도로 기록해야 합니다. WSL·macOS·다른 아키텍처는 이 VM과 같은 검증 환경이 아닙니다.

## 2. 소스를 준비하고 설치 대상을 확인하기

[실습 패키지·전체 README](https://github.com/Middleages/my-books/tree/main/examples/kubernetes)를 받습니다. 앱·manifest·의존 chart 없는 최소 chart가 함께 있습니다. 이하 상대 경로는 저장소 루트에서 시작합니다. 빌드 PC와 VM은 다른 실행 위치일 수 있습니다.

VM에서 `uname -m`, `/etc/os-release`, `ss -ltn`, `timedatectl`, `df -h`를 확인합니다. amd64와 x86_64 표기는 같은 계열입니다. 기존 80/443 리스너가 있다면 이 기본 설치 경로를 사용하지 말고 [공존 부록](#/kubernetes/lab-airgap)을 먼저 읽습니다. VM 방화벽·외부 네트워크에서 필요한 관리 경로와 앱 진입만 허용하고 API 6443을 인터넷 전체에 공개하지 않습니다.

**설치는 VM의 시스템 서비스·방화벽 관련 구성을 바꿉니다.** 본인 소유의 새 일회용 VM에서만 아래 공식 설치 경로를 검토한 뒤 실행합니다. 고정 태그의 k3s 바이너리와 `sha256sum-amd64.txt`를 공식 release에서 받아 검증할 수 있습니다. 온라인 설치 스크립트도 파일로 받아 내용을 읽고 해시를 기록합니다. 폐쇄망은 바이너리·이미지 반입 절차가 별도입니다.

```sh
# 새 일회용 VM에서만. 다운로드 성공과 스크립트 내용을 먼저 확인.
curl -fL https://get.k3s.io -o /tmp/books-k3s-install.sh
sha256sum /tmp/books-k3s-install.sh
# 읽어 본 파일을 실행. 기존 서비스가 있는 서버에서는 실행하지 않음.
sudo env INSTALL_K3S_VERSION='v1.35.9+k3s1' sh /tmp/books-k3s-install.sh
sudo k3s --version
sudo k3s kubectl get nodes -o wide
sudo k3s kubectl get pods -n kube-system
```

기대 관측은 지정 버전, 노드 Ready, 시스템 Pod의 준비 완료입니다. 실패하면 `sudo journalctl -u k3s --no-pager -n 100`과 [12장](#/kubernetes/troubleshooting)의 증거 순서로 확인합니다. 재설치를 첫 조치로 삼지 않습니다.

## 3. context와 namespace를 구분하기

이 기본 경로는 VM 안에서 관리합니다. kubeconfig를 무작정 개인 PC의 기존 파일에 덮어쓰지 않습니다. 아래 함수는 **해당 VM의 k3s kubeconfig만** 사용하도록 경계를 고정합니다. 기본 인증은 관리자이므로 공유 계정을 만들거나 kubeconfig를 웹에 올리지 않습니다. namespace는 권한을 줄이는 장치가 아니며 한 namespace 사용자는 관리자에게 배포·관측에 필요한 권한만 받아야 합니다.

```sh
# VM 관리 터미널. 이하 이 셸의 k 함수로 같은 대상 사용.
k() { sudo k3s kubectl --kubeconfig /etc/rancher/k3s/k3s.yaml "$@"; }
k config current-context
k config view --minify
k auth can-i create deployments -n books-lab
k get namespace books-lab
```

마지막은 최초 실습이면 NotFound가 기대됩니다. 기존 namespace가 있으면 소유자와 자원을 확인하고 멈춥니다. 아래 패키지는 `books-lab`을 전용으로 사용하며, 다른 앱이 있으면 그대로 적용·삭제하지 않습니다. `config view --raw`로 인증정보를 출력할 필요가 없습니다.

## 4. 배포 전에 진짜 이미지를 만들기

공개 registry에 `study-web:v1`이 있다고 가정하지 않습니다. [앱 소스와 Dockerfile](https://github.com/Middleages/my-books/tree/main/examples/kubernetes/app)로 **빌드 PC에서** v1·v2를 만듭니다. Python 표준 라이브러리만 사용하며 컨테이너는 8080에서 listen합니다. v1/v2는 빌드 인자로 이미지 안에 넣은 표시입니다. 가변 태그만으로 재현성을 주장하지 말고 기반 이미지 digest·앱 image ID·tar 해시도 기록합니다.

```sh
# Docker가 있는 빌드 PC. base image를 먼저 가져올 수 있어야 함.
docker build --platform linux/amd64 --build-arg APP_VERSION=v1 -t study-web:v1 examples/kubernetes/app
docker build --platform linux/amd64 --build-arg APP_VERSION=v2 -t study-web:v2 examples/kubernetes/app
docker image inspect study-web:v1 study-web:v2 --format '{{.Id}}'
docker save -o study-web-images.tar study-web:v1 study-web:v2
sha256sum study-web-images.tar
# tar를 일회용 VM으로 복사한 뒤 VM에서:
sudo k3s ctr images import study-web-images.tar
sudo k3s crictl images
```

manifest의 `imagePullPolicy: Never`는 이 사전 반입을 전제로 합니다. tar가 없으면 외부에서 가짜 주소를 pull하지 않고 실행이 실패합니다. 두 태그가 runtime 이미지 목록에 있는지 먼저 봅니다. 여러 노드로 확장하면 각 실행 노드에 같은 이미지가 있어야 합니다. registry를 쓰는 전환은 [폐쇄망 부록](#/kubernetes/lab-airgap)의 별도 경로입니다.

## 5. v1 → Service → 외부 입구를 각각 확인하기

```sh
# VM: 저장소 파일을 준비하고 대상 namespace가 비어 있음을 확인한 뒤
k apply -f examples/kubernetes/manifests/namespace.yaml
k apply -f examples/kubernetes/manifests/app.yaml
k rollout status deployment/study-web -n books-lab --timeout=120s
k get pods,service,endpointslices -n books-lab -o wide
# 별도 VM 터미널: 3절의 k 함수를 이 새 셸에도 정의한 뒤 실행.
# 외부 노출 없이 localhost만 사용.
k port-forward -n books-lab service/study-web 18080:80 --address 127.0.0.1
# 또 다른 VM 터미널:
curl -f http://127.0.0.1:18080/
curl -f http://127.0.0.1:18080/health/ready
```

v1과 `hello books-lab`, readiness 200을 기대합니다. port-forward는 API 터널이며 Service의 실제 데이터 전달 경로를 끝까지 검증한 것이 아닙니다. 다음 README의 **Pod 안 Service DNS 요청**으로 DNS·Service 경로도 별도로 확인합니다.

외부 요청은 기본 Traefik·ServiceLB가 80/443을 맡고 해당 VM의 네트워크에 접근할 수 있는 조건에서만 시험합니다. 아래 HTTP는 가상 앱의 비밀 없는 응답을 보는 선택 실습이며 TLS 통과 증거가 아닙니다.

```sh
k apply -f examples/kubernetes/manifests/ingress.yaml
k get ingress,service -n books-lab
# 호출 PC: VM_IP 변수는 실제로 관측한 VM IP로 설정한 뒤 사용
curl -f --resolve "study.example.test:80:${VM_IP}" http://study.example.test/
```

`study.example.test`는 가상 이름입니다. `--resolve`는 이 요청의 이름→IP만 지정하므로 사내 DNS 설정 완료를 뜻하지 않습니다. HTTPS도 시험하려면 README의 **일회용 인증서·TLS Secret·curl --cacert** 절차를 사용합니다. 그 시험도 공인 인증서나 모든 브라우저 trust store의 성공을 의미하지 않습니다.

## 6. 업데이트와 명시적 되돌리기

```sh
# 앞의 k 함수가 있는 VM 터미널
k set image deployment/study-web web=study-web:v2 -n books-lab
k rollout status deployment/study-web -n books-lab --timeout=120s
k rollout history deployment/study-web -n books-lab
# 같은 요청을 반복해 v2를 직접 관측한 뒤, 다음 명령을 명시적으로 실행
k rollout undo deployment/study-web -n books-lab
k rollout status deployment/study-web -n books-lab --timeout=120s
```

초기 v1 → 새 v2 → 다시 v1 응답을 **같은 URL에서** 확인합니다. port-forward는 Pod 교체 때 끊길 수 있어 다시 실행합니다. rollout 완료와 앱 내용 확인은 다른 증거입니다. rollback은 Pod template을 바꾸며 별도 ConfigMap·PV·외부 DB 내용을 같은 시점으로 되감지 않습니다. 자동 무중단·자동 rollback을 보장하지 않습니다.

Helm을 시험하고 싶으면 **manifest 실습을 정리한 후** README의 별도 경로를 사용합니다. 같은 이름을 양쪽 도구가 동시에 관리하게 만들지 않습니다. chart 0.1.0은 앱 이미지 태그나 release revision과 다른 번호입니다.

## 7. 실습 자원 정리

전용 일회용 VM과 이 실습에서 만든 namespace임을 재확인합니다. namespace 삭제는 그 안의 다른 자원도 없애므로 기존 내용이 있었다면 실행하지 않습니다. 이 앱은 PVC를 만들지 않으며 이미지 tar와 로컬 빌드 이미지는 namespace 삭제로 지워지지 않습니다.

```sh
k config current-context
k get all,configmaps,secrets,ingress,pvc -n books-lab
# books-lab 전체가 이번 실습 소유일 때만
k delete namespace books-lab --wait=true
k get namespace books-lab
```

NotFound까지 확인하고 port-forward를 Ctrl+C로 종료합니다. namespace 삭제를 클러스터 백업이나 k3s 제거로 해석하지 않습니다. VM 전체 폐기는 해당 VM에 별도 보관할 파일이 없는지 확인한 후 VM 관리 도구에서 처리합니다. 이 페이지는 시스템 제거 스크립트를 자동 실행하지 않습니다.
