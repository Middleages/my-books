## 1. ‘안 된다’를 관측 가능한 질문으로 바꾸기

먼저 **누가, 어디에서, 어떤 이름과 포트로, 언제 요청했고, 무엇을 봤는지** 적습니다. 브라우저에서 인증서 검증이 실패한 것과 Pod 안에서 DB 연결이 끊긴 것은 다른 구간입니다. 같은 “접속 실패”라도 조사할 위치가 달라집니다.

02장의 제어 경로와 앱 요청 경로를 기억하세요. API에 Deployment가 있다는 것은 명세가 저장됐다는 증거입니다. Pod 실행·Ready·Service 대상·Ingress 규칙·TLS와 실제 업무 성공은 각각 다른 질문입니다. 하나의 초록 표시로 모두 정상이라고 판단하지 않습니다.

**먼저 대상 확인:** 관리 터미널에서 `kubectl config current-context`를 확인하고 각 명령에 `-n books-lab`처럼 의도한 namespace를 지정합니다. 조회의 Forbidden은 권한 문제를 뜻할 수 있고, 목록이 비어 있어도 다른 context나 namespace를 조회했을 수 있습니다. 접근할 수 없는 계층은 관리 담당자에게 관측을 요청하며 임의로 클러스터 관리자 권한을 요구하지 않습니다.

## 2. 같은 상태에도 원인은 여러 개다

<div className="k8-table" role="region" aria-label="증상과 다음 증거 비교" tabIndex={0}>

| 시작 증상 | 아직 모르는 것 | 다음에 대조할 증거 |
| --- | --- | --- |
| Pending | 배정 전인지, 이미지·볼륨 준비 중인지 | nodeName, Pod conditions, describe/events, requests·제약 |
| ImagePullBackOff | 참조·권한·DNS·CA·registry 중 무엇인지 | pull 실패 이벤트 원문과 노드의 이미지 접근 조건 |
| CrashLoopBackOff | 앱 종료·설정·OOM·probe 중 무엇인지 | lastState/exitCode/reason, 이전 로그, probe 이벤트 |
| ready 대상 없음 | selector 불일치인지 준비 실패인지 | Pod label, EndpointSlice 주소·conditions.ready, probe |
| Service 연결 실패 | 이름·대상·포트·실제 네트워크 중 무엇인지 | DNS, selector, ready, targetPort, 앱 listen, 같은 호출 위치 |
| 외부 URL 실패 | controller·규칙·TLS·backend 중 어디인지 | 실패 클라이언트, host/path, TLS 종료점, 내부 연결 비교 |

</div>

`Pending`은 Pod phase이지만 `CrashLoopBackOff`와 `ImagePullBackOff`는 보통 kubectl의 STATUS 열 등에 나타나는 컨테이너 대기 이유입니다. STATUS 열의 모든 문자열이 같은 종류의 API 필드는 아닙니다. “CrashLoopBackOff니까 메모리를 올린다”처럼 상태를 처방에 바로 연결하지 마세요.

## 3. 증거 카드로 다음 관측 선택하기

기본 사례 A에서 전체 상태만 조회해 보세요. 끝까지 가도 원인을 확정할 수 없습니다. 다음 관측을 `describe + events`로 바꾸면 자원 요청과 배정 실패의 관계가 드러납니다. 사례 D·E·F에서는 같은 Service 관측으로도 서로 다른 경계가 나옵니다.

먼저 조사할 지점을 예측하고 한 단계씩 진행하세요. 굵은 경계는 이번 증거가 가리킨 곳이며 나머지 점선 경계를 정상으로 인증한 것은 아닙니다. **실패를 맞히는 퀴즈보다, 증거가 어디까지 말해 주는지 구분하는 실험**입니다.

## 4. 명령을 외우기 전에 질문을 고르기

아래 명령은 모두 읽기 중심의 설명용 예이며 이번 작업에서 실제 클러스터에 실행하지 않았습니다. `POD_NAME`은 실제 이름, `web`은 실제 컨테이너 이름으로 바꿉니다. 로그에는 민감정보가 포함될 수 있으므로 필요한 부분만 확인하고 공유할 때 내용을 점검합니다.

```sh
# 관리 터미널: 전체 상태와 사건
kubectl config current-context
kubectl get deployment,replicaset,pods -n books-lab -o wide
kubectl describe pod POD_NAME -n books-lab
kubectl get events -n books-lab --sort-by=.metadata.creationTimestamp

# 관리 터미널: 현재와 이전 실행은 다름
kubectl logs POD_NAME -c web -n books-lab --tail=50
kubectl logs POD_NAME -c web -n books-lab --previous

# 관리 터미널: 교체 진행과 과거 template
kubectl rollout status deployment/study-web -n books-lab --timeout=10s
kubectl rollout history deployment/study-web -n books-lab
```

`get`은 어떤 객체를 볼지 정하고, `describe`는 조건·종료 이유·관련 이벤트를 모아 보게 합니다. 이벤트는 영구 감사 기록이 아니며 보존 시간과 반복 집계가 있어, 안 보인다고 사건이 없었다고 단정할 수 없습니다. `logs`는 현재 컨테이너, `--previous`는 남아 있는 이전 인스턴스 로그를 읽습니다. 오래된 Pod가 삭제되거나 수집이 안 됐다면 별도 로그 저장소가 필요할 수 있습니다.

`rollout status`가 timeout이 되면 정해진 시간 안에 완료를 관측하지 못했다는 뜻입니다. 원인을 고치거나 rollback한 명령이 아닙니다. 반대로 완료돼도 외부 인증서나 업무 데이터까지 정상임을 보장하지 않습니다. Helm으로 관리한 앱이라면 `helm history`와 렌더/적용 명세도 함께 대조해, 직접 수정한 값과 다음 upgrade가 덮어쓸 값이 충돌하지 않는지 봅니다.

## 5. 접속 문제는 호출 위치를 보존한다

04장의 순서대로 이름 → 선택 대상 → ready → 포트를 나눕니다. EndpointSlice의 주소 개수와 ready 전달 후보 수는 다릅니다. `containerPort: 8080` 선언만으로 앱이 그 포트에 listen한다고 결론 내리지 않고 앱 설정·로그·실제 연결 관측을 대조합니다.

Pod에서 되는 요청이 사용자 PC에서도 된다는 보장은 없습니다. DNS·라우팅·방화벽·NetworkPolicy·프록시 경계가 다를 수 있습니다. 직접 Pod 포트 연결과 Service 이름 연결을 비교한다면 **동일한 호출 환경에서** 확인해야 합니다. 이 실험은 기본 Service 모델의 selector·ready·targetPort를 재사용하며 CNI·NetworkPolicy 장애까지 모두 재현하지는 않습니다.

05장의 기존 NGINX 공존 구성에서는 브라우저 → NGINX와 NGINX → controller의 TLS를 따로 봅니다. 누가 검증했고, 어느 이름으로 연결했으며, 어떤 CA를 신뢰하는지 적습니다. 관리 PC의 OpenSSL 검증 결과가 브라우저나 NGINX의 trust store까지 대신하지 않습니다. `-servername`은 SNI 전달, `-verify_hostname`은 이름 검증으로 역할도 다릅니다. 검증 오류를 없애려고 인증서 검증을 꺼서 성공으로 만들지 않습니다.

HTTP 상태 코드도 관측 지점을 붙여 읽습니다. 프록시의 502, controller의 404, 앱의 503은 여러 원인이 가능하며 숫자 하나가 원인 이름이 아닙니다. TLS handshake에서 실패했다면 HTTP 응답 자체가 없을 수 있습니다.

## 6. 관측 → 최소 변경 → 같은 조건으로 재확인

사례 D의 DB timeout은 readiness가 실패한 이유를 좁히지만 DB 서버 종료와 DNS·방화벽·TLS 오류를 모두 구분해 주지는 않습니다. 다음 조사에서 하나씩 가설을 확인합니다. Pod 재시작은 DB 복구가 아니며, readiness 실패만으로 재시작시키지 않는 09장의 원칙을 유지합니다.

수정 후에는 같은 요청 위치·이름·경로로 다시 관측합니다. 바뀐 명세만 확인하지 말고 실제 실행·Ready·대상 목록·업무 응답까지 확인하세요. 원인, 바꾼 필드, 기대한 결과, 실제 결과를 남기면 다음 장애 때도 사용할 수 있습니다. 파괴적인 삭제·재설치보다 읽기 증거를 먼저 확보합니다.

## 7. 기존 앱 하나씩 전환하는 계획

전체 서버를 한 번에 바꿀 필요는 없습니다. 기존 호스트 NGINX와 외부 DB를 유지하며, 작고 되돌리기 쉬운 앱 하나로 시작합니다.

1. **현재 계약 적기:** 도메인·443 리스너·컨테이너 포트·설정·외부 DB·저장 경로·백업 책임·업무 확인 방법을 기록합니다.
2. **격리된 새 배포 확인:** 별도 실습 namespace와 시험용 경로로 이미지·설정·requests·probe·Service를 관측합니다. 실제 공유 DB에 시험 데이터 변경을 일으키지 않도록 환경을 분리합니다.
3. **진입 경로 공존:** 기존 NGINX의 80/443을 보존하는 포트 계획을 세웁니다. k3s 기본 ServiceLB 점유와 충돌하지 않는 구성은 05장 조건을 확인합니다. 시험 도메인·Host·SNI·인증서도 함께 맞춥니다.
4. **전환과 되돌리기 조건 정하기:** 변경할 라우팅과 책임자를 정하고 오류·지연·업무 확인 기준을 기록합니다. 이전 앱을 다시 연결해도 현재 DB 구조와 호환되는지 먼저 확인합니다.
5. **전환 후 같은 요청 검증:** 실행·Ready·Service·외부 TLS·업무 응답을 확인합니다. 문제가 생기면 확보한 증거와 사전 기준으로 되돌리며, 데이터 변경은 별도 복구 계획을 따릅니다.

이는 전환 계획의 뼈대입니다. 실제 서버 설치·삭제·DB 변경은 이번 교재 사이트 작업에 포함되지 않습니다. 설치·복구·폐쇄망의 완전한 실행 묶음은 다음 배치 G의 선택 부록으로 남깁니다.
