## 1. 실행 가능한 자리와 지금 쓰는 양

식당에 빈 의자가 보여도 예약이 꽉 찼다면 새 예약을 받기 어려울 수 있습니다. Kubernetes의 **requests**도 배치에 필요한 몫을 명세로 표현한다는 점에서 비슷합니다. 다만 물리적인 의자를 떼어 두는 장치는 아닙니다. 실제 CPU 사용은 나눠 쓰고 여유 자원을 더 사용할 수도 있습니다.

이 장에서는 노드 한 대에 일반 컨테이너 하나를 가진 Pod를 새로 배치합니다. 그림은 네 숫자를 나눠 보여 줍니다.

- **allocatable:** 시스템용 예약 등을 제외하고 노드가 Pod에 제공할 수 있다고 보고한 자원량. 장비의 전체 사양(capacity)과 다를 수 있습니다.
- **request:** 이 컨테이너를 배치할 때 고려할 CPU·메모리 요구량. scheduler는 이미 배치된 requests와 새 requests가 노드에 들어가는지 확인합니다.
- **limit:** 실행 중 자원 사용을 제한하는 경계. CPU와 메모리의 제한 방식은 다릅니다.
- **실사용량:** 그때 실제로 사용한 양을 관측한 값. `kubectl top` 같은 도구로 보는 숫자이며 request와 일치할 필요가 없습니다.

CPU `1000m`는 1 CPU, `500m`는 0.5 CPU입니다. 여기서 m은 milli 단위입니다. 메모리는 Mi 단위를 사용하며 1Mi는 2의 20제곱 바이트입니다. CPU의 m과 메모리의 Mi를 섞어 읽지 않습니다.

**먼저 기본 설정으로 끝까지 진행하세요.** CPU 사용량은 100m뿐인데 requests는 1800m입니다. 새 request 500m가 들어가는지 계산한 뒤 기존 requests를 1500m로 낮춰 다시 관찰합니다. 슬라이더 변경은 별개 실험 조건을 고르는 것이며 운영 중인 Pod를 즉시 수정하는 명령이 아닙니다.

## 2. 왜 CPU가 쉬는데 Pending일까?

기본 노드의 CPU allocatable은 2000m입니다. 이미 배치된 앱들이 요청한 합은 1800m이고 새 앱은 500m를 요청합니다. 합계 2300m는 배치 가능한 2000m를 넘습니다. 지금 기존 앱이 100m만 쓴다는 관측은 **배치 명세의 합계를 대신하지 않습니다.**

기존 requests를 1500m로 바꾸면 합계가 정확히 2000m가 되어 CPU 조건에 맞습니다. 메모리도 맞아야 합니다. 기존 메모리 requests를 1900Mi로 바꾸면 새 앱 256Mi를 더한 2156Mi가 allocatable 2048Mi를 넘어 다시 Pending이 됩니다. 한 자원에 여유가 있다고 다른 자원 부족이 상쇄되지 않습니다.

실제 scheduler는 노드의 Ready 상태·taint·affinity·스토리지·다른 제약도 확인합니다. 따라서 **모든 Pending의 원인이 CPU 부족은 아닙니다.** 이번 모델은 다른 조건이 정상인 상태에서 CPU·메모리 requests 적합성만 보여 줍니다. 낮추기 전에 관측 기간·부하 피크·시작 시 자원·안정성을 확인해야 하며, 무조건 request를 작게 만드는 것이 해결책은 아닙니다.

## 3. namespace quota는 노드의 빈 공간과 다른 경계다

**ResourceQuota**는 한 namespace가 사용할 수 있는 자원 총량이나 객체 수를 제한하는 정책입니다. 이 실험은 `books-lab`의 `requests.cpu`만 제한합니다. 이미 그 namespace가 사용 중인 몫은 500m이고, 노드 전체의 다른 namespace 몫과 구분합니다.

새 request 500m를 더하면 namespace 합계는 1000m입니다. quota가 750m라면 **Pod 생성 요청 자체가 거절**됩니다. 노드 requests를 500m로 낮춰 충분한 공간을 만들어도 quota 거절은 같습니다. 반면 quota를 통과한 Pod가 노드에 배치되지 못하면 Pending으로 남을 수 있습니다. 그 Pending Pod의 requests도 namespace quota에 포함됩니다.

Deployment를 통해 생성한다면 Deployment 객체는 존재하지만 하위 Pod 생성이 거절되는 형태로 보일 수도 있습니다. 그래서 “배포 객체가 있으니 Pod도 생성됐다”고 추정하지 말고 ReplicaSet 이벤트와 실제 Pod 목록을 확인합니다. 이 실험의 quota 심사는 **새 Pod 생성 요청**을 관찰한 것입니다.

## 4. CPU limit은 기다림으로 나타날 수 있다

기존 CPU requests를 500m로 바꿔 배치가 되게 한 뒤 ‘CPU 수요 증가’를 선택하세요. 새 앱은 1500m만큼 실행 기회를 원하지만 CPU limit은 1000m입니다. 충분한 노드 여유를 가정한 그림에서 사용은 1000m로 제한되고 나머지는 기다립니다. 이런 제한을 <strong>throttling(실행 기회 제한)</strong>이라고 합니다.

CPU limit을 넘겨 쓰려 했다는 이유만으로 메모리 OOM처럼 컨테이너가 종료되는 것은 아닙니다. 대신 요청 처리가 느려지거나 지연 시간이 늘 수 있습니다. 실제 CPU 시간은 일정 구간에 걸쳐 제한되며, 그림의 막대는 단순화한 관측 값입니다. 어느 순간에도 정확히 1000m로 고정된다는 법칙이 아닙니다.

request를 100m로 낮춰도 이 실험의 CPU limit은 1000m 그대로입니다. **request가 낮다는 것과 그 이상 쓸 수 없다는 것은 다릅니다.** 실제 경쟁 상황에서 CPU request는 배치뿐 아니라 CPU 시간 배분의 가중치에도 관계합니다. 이 장은 그 경쟁 전체를 재현하지 않습니다.

## 5. 메모리는 기다리게만 할 수 없다

프로세스가 파일을 읽고 구조를 만들면 메모리가 필요합니다. CPU처럼 잠시 실행을 늦추는 것만으로 이미 잡은 메모리가 자동 반환되지는 않습니다. 메모리 limit은 커널의 메모리 관리와 OOM 처리를 통해 강제될 수 있습니다.

‘메모리 압박 → OOM 사례’를 선택하면 4단계에서 앱은 768Mi를 요구하지만 관측 사용량은 500Mi입니다. **요구량과 실제 할당·사용량을 같은 값으로 그리지 않습니다.** 5단계는 다음 관측에서 OOM 종료가 확인된 사례입니다. 메모리 limit 512Mi를 넘는 요구를 했다는 계산만으로 특정 시점의 즉시 종료를 선언한 것이 아닙니다.

실제 종료 여부·시각은 커널이 감지하는 메모리 압박과 할당 상황에 영향을 받습니다. 종료 직후 사용량이 0으로 떨어져도 Pod가 남아 있다면 배치 requests가 즉시 해제되는 것은 아닙니다. 이 차이가 그림의 파란 예약 막대와 초록 사용 막대에 나타납니다. 이후 컨테이너 재시작은 restartPolicy 등 조건에 따라 진행하며, 반복 실패의 시간선은 이 실험 밖입니다.

OOM과 노드 메모리 압박에 의한 <strong>Pod 퇴거(eviction)</strong>도 같은 사건이 아닙니다. `OOMKilled`, 종료 코드, 이벤트, 이전 컨테이너 로그를 함께 대조하고 상태 문자열 하나로 메모리 누수의 원인까지 확정하지 않습니다.

아래는 관리 터미널의 읽기 예시입니다. `node-a`는 가상 이름이므로 실제 노드 이름을 확인해야 합니다. Node 조회는 관리자 권한이 필요할 수 있고 `top`은 metrics API가 있어야 동작합니다. **실제 클러스터에서는 이번에 실행하지 않았습니다.**

```sh
kubectl config current-context
kubectl get pods -n books-lab -o wide
kubectl describe node node-a
kubectl get resourcequota -n books-lab
kubectl get events -n books-lab --sort-by=.metadata.creationTimestamp
kubectl top pods -n books-lab
```

`top`의 낮은 사용량만 보고 “scheduler 오류”라고 결론 내리지 않습니다. requests 부족이면 명세·노드 규모·다른 제약을, quota 거절이면 namespace 정책과 사용 현황을, 실행 중 한도 문제면 실제 부하와 limits를 각각 확인합니다.
