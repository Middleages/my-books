## 1. 실행 재료와 실행 중인 앱은 다르다

이미지는 프로그램과 필요한 파일을 묶은 실행 재료입니다. 컨테이너는 그 재료를 사용해 만든 실행 인스턴스입니다. 같은 이미지로 둘을 실행해도 각각의 프로세스가 움직입니다. 이미지 파일이 있다는 사실만으로 웹앱이 실행 중인 것은 아닙니다.

<ImagePrimer />

여기서 **인스턴스**는 같은 종류를 실제로 만든 개별 하나라는 뜻입니다. 컨테이너 하나를 끝냈다고 이미지가 지워지지는 않습니다. 반대로 이미지를 새로 가져왔다고 실행 중인 컨테이너가 저절로 새 버전으로 바뀌지도 않습니다.

## 2. 운영 일을 누구에게 맡길까?

앱 3개를 실행하는 팀을 생각해 봅시다. 포트·환경변수·볼륨을 명령마다 입력할 수도 있고, 파일에 모아 재현할 수도 있습니다. 어떤 도구를 쓰든 앱의 올바른 설정과 데이터 복구 방법은 사람이 정해야 합니다.

<div className="k8-table" role="region" aria-label="비교 표 · 좁은 화면에서는 좌우로 이동" tabIndex={0}>

| 운영 일 | Docker 직접 실행 | 단일 호스트 Compose | Kubernetes |
| --- | --- | --- | --- |
| 시작 조건 기록 | 실행 명령·스크립트로 관리 | 서비스·네트워크·볼륨을 YAML로 묶음 | API 리소스로 원하는 상태 선언 |
| 앱 프로세스 종료 | 정책을 지정하면 Engine이 재시작 | `restart` 정책을 Engine이 수행 | kubelet·runtime이 Pod의 재시작 정책에 따라 처리 |
| 실행 단위 자체가 사라짐 | 운영자·별도 자동화가 재생성 | 다시 `up` 하거나 별도 자동화 필요 | Deployment 등 controller가 원하는 개수에 맞춰 Pod 생성 |
| 새 이미지 반영 | 새 컨테이너로 교체 | 변경 후 `compose up`으로 필요한 서비스 재생성 | Deployment의 Pod 템플릿 변경을 기반으로 교체 관리 |
| 운영자가 계속 맡는 것 | 이미지·설정·백업·호스트 | 왼쪽 + Compose 파일 관리 | 왼쪽 + 클러스터 버전·권한·네트워크·스토리지 관리 |

</div>


Compose에도 재시작 기능과 운영 기능이 있습니다. 단일 VM에서 앱 몇 개를 안정적으로 운영하는 데 충분할 수 있습니다. `docker compose restart`만으로 바꾼 설정이나 새 이미지를 반영한다고 생각하면 안 됩니다. 다시 만드는 작업과 다시 시작하는 작업을 구분하세요.

Kubernetes는 **원하는 상태와 실제 상태의 차이를 계속 줄이는 구조**가 필요할 때 가치가 있습니다. 대신 YAML만 늘리는 것이 아니라 API 접근 권한, 클러스터 업그레이드, 저장소, 문제 진단까지 배워야 합니다. 자동 교체도 무중단·데이터 복구·업무 성공 전체를 보장하지 않습니다.

## 3. 실험에서 세 가지를 비교하기

1. Compose, 앱 종료, 3개를 선택합니다. 하나가 멈춘 뒤 Engine이 재시작하는지 봅니다. Kubernetes에서도 이 사례는 **같은 Pod 안 컨테이너의 재시작**입니다.
2. Docker 정책 없음으로 바꿉니다. 줄어든 실행 수가 유지됩니다. Docker에도 정책을 추가하면 자동 재시작할 수 있으므로 도구의 절대적인 능력 차이라고 읽지 않습니다.
3. VM 전체 종료로 바꿉니다. 1개에서 3개로 늘려도 모두 같은 VM 안에 있습니다. 이 VM에서 동작하던 복구 담당도 같이 멈춥니다.

<strong>replica(복제본)</strong>는 같은 역할의 실행 단위를 여러 개 유지하는 개수입니다. 같은 VM의 여러 Pod는 앱 하나의 실패나 교체에 도움을 줄 수 있지만, 물리적인 장애 경계를 나누지는 못합니다. 여러 노드를 갖춰도 배치·데이터·제어 영역까지 따져야 높은 가용성을 얻을 수 있습니다.

## 4. 내 운영에 적용하기

“앱이 죽으면 다시 켜기”가 주된 문제라면 현재 Docker 재시작 정책과 로그부터 점검할 수 있습니다. “여러 앱의 원하는 개수·교체 절차·권한을 같은 API로 다루기”가 반복된다면 Kubernetes 도입 이유가 더 분명해집니다. 선택 기준은 유행이 아니라 반복되는 운영 일과 관리 비용입니다.

이미 Docker를 쓰는 **실습 호스트에서** 다음 읽기 전용 명령으로 관찰할 수 있습니다. 아래 이름은 가상 이름이며 실제 존재하는 컨테이너 이름으로만 확인합니다. 이 교재 제작 과정에서는 명령을 실제 Docker 서버에서 실행하지 않았습니다.

```sh
docker ps -a
docker inspect study-web --format '{{.HostConfig.RestartPolicy.Name}}'
```

첫 명령은 실행 여부, 두 번째는 재시작 정책을 확인합니다. 컨테이너가 없다는 오류는 앱 내부 장애를 증명하지 않습니다. 관측한 호스트와 이름부터 확인하세요. 실제 앱 종료나 VM 종료를 실행할 필요는 없습니다.
