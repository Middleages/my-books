## 요청 하나와 연결 하나는 다릅니다

<div className="learning-goals">
이 장을 읽고 나면 앱 요청·연결 풀·DB 세션의 경계를 구별하고, 연결을 기다린 시간과 연결을 가진 동안의 시간을 나눌 수 있습니다. 트랜잭션을 같은 client에 묶고, 풀 상한을 앱 전체에서 합산해야 하는 이유도 설명합니다.
</div>

손님 네 명이 동시에 주문 버튼을 눌렀습니다. 웹앱에는 요청 네 개가 들어오지만, DB와 이미 맺은 연결을 네 개씩 새로 만들어야 하는 것은 아닙니다. **연결 풀(connection pool)**은 사용할 연결을 관리하고 요청이 빌렸다가 돌려주도록 돕습니다.

여기서 요청은 처리할 일, client는 앱 쪽 연결 객체, DB 세션은 그 연결의 서버 쪽 대화 상태입니다. 연결을 빌린 관계를 이 장에서는 **대여**라고 부릅니다. 풀의 최대 크기는 연결을 둘 수 있는 상한이지, 항상 그 수만큼 연결이 열려 있다는 뜻이 아닙니다.

아래는 앱 인스턴스 하나가 PostgreSQL에 직접 연결하는 교육 모델입니다. 요청 색이나 결과 숫자만 보지 말고 **요청 → client → DB 세션의 선이 언제 생기고 사라지는지** 보세요.

## 기다림을 한 덩어리로 보지 않습니다

기본 실험에서 각 SQL 작업은 가상의 2tick을 사용합니다. 상한2이면 R1·R2는 tick2에, R3·R4는 tick4에 완료됩니다. 상한1이면 완료 시점이2·4·6·8입니다. 이는 동시 도착·FIFO·고정 작업 시간이라는 가정의 결과이지 실제 처리량 예측이 아닙니다.

반환 누락에서는 SQL이 끝나도 요청이 client를 계속 쥡니다. 새 요청은 그 연결을 빌릴 수 없습니다. 반대로 정상 반환하면 **요청의 대여 관계만 끝나고, 건강한 연결과 DB 세션은 idle로 남아 재사용**될 수 있습니다. 요청 하나의 종료와 연결 자체의 종료가 다른 이유입니다.

시간도 구간별로 읽습니다.

1. 연결 대기: 사용할 client를 얻기 전입니다.
2. DB 사용: client를 빌린 뒤 SQL을 수행합니다. 앞 장의 잠금 대기는 이 구간 안에 포함될 수 있습니다.
3. 앱 보유: 이 실험에서는 SQL이 끝난 뒤에도 앱이 client를 돌려주지 않은 시간입니다.

잠금 대기를 DB 사용 시간에 이미 포함해 놓고 다시 더하면 중복입니다. 또한 **client를 보유했다는 사실만으로 열린 트랜잭션이나 잠금이 있다고 단정할 수 없습니다.** COMMIT 뒤 연결만 오래 쥔 경우와, 트랜잭션을 열어 둔 채 외부 응답을 기다리는 경우는 다릅니다. 이 실험은 앞의 경우만 보여 줍니다.

연결 획득 실패도 SQL 오류와 다릅니다. 획득하지 못한 client에는 SQL을 보낼 수 없고 반환할 client도 없습니다. 실제 driver의 대기 제한, 네트워크 장애, 풀의 종료 정책은 별도로 확인해야 합니다.

## 트랜잭션의 대화 상대를 바꾸지 않습니다

PostgreSQL 트랜잭션은 같은 세션에서 이어집니다. node-postgres의 `pool.query`는 **독립적인 한 쿼리**를 실행하는 데 편리하지만, 그 메서드를 여러 번 호출한 것만으로 하나의 트랜잭션을 보장하지는 않습니다.

실험의 잘못된 배정 예에서는 BEGIN은 C1에, UPDATE는 C2에 갑니다. C2의 자동 확정은 C1의 ROLLBACK으로 되돌릴 수 없습니다. 항상 이 배정이 일어난다고 예언하는 그림이 아닙니다. 배정을 우연에 맡기지 않고, 한 client를 빌려 BEGIN·업무 변경·COMMIT 또는 ROLLBACK까지 유지해야 한다는 반례입니다.

아래는 **서버 코드의 구조를 설명하는 예시**입니다. 브라우저에서 실행하지 않으며 완성된 주문 처리 함수도 아닙니다. `work(client)` 안에는 앞 장의 조건부 차감, 결과 행 수 확인, 주문·항목 기록을 모두 같은 client로 수행하는 업무 로직이 들어가야 합니다.

<div className="db-server-example">

```js
async function inOneTransaction(pool, work) {
  const client = await pool.connect();
  let discard = false;
  let commitSent = false;
  try {
    await client.query('BEGIN');
    const result = await work(client);
    commitSent = true;
    await client.query('COMMIT');
    return result;
  } catch (error) {
    if (commitSent) {
      discard = true;
      throw new Error(
        'COMMIT 결과를 별도로 확인해야 합니다',
        { cause: error }
      );
    }
    try {
      await client.query('ROLLBACK');
    } catch {
      discard = true;
    }
    throw error;
  } finally {
    client.release(discard);
  }
}
```

</div>

연결 획득은 client를 얻은 뒤의 정리 블록과 분리했습니다. 획득 자체가 실패하면 없는 객체를 반환하지 않습니다. 확보한 연결은 한 번 반환하며, 정리가 실패해 상태를 믿을 수 없으면 재사용 풀로 돌리지 않고 폐기합니다. node-postgres의 `release(true)`는 해당 client를 파괴하는 경로입니다.

COMMIT을 보낸 뒤 응답을 받지 못한 경우에는 **업무가 확정됐는지 모를 수 있습니다.** 위 예는 이 구간의 오류를 보수적으로 구별하고 연결을 폐기합니다. 연결을 닫았다는 사실이 이미 확정된 주문을 취소하지는 않으며, 곧바로 같은 주문을 무조건 재실행해서도 안 됩니다. 요청 키와 결과 확인은 마지막 진단 장에서 이어갑니다.

## 값과 비밀정보의 경계

사용자가 넣은 값을 SQL 문자열에 붙이지 않고 driver의 매개변수로 전달합니다. 예를 들어 수량과 상품 id는 `$1`, `$2`에 대응하는 값 배열로 보냅니다. 이는 SQL 구조와 데이터를 구분하는 장치입니다. 테이블 이름·열 이름까지 같은 값 매개변수로 바꿀 수 있다는 뜻은 아닙니다.

DB 접속 비밀번호나 권한이 큰 계정 정보를 웹 브라우저에 넣지 않습니다. 연결 풀은 서버 쪽 앱의 책임이며, 풀을 쓴다는 이유만으로 입력 검증·접근 권한·최소 권한이 해결되지는 않습니다.

## 연결 수를 늘리기 전에 묻습니다

서버 전체의 `max_connections`와 앱 인스턴스 하나의 풀 상한은 다릅니다. 앱 세 개가 각각 최대4개를 열 수 있다면 가능한 앱 연결 합계는12개입니다. 이 수는 현재 열린 연결을 측정한 값이 아니라 **구성상 가능한 상한**입니다.

그림은 서버 최대12에서 예약 진입 여유4와 다른 연결2를 남겨 일반 앱의 보수적 예산을6으로 잡았습니다. PostgreSQL의 예약 설정은 역할별로 신규 연결을 받을 문턱입니다. 관리자 소유의 연결 객체 네 개가 미리 만들어진다는 뜻이 아닙니다. 실제로 열린 다른 연결도 전체 사용량에 들어갑니다.

상한 안에 들어간다고 성능이 최적인 것은 아닙니다. 큰 풀은 느린 SQL·행 잠금·CPU·메모리·I/O 경합을 없애지 않으며, 동시에 밀어 넣는 작업을 늘릴 수도 있습니다. 앱의 획득 대기, DB 사용 시간, 반환 누락과 서버 자원을 함께 관측해야 합니다.

<div className="note">
이 장의 코드 수명은 node-postgres를 기준으로 합니다. 다른 driver나 프록시가 연결·세션을 재사용하는 방식은 다를 수 있습니다. PostgreSQL의 연결 진입 설정을 MSSQL의 같은 이름 설정처럼 일반화하지 않습니다.
</div>
