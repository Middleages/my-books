## 주문은 두 건인데, 왜 세 줄일까요?

<div className="learning-goals">
이 장을 읽고 나면 조회 결과의 한 행이 무엇을 나타내는지 정하고, JOIN 뒤의 행 수와 주문 수가 다른 이유를 설명할 수 있습니다. 짝이 없는 고객과 NULL, 조건의 위치가 만드는 차이도 구별합니다.
</div>

가람 고객의 확정 주문은 1001과 1002, 두 건입니다. 그런데 주문한 상품까지 붙이면 세 행이 됩니다. 주문 1001에는 머그와 노트가 함께 있기 때문입니다. **조회가 데이터를 잘못 늘린 것이 아니라, 한 행의 단위가 ‘주문’에서 ‘주문 항목’으로 바뀐 것**입니다.

SQL은 원하는 데이터를 설명하는 언어입니다. `SELECT`는 보여 줄 열, `FROM`은 읽을 표, `WHERE`는 남길 행의 조건을 나타냅니다. 예를 들어 다음 문장은 가람의 확정 주문 번호를 읽습니다. 아래 예와 실험의 SQL은 읽기 위한 예시이며 브라우저에서 실제 DB에 보내지 않습니다.

```sql
SELECT id
FROM orders
WHERE customer_id = 1 AND status = 'confirmed'
ORDER BY id;
```

`ORDER BY`는 결과 순서를 명시합니다. 표가 화면에서 늘 같은 순서로 보였다는 경험만으로 다음 조회의 순서까지 보장되지는 않습니다.

## 같은 주문 번호가 두 번 보이는 이유

JOIN은 조건에 맞는 행의 **짝을 만들어 읽는 연산**입니다. 원본 주문 1001은 여전히 한 행이지만, 결과에는 항목 `(1001, 1)`과 짝인 행, `(1001, 2)`와 짝인 행이 각각 생깁니다. 그림에서 하나의 주문 번호에서 갈라지는 선을 따라가 보세요.

항목까지 붙인 고객 1의 결과는 세 행입니다.

| 무엇을 세는가 | 같은 결과에서 얻는 값 | 이유 |
| --- | ---: | --- |
| `COUNT(*)` | 3 | 결과의 모든 행 |
| `COUNT(o.id)` | 3 | 주문 id가 NULL이 아닌 행 |
| `COUNT(DISTINCT o.id)` | 2 | 중복을 제외한 주문 id |
| `SUM(i.qty)` | 7 | 항목별 주문 수량의 합 |
| `SUM(i.qty * i.unit_price_won)` | 36,000원 | 항목 수량 × 주문 당시 단가의 합 |

`COUNT(o.id)`라고 썼다고 주문 번호의 중복이 자동으로 사라지지는 않습니다. 수량 7개도 주문 7건이라는 뜻은 아닙니다. **행·주문·상품 수량·금액의 단위를 먼저 고른 뒤 함수를 고릅니다.**

GROUP BY는 공통 값을 가진 결과행을 한 묶음으로 집계합니다. 이 실험에서는 고객 id가 묶음의 경계입니다. 같은 이름을 가진 고객이 있어도 id가 다르면 별개의 고객입니다. 그림의 묶음과 숫자는 같은 결과행에서 계산합니다.

## 짝이 없다는 사실도 결과가 됩니다

INNER JOIN은 짝이 맞는 행을 남깁니다. LEFT JOIN은 왼쪽 행을 유지하되, 짝이 없는 오른쪽 열을 NULL로 채웁니다. NULL은 숫자 0이나 빈 문자열이 아니라 **그 위치에 값이 없음을 나타내는 표시**입니다.

다온 고객 3을 선택하고 두 방식을 비교하세요. LEFT JOIN의 결과 한 행에는 고객은 있지만 주문과 항목이 없습니다. 그래서 `COUNT(*)`는 1, `COUNT(o.id)`와 중복 없는 주문 수는 0입니다. 원본에 ‘번호가 NULL인 주문’이 새로 저장된 것은 아닙니다.

합칠 수량·금액이 없으면 이 예의 SUM은 NULL입니다. 업무 화면에서 ‘주문 없음’을 0원으로 보여 주려면 `COALESCE(SUM(...), 0)` 같은 표시 규칙을 따로 정할 수 있습니다. 이 변환이 원래 값이 없었다는 사실을 바꾸지는 않습니다.

반면 INNER JOIN 뒤에 남은 행이 없고 고객별 GROUP BY를 하면 **고객 집계행 자체가 없습니다.** ‘고객 행 하나에 합계 0’과 다릅니다. GROUP BY 없이 전체를 집계하는 쿼리의 빈 결과 규칙과도 섞지 마세요.

## 조건은 같은 말이어도 놓인 자리가 중요합니다

위 작은 실험은 고객과 주문 두 표만 비교합니다. 확정 조건을 ON에 넣으면 ‘이 고객의 확정 주문과 짝을 찾는다’는 뜻입니다. 취소 주문만 있는 누리와 주문이 전혀 없는 다온도 LEFT JOIN의 왼쪽 고객으로 남습니다.

조건을 WHERE에 두면 JOIN으로 만든 결과에서 확정 주문인 행만 남깁니다. 누리의 취소 주문 행도, 다온의 주문 NULL 행도 그 조건을 만족하지 않아 사라집니다. **짝을 고르는 조건과 만들어진 결과를 거르는 조건을 같은 것으로 취급할 수 없습니다.**

앞의 큰 실험은 고객을 보존하는 LEFT 설정일 때 주문과 항목 모두 LEFT로 연결합니다. 중간까지 LEFT로 붙인 뒤 마지막 항목을 INNER로 연결하면, 항목 없는 행을 다시 없앨 수 있습니다. 실제 쿼리에서는 한 JOIN의 이름만 보지 말고 전체 연결을 읽으세요.

## 화면 숫자가 의심될 때

1. 결과 한 행의 단위를 적습니다. 고객인가, 주문인가, 주문 항목인가요?
2. 원본의 한 행이 몇 짝으로 이어지는지 작은 id 몇 개로 확인합니다.
3. 짝이 없는 행을 버릴지 남길지, 조건이 ON과 WHERE 중 어디에 있는지 확인합니다.
4. 집계 전에 행을 살피고 NULL·중복·단위를 확인합니다.

금액은 `products`의 현재 가격이 아니라 `order_items`에 보관한 주문 당시 단가로 계산했습니다. 오늘 노트 가격을 바꾸어도 과거 주문의 합계를 다시 매기지 않습니다. 여기서 확정 주문 금액은 결제 완료나 회계상 매출을 증명하는 값은 아닙니다.

그림의 원본→짝→집계 순서는 **쿼리의 뜻을 이해하는 논리적 관찰 순서**입니다. PostgreSQL이 꼭 이 순서로 메모리와 디스크를 처리했다는 실행 기록이 아닙니다. 실제 실행 방법을 확인하는 실행계획은 뒤의 장에서 다룹니다.
