## 찾는 길을 하나 더 만들면 항상 빠를까요?

<div className="learning-goals">
이 장을 읽고 나면 인덱스 항목과 실제 행을 구별하고, 찾는 행의 수·저장 위치·쓰기 변경이 접근할 구조를 어떻게 바꾸는지 설명할 수 있습니다. 교육용 페이지 개수를 실제 실행 시간으로 읽지 않습니다.
</div>

주문 표에서 며칠 사이의 주문을 찾는다고 합시다. 표를 처음부터 읽으며 조건을 비교할 수도 있고, 날짜 순으로 정리한 별도 길을 따라 필요한 행의 위치를 찾을 수도 있습니다. 뒤의 길이 **인덱스**입니다.

이 장에서는 정렬된 키로 범위를 찾을 수 있는 B-tree 인덱스를 사용합니다. 뿌리에서 알맞은 아래쪽 페이지로 내려가고, 마지막 단계의 항목에서 실제 행의 위치를 따라갑니다. 인덱스에 적힌 키와 주문의 전체 행은 같은 물건이 아닙니다.

그림은 가상 주문 64행을 데이터 페이지 8개에 8행씩 배치합니다. 페이지는 여러 행을 함께 담는 저장 단위라는 의미를 보여 주는 상자입니다. **실제 PostgreSQL 페이지에 항상 8행이 들어가거나, 실제 트리 높이가 이 그림과 같다는 뜻은 아닙니다.**

## 반환한 행 수와 들른 페이지 수는 다릅니다

먼저 좁은 조건에서 ‘모인 배치’와 ‘흩어진 배치’를 비교하세요. 주문 id와 날짜, 조건에 맞는 주문은 그대로입니다. 바뀐 것은 **같은 행들이 어느 데이터 페이지에 놓였는가**입니다.

모여 있으면 한 데이터 페이지에서 여러 결과행을 얻습니다. 흩어져 있으면 같은 개수의 행을 위해 여러 페이지를 따라갑니다. 인덱스를 찾는 페이지도 별도로 방문했습니다. 그림에서 강조된 페이지와 비교 막대의 칸 수를 함께 읽어 보세요.

조건을 넓히면 인덱스를 거쳐 많은 데이터 페이지를 읽을 수 있습니다. 모든 행을 읽는 경우에는 표의 여덟 페이지뿐 아니라 인덱스 쪽 페이지도 지나갑니다. 반대로 결과가 0건이어도 ‘없다’를 확인하는 탐색은 필요합니다. 결과행이 없다는 사실이 아무 일도 하지 않았다는 뜻은 아닙니다.

이 실험의 단위는 **서로 다른 접근 페이지 수**입니다. 같은 페이지를 다시 방문한 사건은 이력에 남지만 고유 페이지 개수에는 한 번만 넣습니다. 이것은 다음 값들과 다릅니다.

- 실제 디스크에서 읽은 횟수나 바이트
- PostgreSQL 실행계획의 비용 값
- 밀리초로 측정한 실행 시간

캐시에 이미 있는 페이지, 순차 읽기와 여러 위치 읽기의 차이, 행 버전 확인, bitmap/index-only scan, 병렬 처리와 통계 등은 생략했습니다. 따라서 막대가 작다는 이유만으로 실제 서비스가 반드시 더 빠르다고 판정하지 않습니다. 같은 반환 행을 유지하면서 **왜 접근 경로가 달라지는지**를 보는 실험입니다.

## 인덱스는 읽을 때만 존재하지 않습니다

날짜를 기준으로 찾는 길을 만들었다면 주문을 새로 넣거나 날짜 값을 바꿀 때 그 길도 데이터와 맞아야 합니다. 다음 그림은 쓰기 때문에 함께 유지해야 하는 논리적 구조를 비교합니다.

새 행이 들어갈 때 표만 바뀌고 인덱스가 낡은 채 남는다면 다음 조회에서 새 주문을 놓치게 됩니다. 인덱스 열의 값이 바뀌면 이전 키와 새 키가 가리켜야 하는 관계도 달라집니다. 별도 구조가 늘수록 저장 공간과 유지 작업도 고려해야 합니다.

이 작은 쓰기 그림은 ‘함께 맞추어야 하는 구조’를 나타냅니다. PostgreSQL의 실제 행 버전을 같은 자리에 덮어쓰는 과정이나 디스크 쓰기 횟수를 재현하지 않습니다. 페이지 분할·MVCC·HOT·WAL·VACUUM 같은 내부 과정은 이 장면 밖입니다. 읽기 실험의 페이지 개수와 쓰기 구조 개수를 한 단위처럼 더하지 마세요.

## 키 두 개의 순서가 만드는 범위

`(customer_id, created_at)` 순으로 정리하면 먼저 고객끼리 묶이고 그 안에서 날짜가 이어집니다. 고객 한 명과 날짜 조건을 함께 주면 정렬 띠 안의 한 구간을 좁히기 좋습니다. 고객을 고르지 않고 날짜만 찾으면 여러 고객의 구간에 답이 나뉠 수 있습니다.

그렇다고 ‘첫 열 조건이 없으면 이 인덱스는 절대 사용할 수 없다’고 외우면 안 됩니다. PostgreSQL 18에는 조건과 분포에 따라 여러 탐색을 이용하는 **skip scan** 최적화가 있습니다. 이 띠는 정렬 관계를 설명하며 실제 planner가 어떤 방법을 선택할지 예측하는 도구가 아닙니다.

<div className="note">
**MSSQL과 구분하기.** SQL Server에서는 clustered index의 마지막 단계가 테이블의 데이터 행을 담습니다. 별도의 nonclustered index는 행 위치를 찾는 정보를 가집니다. clustered index가 없는 테이블은 heap이라고 부릅니다. PostgreSQL에서 PRIMARY KEY를 선언했다고 이 SQL Server의 clustered 저장 구조가 되는 것은 아닙니다. 제품 이름과 설정을 확인한 뒤 그림을 적용하세요.
</div>
