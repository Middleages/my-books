## 백업 작업의 성공과 서비스 복구는 다릅니다

<div className="learning-goals">
이 장을 읽고 나면 남은 사본과 연속 WAL로 복구 가능한 데이터 시점을 따지고, RPO와 RTO를 서로 다른 시간 축에서 비교할 수 있습니다. 복구한 행·관계·금액·재고와 앱 읽기 검증까지 있어야 서비스 복구를 판단할 수 있음을 설명합니다.
</div>

문구 상점의 원본 저장 장치가10:15에 소실됐습니다. ‘백업 성공’ 알림은 있었지만, 어떤 데이터까지 남았으며 언제 주문을 다시 받을 수 있을까요? 파일이 있다는 사실만으로 두 질문의 답을 알 수는 없습니다.

**RPO(Recovery Point Objective)**는 장애 뒤 어느 데이터 시점까지 되살려야 하는지에 관한 목표입니다. 여기서는 장애 전5분보다 오래된 시점으로 되돌아가지 않는 목표를 둡니다. **RTO(Recovery Time Objective)**는 장애 뒤 서비스를 되살리는 데 허용한 시간 목표입니다. 여기서는20분입니다. 목표값과 실제 달성 결과를 구분합니다.

아래의 위쪽 축은 **장애 전 데이터 시점**, 아래의 경과 축은 **장애 뒤 서비스 복구 시간**입니다. 같은 ‘분’이어도 기준점이 다릅니다. 먼저 사본을 바꿔 가능한 범위를 보고, 복구 단계를 진행하며 실제 대상이 생기고 자료가 들어오는 것을 관찰하세요.

## 사본 종류가 복원 방법을 정합니다

**논리 dump**는 데이터와 구조를 논리적으로 내보낸 자료입니다. 이 예에서는09:58의 일관된 snapshot을 읽어10:00에 파일을 완성했습니다. 파일 완료 시각이 데이터 시점은 아닙니다. 이 dump의 데이터를 적재한 뒤 PostgreSQL 물리 WAL을 이어 붙여10:11로 가는 방식으로 그리지 않습니다.

**물리 base backup**은 데이터 파일을 기반으로 복원하는 출발 자료입니다. 운영 중 얻은 물리 base는 필요한 WAL과 함께 일관된 상태로 복구할 수 있어야 합니다. 이 실험은09:58–10:00의 base와 **그 기간에 필요한 WAL까지 모두 확보한 유효 사본**을 가정합니다. 파일 일부를 복사한 것만으로 이 전제를 충족하지는 않습니다.

그 이후 원하는 시점까지 가려면 필요한 WAL이 끊기지 않아야 합니다. 기본 예는10:11까지 연속 자료가 있어 장애 시각10:15와4분 차이가 납니다. 시간 목표5분 안에 들지만 실제 복원·검증 전에는 통과했다고 확정하지 않습니다.

## 뒤쪽 조각이 있어도 빈틈을 건너뛰지 못합니다

‘WAL7 구간 누락’을 고르면1–6의 연결 뒤에 틈이 생깁니다.8–11 조각이 있어도7을 건너뛰지 못해 이 고정 예에서는10:06까지의 prefix만 사용합니다. 장애와9분 차이이므로 RPO5분 목표 밖입니다. 회색 뒤쪽 조각과 실제로 잇는 초록 경로를 구별하세요.

실제 WAL segment는 이 그림처럼1분 단위로 나뉘지 않습니다. 숫자1–11은 합성 시간구간이며 실제 segment 이름이나 파일 크기가 아닙니다. 필요한 범위와 연속성을 설명하기 위한 눈금입니다.

‘같은 장치의 사본도 소실’에서는 복구 자료 자체가 없습니다. 복구 가능한 시점과 소요를 모른다고 표시합니다. **모름은0이 아닙니다.** 원본과 사본이 같은 장애 범위 안에 있으면 사본 수만 세어서는 보호 수준을 알 수 없습니다.

## RPO를 만족하고 RTO는 놓칠 수 있습니다

기본 예의 단계 소요는 감지·대상 준비3분, 사본 가져오기4분, 재생6분, DB 시작2분, 검증5분, 서비스 전환1분입니다. 합계21분은 RTO20분보다1분 깁니다. 막대는20분에서 잘리지 않습니다. 데이터 시간 차4분과 서비스 소요21분을 한 성공 점수로 합치지 않습니다.

이 숫자는 교육용 고정 시간입니다. 실제 복구 속도는 자료량, 전송, 로그 재생, 장비와 검증 절차 등에 따라 달라집니다. ‘파일 복사가 끝났다’나 ‘DB 프로세스가 켜졌다’는 중간 단계이지 서비스 복구 완료와 같은 사건이 아닙니다.

## 무엇을 복구했다고 확인할까요?

이 장은 같은 상점의 **별도 backup-day fixture**에 새 주문6건을 더합니다. 기존 주문은 시작 재고에 이미 반영돼 있으며 다시 차감하지 않습니다. 고정 사건 ID와 예상 snapshot으로 복구 자료를 대조합니다.

1. PK·FK와 제약: 항목이 실제 주문·상품을 가리키는가?
2. 예상 행: 해당 시점의 주문·항목 수가 맞는가?
3. 금액·재고: 확정 주문의 항목 합과 상품별 재고가 맞는가?
4. 앱 읽기: 새 대상에서 앱이 실제로 필요한 데이터를 읽을 수 있는가?

기본10:11 복원은 새 주문5건을 포함해 주문8행·항목9행, 확정 주문금액96,000원입니다.10:13의 새 주문은 자료 범위 밖입니다. 이처럼 고정 사건을 알고 있으므로 무엇이 빠졌는지 말할 수 있습니다. 현실에서는 **4분이라는 시간 차만으로 손실 건수·금액을 알 수 없습니다.** 주문 금액도 결제 성공이나 회계 매출과 다릅니다.

‘데이터 복구 뒤 앱 읽기 권한 누락’에서는 세 데이터 검사가 통과해도 앱 경로가 막힙니다.20분 경과를 완료 소요20분으로 표시하지 않습니다. 서비스는 미복구이고 남은 시간도 미정입니다. 이 반례는 새 대상의 권한 누락이지 정상 WAL 재생이 임의로 FK를 망가뜨린다는 뜻이 아닙니다.

실제 복구 연습은 원본을 덮어쓰지 않는 격리 대상에서 수행하고, 해당 시스템의 역할·권한·설정 파일·확장·외부 의존성도 확인해야 합니다. WAL만으로 모든 외부 설정이나 외부 결제 상태까지 복구된다고 가정하지 않습니다.

<div className="note">
MSSQL 비교: SQL Server는 simple·full·bulk-logged라는 recovery model에 따라 로그 백업과 복구 선택의 전제가 달라집니다. PostgreSQL의 base backup+WAL 조건을 이름만 바꿔 그대로 적용하지 않습니다. 제품의 recovery model, 유효한 백업과 로그 체인, 실제 복원 절차를 따로 확인해야 합니다.
</div>
