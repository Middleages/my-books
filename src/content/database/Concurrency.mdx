## 기다렸다고 예전 판단이 안전해지지는 않습니다

A가 행을 변경하는 동안 B의 충돌하는 변경 문장은 기다릴 수 있습니다. 잠금(lock)은 여기서 같은 자원의 충돌하는 작업을 조정하는 장치입니다. B가 기다리고 있다는 사실은 SQL 오류나 0행 완료가 아닙니다. 아직 완료된 결과가 없습니다.

A가 확정한 뒤 B가 재개할 때, ‘이미 계산해 둔 0을 저장’하는 문장은 현재 재고가 0이어도 조건이 상품 id뿐이면 맞는 행을 갱신합니다. PostgreSQL UPDATE의 결과 행 수는 값이 이전과 같았던 행도 포함합니다. 따라서 ‘1행 갱신’과 ‘마지막 한 개를 안전하게 확보’는 같은 판단이 아닙니다.

그림에서 A가 만든 0과 B가 만든 0을 다른 버전으로 표시한 이유도 여기에 있습니다. 숫자가 같아도 변경의 주체·순서·주문은 다릅니다. 버전 이름은 이 교육 모델의 정체성 표시이며 실제 서버의 물리 tuple 주소가 아닙니다.

## 조건 확인과 감소를 한 문장에 둡니다

다음은 한 개를 예약하기 위한 갱신 부분입니다. 실제 앱에서는 이 문장과 관련 주문 기록을 같은 트랜잭션에 두고 결과를 확인해야 합니다. 브라우저에서 실행하는 SQL이 아닙니다.

```sql
UPDATE products
SET available_qty =
  available_qty - 1
WHERE id = 101
  AND available_qty >= 1;
```

실험의 PostgreSQL Read Committed에서 B가 기다리던 대상이 A의 확정으로 바뀌면, **같은 UPDATE 문장이 그 대상의 새 버전에서 조건을 다시 확인**합니다. 현재 재고가 0이면 조건을 만족하지 않아 갱신 결과는 0행입니다. 앱은 이를 보고 주문 헤더·항목을 만들지 않고 요청을 거절합니다. SQL 오류가 자동으로 발생한 것은 아닙니다.

이 재확인은 문장 전체의 snapshot을 새로 만들어 모든 행을 다시 본다는 뜻이 아닙니다. 이 실험처럼 정해진 한 상품 행을 대상으로 한 경우를 관찰합니다. 복잡한 여러 행 조건의 동시성까지 같은 그림으로 일반화하지 않습니다.

A가 확정하지 않고 취소하면 A의 잠정 변경은 사라지고 B는 남아 있는 원래 재고 1을 기준으로 진행할 수 있습니다. 취소된 A의 주문을 현재 확정 주문 경계 안에 남기지 않는지도 확인하세요.

## 먼저 잠그고 읽는 방식에도 업무 확인이 필요합니다

다른 방식은 같은 연결·같은 트랜잭션 안에서 아래처럼 행을 잠그며 읽고, **반환된 현재 재고를 확인한 뒤** 감소와 주문 기록을 수행하는 것입니다.

```sql
SELECT available_qty
FROM products
WHERE id = 101
FOR UPDATE;
```

잠금 획득 자체가 재고 확보 성공은 아닙니다. A의 확정 뒤 B가 반환받은 행이 하나이고 그 재고가 0이라면, SELECT는 1행을 반환했어도 앱은 주문을 거절해야 합니다. SELECT의 반환 행 수와 UPDATE의 갱신 행 수도 구별해야 합니다.

이 실험의 일반 SELECT는 표시한 행 변경 잠금 때문에 막히지 않고 자신에게 보이는 확정 버전을 읽습니다. 이것을 ‘SELECT는 아무 잠금도 쓰지 않는다’거나 ‘모든 DB가 같은 방식이다’로 확대하면 안 됩니다.

## 같은 SELECT를 두 번 실행하면

별도 장면에서는 재고가 다시 5개입니다. A의 첫 조회 뒤 B가 두 개의 예약을 올바르게 확정해 재고를 3개로 바꿉니다. PostgreSQL 기본 Read Committed는 각 문장이 시작할 때의 확정 상태를 기준으로 읽으므로 A의 다음 조회는 3을 볼 수 있습니다.

Repeatable Read는 이 예에서 첫 데이터 문장이 정한 snapshot을 유지해 두 번째 조회도 5를 읽습니다. snapshot은 ‘이 읽기에 보이는 버전의 범위’입니다. BEGIN을 보낸 순간과 첫 데이터 문장이 시작한 순간은 같지 않을 수 있습니다. 어느 격리 수준에서도 자기 트랜잭션의 앞선 유효 변경은 읽을 수 있지만, 이 작은 비교 장면에서 A는 값을 쓰지 않습니다.

Repeatable Read가 모든 업무 판단을 직렬 실행처럼 보장하는 것은 아닙니다. 더 강한 Serializable도 무조건 기다린 뒤 모든 요청을 성공시키는 설정이 아닙니다. 충돌 때문에 실패할 수 있으며 앱은 전체 트랜잭션을 새로 시작해 판단을 다시 해야 합니다.

<div className="note">
<strong>MSSQL 차이:</strong> Microsoft SQL Server의 READ COMMITTED는 READ_COMMITTED_SNAPSHOT 설정에 따라 잠금 기반 또는 행 버전 기반 읽기가 됩니다. SQL Server의 기본 설정은 OFF, Azure SQL Database의 기본은 ON입니다. 같은 격리 수준 이름만 보고 PostgreSQL 그림과 내부 동작이 같다고 판단하지 말고 실제 제품·설정을 확인하세요.
</div>

## 서로 놓아주기를 기다리는 고리

A가 상품 101을 잡고 102를 기다리는 동안 B가 102를 잡고 101을 기다리면 기다림이 고리가 됩니다. 이를 교착 상태(deadlock)라고 합니다. 그림에서는 **자원에서 트랜잭션으로 향하는 소유 선**, **트랜잭션에서 자원으로 향하는 대기 선**을 구별하세요.

실험은 설명을 위해 B를 중단 대상으로 정합니다. 실제 PostgreSQL이 어느 트랜잭션을 고를지 예측한 것이 아닙니다. 오류로 중단된 트랜잭션의 일반 잠금이 해제되면 다른 작업이 진행할 수 있고, 클라이언트는 남은 실패 상태를 ROLLBACK으로 정리합니다. 뒤의 B2는 같은 마지막 문장을 다시 누른 것이 아니라 새 트랜잭션입니다.

이 작은 실험의 요청은 두 상품을 순서대로 잠그고 읽어 확인하는 작업입니다. 재시도도 그 작업 전체를 새 읽기부터 반복합니다. 별도의 주문 쓰기를 수행했다고 가정하지 않습니다. 여러 경로에서 같은 자원 순서를 쓰면 이 고리를 예방할 수 있지만 모든 종류의 교착이 사라진다는 보장은 아닙니다.

## 실제 앱에서 점검할 네 가지

1. 읽은 값이 언제, 어느 트랜잭션의 결과인지 확인합니다. 과거 화면 값만으로 지금의 재고를 확정하지 않습니다.
2. 업무 조건을 원자 갱신 또는 같은 트랜잭션의 잠금 뒤 확인에 포함하고, 결과 행 수의 뜻을 확인합니다.
3. 대기·정상 0행·SQL 오류·앱 거절을 다른 결과로 처리합니다. 대기 중인 같은 연결에 후속 주문 문장을 보냈다고 가정하지 않습니다.
4. 재시도 가능한 실패는 트랜잭션 전체를 새로 시작해 읽고 판단합니다. 응답 유실이나 이미 발생한 외부 부작용은 단순 재실행의 안전성을 별도로 확인합니다.
