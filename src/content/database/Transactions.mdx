## 주문 하나는 여러 행의 약속입니다

<div className="learning-goals">
이 장을 읽고 나면 재고·주문·항목을 함께 확정해야 하는 이유, COMMIT과 ROLLBACK의 경계, 문장 성공과 업무 완료의 차이를 설명할 수 있습니다.
</div>

가람이 머그 두 개를 주문합니다. 가용 재고 5개를 3개로 줄이고, 주문 헤더를 만든 뒤, ‘머그 2개·당시 단가 12,000원’인 항목을 남겨야 합니다. **재고 차감 하나만 성공해도, 주문 번호 하나만 생겨도 요청 전체가 끝난 것은 아닙니다.**

트랜잭션(transaction)은 여러 DB 변경을 하나의 확정 단위로 묶습니다. 작성 중인 유효한 변경은 그 트랜잭션이 읽을 수 있지만, 다른 트랜잭션에 중간 상태를 확정된 결과로 공개하지 않습니다. 함께 확정하는 명령이 `COMMIT`, 아직 확정하지 않은 변경을 취소하는 명령이 `ROLLBACK`입니다.

아래에서 마지막까지 진행하기 전에 예상해 보세요. 재고를 줄인 다음 주문 기록이 거절되면, 어느 변경이 남아야 할까요? 선과 경계는 같은 DB의 **논리적 변경 집합과 확정 상태**를 비교합니다. 물리적으로 임시 DB를 하나 더 만드는 그림이 아닙니다.

## 문장 하나의 성공과 요청 하나의 성공

실험의 ‘문장별 자동 확정’은 각 SQL 문장이 성공하면 그 문장의 트랜잭션을 자동으로 확정하는 방식입니다. 이를 autocommit이라고 부릅니다. DB가 아무 트랜잭션 없이 동작한다는 뜻이 아닙니다.

이 방식에서는 재고 UPDATE가 이미 확정된 뒤 주문 INSERT가 실패해도 앞의 재고가 자동으로 돌아오지 않습니다. 항목 INSERT에서 실패하면 재고 3개와 항목 없는 주문 헤더가 남을 수 있습니다. 외래키는 ‘있는 항목이 올바른 주문을 가리킨다’는 규칙이지, 모든 주문에 항목이 반드시 있다는 업무 규칙은 아닙니다.

반면 실험의 단일 트랜잭션은 세 변경을 한 경계에 묶습니다. 중간 SQL 제약 오류 뒤 ROLLBACK하면 가용 재고는 5개이고 새 주문·항목은 없습니다. 성공 경로에서는 COMMIT할 때 재고 3개와 새 주문 1건·항목 수량 2개가 함께 확정됩니다.

| 종료 경로 | 확정 재고 | 새 주문 헤더 | 새 항목 수량 |
| --- | ---: | ---: | ---: |
| 단일 트랜잭션 성공 | 3개 | 1건 | 2개 |
| 단일 트랜잭션 중간 오류 후 취소 | 5개 | 0건 | 0개 |
| 자동 확정·주문 헤더 오류 | 3개 | 0건 | 0개 |
| 자동 확정·항목 오류 | 3개 | 1건 | 0개 |

이 표는 실험에 **새로 추가한 기록만** 셉니다. 앞 장의 기존 주문은 이미 가용 재고에 반영돼 있으므로 다시 차감하지 않습니다. 또 주문의 `status = 'confirmed'`는 우리 상점의 업무 값입니다. 그 문자열만 보고 DB의 COMMIT이 완료됐다고 판정할 수는 없습니다.

## 누가, 언제 읽었는지 함께 봅니다

한 트랜잭션 안에서는 자신이 앞서 쓴 유효한 변경을 읽을 수 있습니다. 실험의 작성 세션은 COMMIT 전에 재고 3개와 자기 주문·항목을 읽습니다. 같은 시점에 다른 세션에서 시작한 Read Committed 조회는 아직 확정된 이전 상태를 읽습니다.

COMMIT 뒤 **새로 시작한** 다른 세션의 조회가 새 상태를 읽습니다. 이미 받아 둔 과거 조회 결과가 저절로 고쳐지는 것은 아닙니다. 그림의 조회 표시에 시점을 붙인 이유입니다. 두 조회 사이의 더 자세한 차이는 다음 장에서 살펴봅니다.

SQL 제약 오류로 명시적 트랜잭션이 실패 상태에 들어간 뒤에는, 이 실험처럼 savepoint가 없는 경우 ROLLBACK으로 정리하기 전의 후속 SELECT도 오류입니다. 화면에 남은 과거 성공 결과나 시도 이력을 ‘오류 뒤 다시 읽은 현재 값’으로 착각하면 안 됩니다. **유효한 변경, 거절된 후보, 과거 관측은 서로 다른 경계에 있습니다.**

## 취소해도 돌아오지 않는 번호가 있습니다

실험은 기존 표와 별도로 이름 붙인 교육용 번호 배정기를 가정합니다. `nextval` 호출이 실제로 성공한 사건에서 주문 번호 1004를 소비합니다. PostgreSQL sequence의 배정 값은 트랜잭션을 취소해도 되돌리지 않습니다. 다음 값이 1005라는 사실만으로 주문 1004가 확정됐거나 주문이 한 건 빠졌다고 추론할 수는 없습니다.

기존 상점 fixture에 자동 증가 기본값이 원래 있었다는 뜻도 아닙니다. 번호 배정은 이 장에서 추가한 명시적 가정입니다. 실제 서버의 sequence를 만들거나 실행하지 않았으며 cache·장애 복구까지 재현하지 않습니다.

## 묶었다고 올바른 업무가 되는 것은 아닙니다

트랜잭션은 **그 안에 넣은 변경을** 함께 확정하거나 취소하게 합니다. 잘못된 수량 계산, 누락한 항목 INSERT, 중복 요청의 뜻까지 대신 정해 주지는 않습니다. UPDATE가 0행을 바꾸어도 그 자체는 정상 SQL 결과일 수 있으므로 앱이 결과 행 수를 확인해야 합니다.

안전한 요청 흐름은 입력과 대상 확인 → 조건을 포함한 변경 → 결과 확인 → 관련 기록 → COMMIT입니다. 오류가 나면 트랜잭션 상태를 정리하고, 다음 요청에 연결을 넘기기 전 같은 연결의 상태를 확인합니다. 실제 앱에서 동일한 연결을 유지하는 문제는 뒤의 연결 풀 장에서 이어집니다.

DB ROLLBACK이 이미 보낸 이메일·외부 HTTP 요청·파일 쓰기까지 취소하지는 않습니다. 또 COMMIT 응답을 받지 못했다고 DB가 반드시 취소됐다고 단정할 수 없습니다. 외부 부작용과 응답 유실은 다른 경계의 문제입니다.
