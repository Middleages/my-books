## 데이터 구조와 앱은 한순간에 바뀌지 않습니다

<div className="learning-goals">
이 장을 읽고 나면 열 이름 변경의 성공과 앱 호환성을 나누고, 추가·공존·채우기·검증·제거의 순서를 설명할 수 있습니다. 채움100%와 값 일치, 남은 옛 참조를 별도로 확인하며 중단·재실행과 DDL 잠금의 경계를 판단합니다.
</div>

문구 상점의 상품 이름 열을 name에서 display_name으로 바꾸기로 했습니다. DB의 이름 변경 명령이 성공하면 배포 중인 옛 앱의 SELECT도 자동으로 바뀔까요? 상품 값은 그대로 있어도 옛 열 이름을 참조하는 코드는 실패할 수 있습니다.

<strong>스키마(schema)</strong>는 표·열·제약처럼 저장 구조를 정의하는 약속입니다. <strong>마이그레이션(migration)</strong>은 그 약속과 자료를 새 구조로 옮기는 변경 작업입니다. 명령 실행 이력은 중요하지만, 앱이 새 구조를 읽고 쓰며 값이 맞는지까지 대신 확인해 주지는 않습니다.

아래 그림의 왼쪽은 앱의 읽기·쓰기 능력, 오른쪽은 현재 존재하는 열입니다. 먼저 ‘곧바로 이름 바꾸기’를 관찰하고, 안전한 전환에서는 세 가지 합격문이 언제 충족되는지 예상하세요. 비활성 앱 상자는 버전의 역할 설명이며 실제 실행 중인 앱은 ‘현재 실행 중’으로 구별합니다.

## 추가해서 공존시킨 뒤 오래된 쪽을 걷어냅니다

이 예의 <strong>확장·축소(expand–contract)</strong>는 두 구조가 잠시 공존하도록 추가한 다음, 사용자를 옮기고 옛 구조를 없애는 순서입니다. 모든 변경의 정답 절차나 무중단 보장은 아닙니다.

1. nullable display_name을 추가합니다. name과 기존 앱은 그대로입니다. 새 열이 생겼어도 NULL뿐이면 새 앱의 표시 계약은 준비되지 않았습니다.
2. ‘연결 앱’을 배포합니다. 이 앱은 name을 읽되 이름을 바꾸면 두 열에 같은 값을 한 transaction에서 씁니다. 한쪽만 성공한 중간 상태를 성공으로 인정하지 않습니다.
3. name만 쓰는 옛 writer가 모두 사라졌는지 확인합니다. 서버뿐 아니라 배치 작업·운영 스크립트·이전 배포본도 실제 점검 범위입니다. 그림은 세 앱 역할만 가정합니다.
4. 기존 행을 작은 묶음으로 채웁니다. 현재 행의 name을 읽어 display_name이 NULL인 행만 채웁니다.
5. 채움과 현재 값 동등성을 직접 확인합니다. 그 뒤 새 열만 읽고 쓰는 앱으로 바꿉니다.
6. 연결 앱의 옛 열 쓰기까지 모두 없어졌는지 확인한 뒤 name을 제거합니다. 제거한 열은 현재 그림에서도 사라집니다.

마지막 검증은 **제거 직전의 두 열 비교**입니다. 제거 뒤에는 name이 없으므로 ‘현재 두 열3/3 일치’라고 표시하지 않습니다. 과거 검증 기록과 현재 구조를 나누어 보존합니다.

## NULL-only 채우기는 과거 값을 덮어쓰지 않는 계약입니다

기존 행을 새 구조에 맞추는 작업을 <strong>backfill</strong>이라고 부릅니다. 이 예에서는 다음과 같이 범위를 작은 묶음으로 제한한 현재 행 기반 갱신을 생각할 수 있습니다. 본문에서 실행하지 않는 설명용 SQL입니다.

```sql
UPDATE products
SET display_name = name
WHERE id BETWEEN 101 AND 102
  AND display_name IS NULL;
```

이미 채운101은 다시 쓸 필요가 없습니다. 연결 앱이102의 두 이름을 ‘노트 새판’으로 함께 바꿨다면102도 건너뜁니다. 중단 뒤 다시 실행해도 오래전에 저장해 둔 ‘노트’ snapshot으로 덮어쓰지 않습니다. 그림의 version은 교육용 상태 번호이지 PostgreSQL xmin이나 물리 행 쓰기 횟수가 아닙니다.

하지만 **재실행해도 같은 결과가 된다는 성질과 내용이 옳다는 성질은 다릅니다.** 옛 writer가 name만 ‘머그 새색’으로 바꾸면 새 열은 여전히 ‘머그’일 수 있습니다. 채움은3/3이어도 일치는2/3입니다. NULL만 채우는 작업을 다시 돌려도 이 불일치는 고쳐지지 않습니다. 먼저 쓰기 경로를 통제하고 현재 값·이력을 확인해야 합니다.

실제 대량 변경에는 잠금·부하·트랜잭션 크기·중단 위치·재시도와 완료 검증을 함께 설계합니다. 같은 이름의 열이 있다는 IF NOT EXISTS 결과만으로 타입·제약·기존 값이 원하는 정의와 같다고 간주하지 않습니다.

## 작은 DDL도 기다릴 수 있습니다

<strong>DDL(Data Definition Language)</strong>은 ALTER TABLE처럼 구조를 바꾸는 명령을 가리킵니다. 이 장의 nullable ADD COLUMN은 ACCESS EXCLUSIVE 잠금을 요구하는 경우로 고정했습니다. 아직 끝나지 않은 SELECT transaction의 ACCESS SHARE와 충돌하면 기다립니다. 기다리는 명령을 보고 ‘새 열이 이미 생겼다’고 해석하지 마세요.

SELECT 결과가 돌아왔다는 사실과 그 transaction이 끝났다는 사실도 다릅니다. 그림은 기존 transaction 정상 종료 → DDL 잠금 획득 → 열 추가 완료를 나눕니다. 막는 세션을 무작정 종료하는 버튼은 제공하지 않습니다. 어떤 업무와 변경을 취소하는지 모르고 종료하면 다른 장애를 만들 수 있습니다.

모든 DDL이 같은 잠금을 사용하는 것은 아닙니다. CREATE INDEX CONCURRENTLY처럼 쓰기를 허용하는 방식에도 추가 스캔·대기·자원 비용이 있으며 transaction block 안에서 실행할 수 없는 제한이 있습니다. 실패 뒤 invalid index가 남을 수도 있습니다. 따라서 모든 migration을 BEGIN/ROLLBACK 하나로 되돌릴 수 있다고 일반화하지 않습니다.

## 앱 롤백과 자료 복구는 별개입니다

옛 열을 이미 제거한 뒤 옛 앱으로 되돌리면 name 참조가 다시 실패할 수 있습니다. 앱 버전 롤백은 삭제된 열과 데이터를 자동으로 복원하지 않습니다. 제거를 늦출 관찰 기간, 호환 범위, 백업과 검증된 복구 경로를 따로 준비해야 합니다. 실제 운영 변경의 승인·점검 절차를 이 교육 모델이 대신하지 않습니다.

<div className="note">
MSSQL 비교: Microsoft SQL Server에서도 열 이름을 바꿨다고 참조하는 모든 코드와 개체가 자동으로 수정되지는 않습니다. sp_rename의 문법·의존성 점검을 PostgreSQL ALTER와 섞지 마세요. SQL Server ONLINE 인덱스 작업도 제품·edition·작업 조건의 제약이 있으며 PostgreSQL CONCURRENTLY와 같은 구현이나 무잠금 보장이 아닙니다. 이 책은 두 엔진을 실제 실행해 비교하지 않았습니다.
</div>
