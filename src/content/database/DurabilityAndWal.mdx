## 성공 응답과 데이터 페이지는 다른 증거입니다

<div className="learning-goals">
이 장을 읽고 나면 RAM·휘발성 쓰기 cache·내구 저장의 경계를 구분하고, WAL을 데이터 페이지보다 먼저 남기는 이유를 설명할 수 있습니다. 장애 뒤 물리적 복원과 새 조회의 가시성이 다른 판단이며, 앱이 응답을 못 받은 상황도 별도로 다뤄야 함을 이해합니다.
</div>

상품101의 재고를5에서4로 바꿨고 앱이 COMMIT 성공을 받았습니다. 그런데 저장 장치의 데이터 페이지에는 여전히5가 있습니다. 이것만으로 DB가 거짓말했다고 결론 내릴 수 있을까요?

DB는 변경할 **페이지 사본을 메모리의 버퍼**에 둘 수 있습니다. 버퍼의 내용과 저장 장치의 페이지가 매 순간 같아야 하는 것은 아닙니다. 대신 장애 때 되살릴 변경 기록을 먼저 남기는 규칙이 필요합니다. **WAL(Write-Ahead Log)**은 데이터 페이지를 쓰기 전에 내구화해야 하는 변경 로그입니다.

그림에서 P1은 같은 페이지의 정체성이고, RAM과 내구 영역의 P1은 서로 다른 사본입니다. v0·v1은 같은 상품 행의 이전·새 버전입니다. 앱의 응답은 저장 영역 밖에 둡니다. 무엇이 남았는지와 무엇을 앱이 들었는지를 섞지 않기 위해서입니다.

## 세 번의 ‘저장’을 구분합니다

| 관찰 | 아직 단정할 수 없는 것 |
| --- | --- |
| RAM에 페이지와 WAL 기록이 생김 | 전원 장애 뒤에도 남는가 |
| WAL을 휘발성 쓰기 cache로 write함 | 내구 장치의 동기화가 끝났는가 |
| 정상 장치에서 WAL의 동기화 완료를 확인함 | 모든 데이터 페이지도 최신인가 |

기본 동기 시나리오는 `fsync=on`, `synchronous_commit=on`, 복제 없음과 정상 장치를 가정합니다. COMMIT 기록까지 내구화된 뒤 성공을 응답하므로, 데이터 페이지를 매번 먼저 내구화하지 않아도 됩니다. 이후 페이지를 쓸 때는 **그 페이지의 변경을 설명하는 WAL이 먼저 내구화돼 있어야** 합니다.

실험의 LSN10과20은 로그 순서의 교육용 표식입니다. 실제 LSN은 WAL 위치이며 transaction 번호나 시각이 아닙니다. pageLSN은 페이지에 반영된 변경 위치를 나타냅니다. 이 예의0·10·20을 실제 파일 크기나 동작 시간으로 읽지 않습니다.

## 장애는 경계를 없애고, 복구는 새 사본을 만듭니다

‘동기 · 성공 응답 뒤 장애’를 끝까지 보세요. 기존 RAM과 cache의 경계가 사라지고 새 instance가 생깁니다. 저장 페이지는 아직 옛 상태여도 생존한 WAL을 사용해 **redo**, 즉 페이지 변경을 다시 반영할 수 있습니다. 임의의 SQL을 처음부터 다시 실행하는 과정이 아닙니다.

‘미확정 page10까지 쓴 뒤 장애’에서는 더 중요한 반례가 보입니다. 미확정 변경의 WAL이 먼저 내구화돼 있다면 그 데이터 페이지가 저장 장치에 내려갈 수도 있습니다. 복구한 페이지에 새 버전4가 남아 있어도, T1의 확정 기록이 없으므로 새 독자는 이전 버전5를 봅니다.

따라서 **물리적으로 존재함 ≠ 지금 조회에 보임**입니다. 이 모델은 PostgreSQL의 여러 버전과 transaction 상태의 역할을 간추린 것이며, 미확정 버전을 모두 지워 옛 페이지로 되감는 그림이 아닙니다. 이미 pageLSN10인 페이지에는 같은 변경을 중복해서 만들지 않습니다.

실제 복구에는 checkpoint, 전체 페이지 이미지, 부분 쓰기 방어, 로그·transaction 상태의 여러 절차가 있습니다. 그림의 ‘redo 데이터 → T1 판정 → 새 조회’는 개념을 나눈 관찰 순서이지 실제 엔진 함수 호출 순서를 완전히 재현한 것이 아닙니다.

## 응답을 못 받았다고 취소된 것은 아닙니다

‘동기 · flush 뒤, 응답 수신 전 장애’에서는 앱은 성공을 받지 못했지만 DB에는 확정 결과가 남습니다. 앞 장의 COMMIT 결과 불명과 이어지는 경계입니다. 이때 새 요청으로 무조건 다시 차감하면 같은 주문을 두 번 처리할 수 있습니다. 원래 요청 키와 확정 결과를 확인하는 절차가 필요합니다.

반대로 비동기 확정은 성공 응답과 WAL 내구화 사이의 간격을 허용합니다. ‘비동기 · 응답 뒤, flush 전 장애’에서는 성공을 받았어도 최근 변경이 사라져 새 조회가5를 반환합니다. 이는 그 정책에서 허용한 **최근 확정 변경 손실**이며, 데이터 페이지가 서로 맞지 않게 손상됐다는 뜻과 다릅니다.

<div className="note">
`synchronous_commit=off`의 최근 변경 손실과 `fsync=off`의 장애 후 일관성 위험은 같은 설정 효과가 아닙니다. 이 장은 경계를 비교할 뿐 운영 설정을 끄도록 권하지 않습니다. 실제 장치가 동기화 완료를 정직하게 보장하는지도 내구성 전제에 포함됩니다.
</div>

## WAL이 있어도 백업이 필요한 이유

‘성공 응답 뒤 로컬 저장 장치도 소실’에서는 data와 WAL이 함께 사라집니다. 같은 장치 안의 로그만으로 이 장치 자체의 소실을 해결할 수 없습니다. 잘못된 업무 변경이나 운영 실수도 그저 정상 변경으로 기록될 수 있습니다. 무엇을 어디에 보관했고 어디까지 되살릴지는 다음 장의 별도 질문입니다.
