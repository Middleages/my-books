## 느린 화면에서 DB의 어느 일을 보고 있나요?

<div className="learning-goals">
이 장을 읽고 나면 실행계획의 자식·부모 관계와 출력 행 수를 읽고, 예상·관측·반복 횟수를 구별할 수 있습니다. 비용·시간·버퍼 접근을 잘못 더하거나, 적은 actual만으로 통계 오류를 단정하지 않습니다.
</div>

주문 목록 화면이 느립니다. 앱이 연결을 기다렸는지, DB가 잠금을 기다렸는지, 많은 행을 읽었는지부터 나누어야 합니다. <strong>실행계획(plan)</strong>은 DB가 한 문장을 처리하는 작업 구조를 보여 줍니다. 앱 요청 전체의 시간표나 모든 네트워크 대기를 보여 주는 지도는 아닙니다.

그림의 아래 작업이 만든 행을 위 작업이 받습니다. scan은 후보를 읽고 조건에 맞는 행을 내보내며, join은 관계를 맞추고, aggregate는 여러 입력을 요약합니다. PostgreSQL에서 필터 조건이 scan에 붙을 수 있다는 점을 반영해, 아래 실험은 가짜 독립 ‘Filter’ 노드를 만들지 않습니다.

**EXPLAIN**의 예상과 **EXPLAIN ANALYZE**의 실행 관측도 다릅니다. 다음 그림은 이 구별을 연습하도록 저자가 만든 합성 plan입니다. 실제 서버 출력이나 실제 SQL 실행 기록이 아닙니다.

## rows는 그 노드가 내보내는 행 수입니다

첫 예는04장의 별도 성장 fixture, 주문2001–2064의64행을 사용합니다. 조건에 맞는40행을 scan이 내보내고, COUNT는 값40이 든 **결과1행**을 돌려줍니다. 따라서 입력64행·중간 출력40행·최종 출력1행은 동시에 맞는 관측입니다.

scan의 예상4행과 관측40행이 다르면 위 작업으로 전달되는 양도 예상과 달라질 수 있습니다. 하지만 숫자 차이를 발견한 것이 곧 해결책을 찾았다는 뜻은 아닙니다. SQL 조건, 데이터 분포, 통계와 계획의 전체 구조를 확인해야 합니다. ‘예상을40으로 맞추기’는 비교용 plan fixture를 바꾸는 조작이지 실제 통계 갱신이나 optimizer 선택을 보장하는 버튼이 아닙니다.

예상 행 수는 수량 추정입니다. 어떤 주문 id가 나올지 미리 알아낸 목록으로 표시하지 않았습니다. **관측하지 않은 actual은0이 아니라 미관측**이라는 차이도 확인하세요.

## 회당 평균과 반복 횟수를 함께 읽습니다

두 번째 예는 원래 상점으로 돌아옵니다. 고객1의 확정 주문1001·1002를 읽고, 안쪽 항목 조회를 각각 실행합니다. 첫 실행은 항목2행, 다음 실행은1행을 내보냅니다.

안쪽 노드의 평균은1.5행, loops는2, 누적 출력은3행입니다. 평균1.5는 행을 반으로 잘랐다는 뜻이 아니라 두 실행의 평균입니다. 실제 표시에 평균·소수·반올림이 있을 수 있으므로, 화면에 보이는 반올림 수를 무조건 정확한 원본 합계로 취급하지 않습니다. 이 모델의1.5는3/2로 계산한 정확한 값입니다.

서로 다른 실행 packet과 저장 행의 정체성도 구별합니다. 항목(1001,1)과(1001,2)는 같은 주문에서 왔지만 다른 행입니다. 조회를 여러 번 했다는 사실만으로 저장 데이터가 그 수만큼 늘지는 않습니다.

## 예상10행인데2행만 나와도 맞을 수 있습니다

LIMIT 예에서는 부모가 필요한2행을 받자 아래 scan을 멈춥니다. 정해 둔 교육용 순서로2001–2004를 확인해2002·2004가 나옵니다. 끝까지 읽으면 일치하는 행은10개지만, 실제로는 끝까지 요청하지 않았습니다.

이때 자식의 예상10과 actual2 차이만 보고 ‘통계가 틀렸다’고 할 수 없습니다. 적게 내보낸 원인이 상위 작업의 조기 중단인지 먼저 봐야 합니다. 또2행을 내보내기 위해4후보를 확인했으므로 **결과2행과 검사2행도 같은 말이 아닙니다.** 실제 SQL의 ORDER BY 없는 반환 순서를 이 합성 배치와 같다고 보장하지 않습니다.

이 반례는 스트리밍 scan 위의 LIMIT입니다. 모든 입력을 먼저 받아야 하는 COUNT나 blocking Sort 위에 같은 그림을 올려도 똑같이 일찍 끝난다고 설명하지 않습니다.

## 비용·시간·버퍼는 서로 다른 단위입니다

- cost: planner가 경로를 비교하는 비용 단위입니다. 밀리초가 아닙니다.
- actual time: 실행을 계측한 startup/total 소요시간이며 반복 노드에서는 회당 평균으로 읽습니다. 공통 시계의 시작 시각과 종료 시각 두 점이 아닙니다.
- BUFFERS: 공유 버퍼의 hit/read 등 접근 카운터입니다. 회당 rows/time과 달리 loops 전체의 누적값이며, 서로 다른 페이지 개수와도 같지 않습니다.

예를 들어 같은 페이지를 여러 번 접근하면 카운터에 반복이 들어갑니다.04장의 ‘서로 다른 방문 페이지 수’와 단위가 다릅니다. 또한 부모의 시간과 버퍼 카운터에는 자식 활동이 포함되므로 **부모+자식 합계를 전체 사용량으로 만들면 중복**될 수 있습니다.

PostgreSQL의 shared read는 공유 버퍼에 없어 바깥에서 가져온 접근입니다. 운영체제 cache가 응답할 수도 있으므로 그 숫자를 바로 물리 디스크 읽기량으로 바꾸지 않습니다. 그림의 시간막대는 포함 관계를 보여 주려고 별도로 만든 합성 시간표이며 실제 plan의 두 숫자를 시작·끝 좌표로 옮긴 것이 아닙니다.

## 관측 순서를 작게 만듭니다

앱이 주문 목록 한 번과 각 주문의 항목을 따로 조회하면 이 예에서는 DB 호출이1+2=3회입니다. 한 JOIN 문장의 안쪽 노드 loops2와는 다른 층의 수입니다. 앱에서 호출을 많이 하는 문제를 한 plan의 노드 시간만으로 해결할 수는 없습니다.

실제 점검에서는 다음을 함께 남깁니다.

1. 앱 요청의 전체 구간과 DB 호출 횟수, 반환량.
2. 연결 획득 대기와 연결 보유 시간, 잠금 대기 여부.
3. 정확한 SQL·매개변수 조건과 데이터 규모, plan의 예상·actual·loops.
4. DB 버전·통계·cache 등 비교 조건과, 변경 전후 같은 요청의 관측.

관측이 없는 구간을0으로 채우지 않습니다. 큰 숫자 하나를 보고 인덱스를 무조건 추가하거나 풀을 늘리기보다, 어느 단계에서 무엇이 달라졌는지 가설을 세우고 작은 변경 뒤 다시 확인합니다.

## ANALYZE는 실제로 실행합니다

`EXPLAIN ANALYZE`는 문장을 실제로 수행합니다. 읽기 쿼리도 작업 부하를 만들 수 있으며, 쓰기 문장은 데이터를 바꿀 수 있습니다. ROLLBACK으로 감싸도 sequence·외부 부작용까지 모두 취소된다는 안전 보장은 없습니다. 이 책의 선택 실습은 승인된 일회용 합성 DB의 부작용 없는 SELECT로 한정합니다.

PostgreSQL18 문서에서는 ANALYZE가 BUFFERS도 암묵적으로 켭니다. 이 동작을 과거·다른 제품에 일반화하지 말고 사용 버전의 문서를 확인하세요. 계측 자체의 부하가 있고, EXPLAIN ANALYZE는 보통 쿼리 결과를 앱에 전달하는 네트워크 비용까지 같은 방식으로 측정하지 않습니다. 실행계획의 시간을 앱 응답시간 전체와 같다고 놓지 않는 이유입니다.
