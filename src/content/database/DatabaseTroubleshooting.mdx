이 책에서 썼던 그림을 다시 사용합니다. 단, 처음부터 숨은 정답을 그리지 않습니다. 그 단계에서 확보한 증거만 보이고, 모르는 경계에는 물음표가 남습니다. 실제 pg_stat_activity나 실행계획을 수집하는 도구가 아니라 관측 범위를 따져 보는 교육 실험입니다.

## 같은 ‘대기’라도 확인할 대상이 다릅니다

**연결 대기:** 실행 A의 R2는 아직 client를 빌리지 못했습니다. SQL을 빠르게 만드는 것만으로 이 대기 원인을 없앨 수는 없습니다. R1의 SQL이2tick에 끝났어도 같은 대여가8tick까지 남는지, 반환 이력과 예외 처리 경로를 확인합니다. R1의 SQL2tick과 R2의 대기8tick을 더해 ‘한 요청10tick’으로 만들지 않습니다.

**잠금 대기:** 세션 B는 이미 DB에 요청했고 상품101의 충돌 자원을 기다립니다. 관계는 B→자원→A입니다. B가 기다리는 동안 영향 행 수는 아직 모릅니다. A가 확정한 뒤 B의 조건부 UPDATE가0행을 반환한 시점과 구별해야 합니다. ‘0행이라 느리다’는 설명은 두 시점을 섞은 것입니다.

**예상과 관측의 차이:** scan 예상4행과 관측40행이 다릅니다. 이것은 과소추정의 근거입니다. 하지만 인덱스 추가나 ANALYZE가 반드시 해결한다는 증거는 아닙니다. 선택 조건, 자료 분포와 통계, 접근 경로, 실제 읽은 페이지와 반복을 확인하고 결과가 같게 유지되는지도 검증합니다. COUNT의 출력1행과 그 안의 값40도 다른 단위입니다.

연결 대여·transaction·SQL·반환을 서로 다른 구간으로 보는 습관이 중요합니다. 열린 연결1개만으로 잠금이 남았다고 단정하지 않고, active session만으로 계속 CPU 연산 중이라고 단정하지 않습니다. PostgreSQL의 state와 wait_event는 독립된 정보입니다.

## 관측값에는 대상과 시점이 필요합니다

한 기록에는 적어도 실행·요청 ID, DB session과 transaction의 대응, 관측 시각 또는 구간, 측정 위치와 단위가 필요합니다. 지금 화면의 교육 step을 실제 서버의 시각으로 받아들이지는 마세요.

pg_stat_activity에서 상태와 대기를 살펴보고 pg_blocking_pids() 등으로 막는 process를 확인할 수 있습니다. 그러나 권한에 따라 보이는 내용이 다르고 여러 관측이 항상 동시에 고정된 완벽한 snapshot도 아닙니다. **보이지 않음은 없음의 증거가 아닐 수 있습니다.**

이 책의 상품101 잠금 그림은 A/B 문장 추적과 잠금 관계를 함께 제공한 합성 자료입니다. A의 미확정 재고를 그렸어도 B가 SELECT로 그 값을 읽었거나 pg_locks가 알려 준 값은 아닙니다. 상품101은 개념상 충돌 자원입니다. 실제 pg_locks에 잠긴 모든 상품의 product_id가 행별로 나타난다고 기대하면 안 됩니다. 행 잠금 대기는 소유 transaction ID를 기다리는 모습으로 보일 수 있습니다. 출력 모양을 외우기보다 ‘어떤 session이 누구 때문에 기다리는가’를 질문하세요.

예상 plan은 실행 전의 추정이고 EXPLAIN ANALYZE는 실제 실행합니다. 변경 쿼리나 비용이 큰 쿼리를 운영에서 무심코 실행하지 않습니다. 같은 조건의 별도 허용 환경과 읽기·쓰기 부작용을 먼저 검토합니다.

## COMMIT 응답을 잃었다면 실패라고 단정하지 않습니다

앱이 응답을 받지 못한 순간에는 DB가 확정했을 수도, 아닐 수도 있습니다. HTTP 실패나 timeout만 보고 새 request_key로 주문을 다시 넣으면 같은 주문을 두 번 만들 위험이 있습니다.

이 고정 사례는05장의 확정 주문1004, 상품101 수량2, 확정 재고3을 **같은 요청 키로 재조회한 뒤** 보여 줍니다. 여기서야 기존 업무 결과가 있다는 증거를 얻습니다. 재시도 내용이 같은 고객·상품·수량이면 기존 결과를 돌려주고 주문과 재고를 다시 변경하지 않습니다.

키가 같아도 수량3으로 바뀌었다면 같은 요청이 아닙니다. 기존 수량2를 덮어써서 성공으로 처리하지 않고 내용 불일치를 거절합니다. 실제 계약에서는 통화·옵션·가격 정책 등 업무상 의미가 같은지도 정의해야 합니다. 이 실험은 세 필드로 한정합니다.

<strong>멱등성(idempotency)</strong>은 같은 요청을 반복해도 정해 둔 효과를 중복시키지 않는 성질입니다. request_key의 UNIQUE와 transaction 범위, 동일 내용 대조와 결과 조회를 함께 설계해야 합니다. 키 하나나 ON CONFLICT라는 문법 하나로 모든 부작용이 해결되지는 않습니다. 특히 결제·이메일 같은 외부 효과의 exactly-once를 이 계약이 보장하지 않습니다.

또한 재조회 결과가 없다고 원래 요청이 취소됐다고 결론 내리지 않습니다. 원래 transaction이 아직 진행 중이거나 관측 시점·범위가 다를 수 있습니다. 이 장은 그런 경우를 임의로 새 INSERT 성공으로 처리하지 않습니다.

## 하나를 고쳐도 다른 문제가 남을 수 있습니다

복합 사례에서 반환 누락의 실행 A, 반환을 정상으로 둔 재실험 B, 계획을 관측한 실행 Q는 별개입니다. B에서4요청이 완료됐다고 A의 중간 이력이 바뀐 것은 아닙니다. Q1의 scan 과소추정은 그대로 남아 있으므로 ‘모든 느림 해결’로 판정하지 않습니다.

변경 전후에는 같은 요청 내용과 조건을 비교합니다. 연결 상한 증가가 서버 부담을 늘리는지, 인덱스가 쓰기 비용을 추가하는지, transaction 종료가 어떤 업무를 취소하는지 확인해야 합니다. 무작정 세션 종료·재시작·백업 덮어쓰기·중복 주문 재실행을 정답 버튼으로 만들지 않은 이유입니다.

## 마지막에 남길 짧은 진단 기록

다음 다섯 줄을 자신의 말로 써 보세요. 정답 도구 이름보다 근거와 한계를 나누는 것이 목표입니다.

1. 관측: 어떤 실행·요청·시점에서 무엇을 보았는가?
2. 가설: 그 증거로 지지할 수 있는 원인은 무엇인가?
3. 다음 확인: 아직 모르는 어떤 경계를 확인할 것인가?
4. 변경의 위험: 취소·중복·부하·데이터 변경의 가능성은 무엇인가?
5. 변경 후 검증: 같은 조건에서 어떤 결과와 관계를 다시 확인할 것인가?
