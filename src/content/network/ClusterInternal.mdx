## 1. Docker에서 배운 개념에 이름 세 개 더하기

**k3s는 쿠버네티스를 간결하게 구성해 제공하는 배포판**입니다. 여기서는 설치법 대신 요청이 어디로 가는지에 집중합니다.

| 이름    | 지금 필요한 이해                                              | 앞 장과 연결                                    |
| ------- | ------------------------------------------------------------- | ----------------------------------------------- |
| Pod     | 함께 실행되는 컨테이너의 단위. 같은 Pod는 IP·포트 공간을 공유 | 같은 Pod의 컨테이너끼리는 localhost로 통신 가능 |
| Service | 바뀌는 Pod들 앞의 일정한 이름·접점                            | 클라이언트가 Pod IP를 매번 바꿔 적지 않게 함    |
| CoreDNS | 클러스터에서 Service 이름을 찾게 하는 DNS 구성 요소           | 이름 조회 성공과 실제 연결 성공은 여전히 별개   |

서로 다른 Pod에서 localhost를 쓰면 상대 Pod를 가리키지 않습니다. 같은 Pod 안의 컨테이너는 네트워크 공간을 공유하므로 같은 주소·포트를 두 앱이 동시에 차지하려 하면 충돌할 수 있습니다.

## 2. Service의 80과 앱의 8000은 다른 숫자다

`api` Service의 **port가 80**, **targetPort가 8000**이라면 클라이언트는 `api:80`으로 접속하고 선택된 Pod의 8000으로 전달됩니다. 앱은 실제로 그 포트에서 listen해야 합니다. Service가 리스너를 만들어 주지는 않습니다.

Service의 **selector**는 Pod의 라벨과 맞춰 대상을 고르는 조건입니다. 준비된 대상 주소·포트는 EndpointSlice 같은 리소스에서 확인할 수 있습니다. selector가 틀려 대상이 없는 경우와, 대상은 있지만 targetPort가 틀린 경우를 나누어 봅니다.

Service는 논리적인 접점입니다. 모든 패킷이 반드시 별도의 “Service 프로그램”을 거쳐 간다고 생각하지 마세요. 실제 전달은 클러스터의 네트워크 구현이 담당합니다. 이 장은 일반적인 selector 기반 ClusterIP Service만 다룹니다.

## 3. 실제 상황에서는 이 세 가지만 확인하기

Pod를 교체해 IP가 달라져도 Service가 유지되고 새 대상이 반영되면 클라이언트는 같은 이름으로 새 연결을 만들 수 있습니다. 기존 TCP 연결까지 새 Pod로 순간이동하는 것은 아닙니다.

올바른 클러스터와 namespace인지 먼저 확인한 뒤 읽기 전용으로 관찰합니다. 아래 `demo`는 예시 namespace입니다.

```sh
kubectl config current-context
kubectl get pods -n demo -o wide --show-labels
kubectl get service api -n demo -o yaml
kubectl get endpointslices -n demo -l kubernetes.io/service-name=api
```

**Pod 라벨·준비 상태 → Service selector·port·targetPort → 실제 대상 목록** 순서로 맞춰 봅니다. `api`라는 짧은 이름은 같은 namespace의 기본 DNS 설정을 가정합니다. 다른 namespace에서는 `api.demo`처럼 범위까지 지정할 수 있습니다.
