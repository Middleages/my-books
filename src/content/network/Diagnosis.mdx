## 1. 세 줄로 상황을 적기

| 적을 것         | 예시                                 |
| --------------- | ------------------------------------ |
| 어디에서 어디로 | 프록시 컨테이너 → app:8000           |
| 무엇을 관찰했나 | 이름은 조회됨, TCP 연결은 거부됨     |
| 아직 모르는 것  | 앱 실행 여부·실제 listen 주소와 포트 |

DNS 성공은 TCP 성공이 아니고, TCP 성공은 TLS 검증 성공이 아닙니다. HTTP 응답을 받았어도 업무 성공이나 브라우저의 응답 읽기까지 보장하지는 않습니다. 아래 네 사례에서 **다음에 볼 곳을 먼저 생각한 뒤** 답을 펼쳐 보세요.

## 3. 연습 B: 프록시를 컨테이너로 옮긴 뒤 502

기존 호스트 Nginx는 `127.0.0.1:18001`로 앱에 연결했습니다. 이제 프록시와 앱은 같은 사용자 정의 bridge에 있습니다. upstream 설정은 여전히 `127.0.0.1:18001`이고, 프록시 로그에는 그 주소의 연결 거부가 기록됩니다.

다른 origin으로 사전 확인이 필요 없는 GET을 보냈습니다. Network에서 본 응답은 200이고 서버 로그도 처리를 확인합니다. 응답에는 Allow-Origin이 없고, Console에 CORS 오류가 표시됩니다.

## 6. 실제 장애에서는 한 조건씩

위 사례는 원인을 알도록 구성한 짧은 연습입니다. 실제 502·timeout·verify 오류는 여러 원인이 가능하고 동시에 발생할 수도 있습니다. **관찰 → 가설 → 한 조건 변경 → 같은 위치에서 재확인** 순서로 진행하세요. 변경 전후의 목적지·명령·결과를 남기면 다른 사람도 판단 과정을 따라갈 수 있습니다.

이 책의 실험은 실제 네트워크를 검사하는 도구가 아닙니다. 배운 원리로 질문을 좁힌 다음 실제 환경에서 증거를 모으는 데 목적이 있습니다. 네트워크의 기초 연결은 여기서 마무리하고, 클러스터를 만들고 운영하는 방법은 별도 쿠버네티스 교재에서 이어갑니다.
