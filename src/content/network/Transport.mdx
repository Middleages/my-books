## 1. TCP 연결은 전용 전선을 만드는 일이 아니다

TCP 양쪽은 연결을 위해 상태를 기억합니다. 상대가 누구인지, 어디까지 보냈고 받았는지, 다음에 받을 바이트가 무엇인지 등을 관리합니다. 네트워크 중간에 전용 전선을 확보하는 것은 아닙니다. 연결 중에도 패킷은 다른 통신과 경로를 공유합니다.

일반적인 연결 시작은 **SYN → SYN과 ACK → ACK**의 세 메시지로 설명합니다. 양쪽이 시작 순서 번호와 연결 상태를 맞춥니다. 연결 설정도 시간이 들기 때문에 이미 만든 연결을 재사용하는 것이 도움이 될 수 있습니다. 모든 웹 요청이 새 TCP 연결을 만드는 것은 아닙니다.

연결 성공은 양쪽 TCP가 대화를 준비했다는 뜻입니다. 서버 앱이 요청을 처리했거나 저장을 완료했다는 뜻은 아닙니다. 그 결과는 HTTP 같은 앱 프로토콜의 응답으로 확인해야 합니다.

## 2. TCP는 메시지 봉투가 아니라 바이트 흐름

앱이 “ABC”와 “DEF”를 두 번 보냈다고 상대 앱이 반드시 같은 크기로 두 번 읽는 것은 아닙니다. 한 번에 “ABCDEF”를 읽거나 더 작은 조각으로 읽을 수도 있습니다. TCP는 **순서 있는 바이트 스트림**을 제공하며, 앱이 보낸 호출 단위의 메시지 경계를 보존하지 않습니다.

따라서 앱 프로토콜은 길이 정보나 구분자 같은 규칙으로 메시지의 끝을 판단해야 합니다. TCP가 파일·JSON·사진이라는 의미를 알아서 분리해 주지는 않습니다. 첫 장에서 본 패킷의 분할과 앱의 메시지 구분은 다른 문제입니다.

## 3. ACK는 다음에 필요한 바이트를 알려 준다

TCP의 순서 번호는 패킷의 일련번호가 아니라 **바이트 위치**를 나타냅니다. 설명을 위해 첫 데이터 번호를 1이라 하면 1~100을 연속해서 받은 수신자는 ACK 101로 다음 기대 위치를 알릴 수 있습니다. 실제 연결은 다른 시작 번호를 쓰며 SYN·FIN도 순서 번호 공간을 사용합니다.

101~200이 빠진 채 201~300을 받아도 누적 ACK는 101에 머뭅니다. 뒤쪽 데이터가 도착했다는 것과 앱에 연속된 데이터를 전달할 수 있다는 것은 다릅니다. 앞의 빈 구간이 채워져야 그 뒤를 순서대로 전달할 수 있습니다.

송신자는 ACK와 타이머 등으로 손실 가능성을 판단해 다시 보냅니다. 타임아웃으로 재전송할 수도 있고, 중복 ACK 등의 신호로 더 일찍 복구할 수도 있습니다. 한 패킷이 늦었다고 곧바로 잃었다고 단정하는 규칙은 아닙니다. 재전송 타이머는 왕복 시간과 변동을 고려합니다.

## 4. UDP는 무엇을 생략할까?

UDP는 데이터그램 단위를 유지하지만, UDP 자체가 연결 핸드셰이크·순서 보장·손실 재전송을 제공하지 않습니다. 앱은 도착하지 않은 메시지에 어떻게 대응할지 정해야 합니다. 실시간 음성에서는 늦게 온 과거 소리보다 새 소리가 중요할 수 있고, 조회 앱은 답이 없으면 다시 질문할 수 있습니다.

**앱이 받는 서비스의 차이**

| 관점           | TCP              | UDP 자체                  |
| -------------- | ---------------- | ------------------------- |
| 데이터 형태    | 바이트 스트림    | 데이터그램                |
| 순서·누락      | 순서 관리·재전송 | 보장하지 않음             |
| 전송 속도 조절 | 흐름·혼잡 제어   | 앱/상위 프로토콜에서 필요 |
| 암호화         | 자체 제공 아님   | 자체 제공 아님            |

UDP가 항상 빠르거나 TCP가 반드시 끝까지 성공하는 것은 아닙니다. TCP도 지속적인 단절에서는 실패합니다. UDP 위에서도 QUIC처럼 신뢰성·혼잡 제어·암호화를 갖춘 프로토콜을 만들 수 있습니다. DNS 역시 UDP만 쓰는 서비스가 아닙니다. 일반적인 DNS에는 TCP도 사용됩니다.

## 5. 빨리 보내기와 빨리 도착하기는 다르다

**대역폭**은 일정 시간에 통로가 운반할 수 있는 데이터량입니다. **지연**은 데이터가 이동하거나 기다리는 시간이고, **RTT**는 갔다가 응답이 돌아오는 왕복 시간입니다. 실제로 앱이 얻은 유효 데이터의 속도인 처리율은 대역폭보다 낮을 수 있습니다.

도로 비유로 보면 차선을 늘리면 같은 시간에 더 많은 차가 통과할 수 있습니다. 하지만 목적지가 멀다는 사실은 바뀌지 않습니다. 데이터량은 지나갈 차량의 양, 대역폭은 통과 용량, 지연은 이동·대기 시간에 대응합니다. 이 비유는 혼잡 제어의 세부 동작까지 설명하지 않습니다.

큰 파일은 데이터량÷대역폭의 영향을 크게 받습니다. 작은 요청을 순서대로 여러 번 주고받는 작업은 왕복 대기의 영향이 커질 수 있습니다. “인터넷은 빠른데 앱이 느리다”면 파일 크기뿐 아니라 몇 번 기다리는지도 살펴보세요.

## 6. TCP는 한 조각마다 멈춰 서지 않는다

TCP는 ACK가 오기 전에 여러 바이트를 보내 둘 수 있습니다. 다만 수신자가 감당할 양을 넘지 않도록 하는 **흐름 제어**와, 네트워크를 과하게 밀어붙이지 않도록 하는 **혼잡 제어**가 전송량을 제한합니다. 전자는 받는 쪽의 여유, 후자는 경로의 혼잡을 다룹니다.

왕복 시간이 길면 응답을 기다리는 동안 충분한 데이터가 이동 중이어야 대역폭을 활용할 수 있습니다. 손실 후 복구나 전송량 조절도 실제 처리율을 바꿉니다. 그래서 위 계산은 개념을 분리하기 위한 이상적 모델이며 실제 TCP 성능을 그대로 예측하지 않습니다.

## 7. 실제 상황: 파일 업로드와 작은 API 요청

큰 파일의 업로드가 느리다면 먼저 파일 크기와 실제 걸린 시간을 기록해 유효 처리율을 계산해 보세요. 업로드 방향의 병목, 서버의 저장 속도, 손실과 재전송도 후보입니다. 회선 상품의 최대 속도가 앱의 실제 전송 속도는 아닙니다.

작은 API 요청이 느리다면 연결 준비, 네트워크 왕복, 서버 처리 중 어디에서 기다렸는지 나눠 봅니다. 서버가 DB 결과를 기다리는 2초를 회선 대역폭만 늘려 해결하기는 어렵습니다. 네트워크 지연을 관찰하더라도 다른 프로토콜의 측정값을 앱의 응답 시간과 동일하게 보지 않습니다.
