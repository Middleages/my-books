## 1. URL은 여러 단계에서 나누어 읽는다

`http://app.example.test:8000/report?day=today#summary`를 예로 들어 봅시다. 이 문자열 전체가 DNS에 질문으로 들어가는 것은 아닙니다. 각 부분이 쓰이는 시점과 역할이 다릅니다.

| 부분             | 뜻과 사용 위치                                    |
| ---------------- | ------------------------------------------------- |
| http             | HTTP 접속 방식. https는 TLS로 보호하는 HTTP       |
| app.example.test | 이름 해석과 서비스 식별에 쓰는 호스트 이름        |
| 8000             | 연결할 서버 포트. 생략하면 http는 80, https는 443 |
| /report          | 서버에 요청할 리소스의 경로                       |
| ?day=today       | 질의 문자열. 서버가 해석할 추가 정보              |
| #summary         | fragment. HTTP 요청 대상에는 포함하지 않음        |

fragment는 문서 안의 위치 등 클라이언트에서 사용하는 정보입니다. 서버의 라우팅 경로와 같지 않습니다. 이 교과서가 주소의 # 뒤에서 장을 바꾸는 것도 브라우저 안의 코드가 그 값을 해석하기 때문입니다.

## 2. 요청은 “무엇을, 어떻게”라는 말

HTTP/1.1의 단순한 요청은 다음처럼 읽을 수 있습니다. 실제 전송에는 헤더 종료를 나타내는 빈 줄 등이 있으며, 아래는 이해를 위한 일부입니다.

```http
GET /report?day=today HTTP/1.1
Host: app.example.test:8000
Accept: application/json
```

**GET**은 대상 리소스의 표현을 가져오겠다는 메서드입니다. **POST**는 보낸 내용을 대상 리소스의 규칙에 따라 처리하도록 요청하는 메서드입니다. POST가 언제나 새 행 생성만 뜻하는 것은 아닙니다. 메서드는 요청의 의도를 표현하고 서버는 그 규칙을 구현해야 합니다.

**Host**는 어떤 호스트와 포트를 대상으로 하는지 알립니다. HTTP/2에서는 `:authority`가 이 역할을 맡습니다. 같은 IP로 여러 도메인이 찾아와도 서버나 프록시가 이를 구분할 수 있습니다. 경로는 그 서비스 안에서 무엇을 요청하는지 나타냅니다.

HTTP/2는 요청을 위 예시와 같은 텍스트 줄 그대로 전송하지 않습니다. 형식이 달라도 메서드·대상·상태 코드 같은 의미는 이어집니다. HTTP/3는 QUIC을 사용하므로 이번 장의 TCP 단계 그림을 그대로 적용하지 않습니다.

## 3. 응답에는 결과를 설명하는 상태가 있다

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"report": "today"}
```

상태 코드는 서버가 요청을 어떻게 처리했는지 알려 주는 단서입니다. 응답을 받았다고 사용자가 기대한 작업이 모두 끝났다고 단정하지는 않습니다. 본문과 앱의 업무 규칙도 함께 봐야 합니다.

| 예시            | 읽는 법                                                       |
| --------------- | ------------------------------------------------------------- |
| 200             | 요청 성공. 구체적인 의미는 메서드에 따라 다름                 |
| 301·302·307·308 | 다른 대상으로 이동하도록 안내. 코드별 메서드 처리 차이가 있음 |
| 401 / 403       | 유효한 인증 자격 필요 / 서버가 요청 수행을 거절               |
| 404             | 대상 리소스를 찾지 못했거나 존재를 공개하지 않음              |
| 500             | 서버가 예상하지 못한 조건으로 처리하지 못함                   |
| 502 / 504       | 게이트웨이의 upstream 응답 문제 / 제때 응답을 받지 못함       |

4xx를 모두 네트워크 장애로, 5xx를 모두 방화벽 문제로 읽지 마세요. 404를 받았다면 적어도 어떤 HTTP 서버가 응답한 것입니다. 다만 그 서버가 내가 의도한 앱인지는 Host·경로·프록시 설정을 더 확인해야 합니다.

## 4. HTTPS에서는 HTTP보다 먼저 상대를 확인한다

새 HTTPS 연결에서는 TCP 연결 뒤에 TLS 협상과 서버 인증서 검증이 들어갑니다. 인증서를 신뢰하지 못해 중단한 것은 HTTP 500 응답을 받은 것과 다릅니다. 일반적인 초기 연결에서 검증이 끝나지 않으면 앱의 HTTP 요청까지 나아가지 못합니다.

이 실험은 새 연결만 보여 줍니다. 실제 브라우저는 DNS 캐시나 기존 연결을 재사용하고, 리다이렉트를 따라 추가 요청을 보내기도 합니다. 화면 하나를 여는 과정에는 HTML·이미지·API 등 여러 요청이 있을 수 있습니다.

## 5. 실제 상황: 404가 뜨는데 포트를 더 열어야 할까?

먼저 개발자 도구의 Network에서 요청 URL·메서드·상태·응답 내용을 확인하세요. 응답을 보낸 서비스가 맞는지, 경로 접두사가 필요한지, 리다이렉트 뒤 URL이 달라졌는지 살펴봅니다. HTTP 응답이라는 증거가 있는 상황에서 방화벽을 무작정 넓히는 것은 원인을 겨냥한 조치가 아닙니다.

<div className="note">

**읽기 전용 관찰 · 요청을 보내는 PC에서**

```sh
curl -v --connect-timeout 5 http://app.example.test:8000/report
```

가상 주소 예시입니다. 실제 서비스에서는 URL과 접근 정책을 확인하세요. 연결 로그와 요청·응답 헤더를 구분해 읽고, 로그를 공유하기 전 쿠키·토큰을 가립니다. 사내 프록시가 개입하면 연결 상대도 달라질 수 있습니다.
