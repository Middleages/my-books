## 1. IP 다음에는 어느 창구일까?

앞 장에서는 목적지 네트워크까지 가는 길을 찾았습니다. 도착한 서버에서는 운영체제가 데이터를 알맞은 통신 창구인 **소켓**으로 넘겨야 합니다. 프로그램은 소켓을 통해 데이터를 보내고 받습니다. 이때 TCP나 UDP 헤더에 있는 **포트 번호**가 사용됩니다.

IP를 건물 주소, 포트를 창구 번호라고 생각해 보세요. 주소가 맞아도 창구 번호가 다르면 원하는 일을 처리할 수 없습니다. 다만 포트 하나가 프로그램 하나의 영구 이름은 아닙니다. 프로그램이 실행될 때 어떤 주소와 포트를 사용할지 정하며, 실제 연결 구분에는 상대의 주소와 포트도 쓰입니다.

`192.0.2.10:8000 / TCP`는 “이 주소의 TCP 8000번”이라는 뜻입니다. 같은 숫자의 TCP 포트와 UDP 포트는 별개입니다. UDP 8000을 허용했다고 TCP 8000 연결이 되는 것은 아닙니다. 이 장의 접속 실험은 TCP만 다룹니다.

## 2. 서버 포트 하나로 여러 사람을 받는 이유

서버가 TCP 8000에서 기다릴 때, 클라이언트도 자기 쪽 포트를 사용합니다. 보통 운영체제가 임시 포트를 고릅니다. 두 클라이언트가 같은 서버 포트로 연결해도 양쪽 주소와 포트의 조합이 달라 서로 구분할 수 있습니다.

<div className="note">

**서로 다른 두 TCP 연결**

PC A 192.0.2.11:51000 ↔ 서버 192.0.2.10:8000

PC B 192.0.2.12:52000 ↔ 서버 192.0.2.10:8000

서버의 8000은 같지만 상대가 다릅니다. 한 사용자가 연결할 때마다 서버에 새 외부 서비스 포트를 배정할 필요는 없습니다.

</div>

80·443·22 같은 번호는 널리 쓰이는 서비스의 약속입니다. 번호만으로 실제 프로그램이나 안전성이 증명되는 것은 아닙니다. 이 책의 8000도 설명용 선택이며, 모든 웹앱이 그 번호를 써야 한다는 뜻은 아닙니다.

## 3. bind는 주소 선택, listen은 연결 대기

**bind**는 소켓에 로컬 주소와 포트를 지정하는 동작입니다. TCP 서버는 이어서 **listen** 상태로 들어가 새 연결을 기다립니다. 받은 연결은 accept로 받아 처리합니다. “프로세스가 실행 중”과 “원하는 주소:포트에서 연결을 기다림”은 같지 않습니다.

IPv4 서버에서 자주 보는 bind 주소

| bind 주소  | 의미                           | 접속할 때                    |
| ---------- | ------------------------------ | ---------------------------- |
| 127.0.0.1  | 자기 네트워크 공간의 loopback  | 같은 공간에서 127.0.0.1 사용 |
| 192.0.2.10 | 서버에 할당된 특정 주소        | 그 주소로 도달해야 함        |
| 0.0.0.0    | 모든 로컬 IPv4 인터페이스 주소 | 서버의 실제 주소를 사용      |

`0.0.0.0`은 여기서 “모든 IPv4 주소에서 받겠다”는 서버 설정입니다. 다른 PC에서 접속할 목적지로 입력하는 주소가 아닙니다. 또 모든 주소에서 기다린다고 모든 사람의 접속이 허용되지는 않습니다. 경로와 방화벽이 별도로 영향을 줍니다. IPv6의 bind는 이 표와 분리해서 확인해야 합니다.

## 4. 방화벽은 앱을 실행하지 않는다

방화벽은 출발지·목적지·프로토콜·포트 같은 조건으로 통신을 허용하거나 막습니다. 허용 규칙은 통과할 수 있는 조건을 만들 뿐, 서버 프로그램을 실행하거나 리스너를 만들지 않습니다. 반대로 앱이 listen 중이어도 요청이 중간에서 차단되면 연결할 수 없습니다.

“포트를 열었다”는 말을 만났다면 **앱이 기다리게 했는지, 방화벽을 허용했는지** 다시 물어보세요. 이후 Docker 장에서는 호스트 포트를 컨테이너로 전달하는 publish가 여기에 더해집니다. 지금은 단일 VM 안에서 두 조건부터 구분합니다.

## 5. 실제 상황: VM에서는 열리고 내 PC에서는 안 열린다

VM 안에서 `127.0.0.1:8000`으로 연결한 결과는 VM 자신의 loopback 경로에 대한 증거입니다. 내 PC에서 같은 주소를 쓰면 내 PC 자신을 가리킵니다. 원격 VM을 시험한 것이 아닙니다.

먼저 출발 위치와 목적지 주소를 함께 적으세요. “VM 안 → 127.0.0.1:8000 성공, 노트북 → VM의 IP:8000 실패”처럼 적으면 두 관찰이 충돌하지 않습니다. VM에서는 리스너의 주소·포트를, 노트북에서는 경로와 허용 정책을 확인할 수 있습니다.

<div className="note">

**읽기 전용 관찰 · Linux VM에서**

```sh
ss -ltnp
```

TCP 리스너 목록에서 Local Address:Port를 봅니다. 127.0.0.1:8000인지 0.0.0.0:8000인지 확인하세요. 프로세스 정보는 권한에 따라 보이지 않을 수 있습니다. 이 목록만으로 원격 방화벽 통과를 확인할 수는 없습니다.

</div>

**연결 거부**는 연결 요청이 명시적으로 거절됐다는 단서이고, **시간 초과**는 정해진 시간 안에 필요한 응답을 받지 못했다는 단서입니다. 거부를 앱 종료, 시간 초과를 방화벽으로 단정하지 마세요. 이 실험은 원인을 알고 만든 한 사례이며 실제 장애에는 다른 원인도 있습니다.
