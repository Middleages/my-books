## 1. verify 오류는 아직 HTTP 응답이 아니다

인증서 검증 실패는 TLS 단계의 문제입니다. 기본적인 새 HTTPS 연결에서는 HTTP 요청과 응답을 주고받기 전에 중단합니다. 따라서 먼저 오류를 낸 도구, 실행 위치, URL, 정확한 메시지를 기록합니다. “SSL 에러”라는 말만으로는 이름 불일치인지 신뢰 경로 문제인지 알 수 없습니다.

같은 계열의 오류라도 라이브러리와 버전에 따라 문구나 처음 보고하는 실패가 다를 수 있습니다. 여러 문제가 동시에 있으면 하나를 고친 뒤 다른 오류가 드러나기도 합니다. 아래 표는 대표적인 단서이며 문구 하나로 모든 원인을 확정하는 표는 아닙니다.

| 관찰할 단서           | 확인할 곳                                     | 수정 방향                                       |
| --------------------- | --------------------------------------------- | ----------------------------------------------- |
| 이름 불일치           | URL의 이름, SAN, 선택된 인증서                | 의도한 이름으로 접속하거나 인증서·SNI 설정 교정 |
| 만료·시작 전          | 현재 시각, 인증서 유효기간                    | 실제 시계 오류 확인, 적절한 갱신·교체           |
| 발급자 경로를 못 찾음 | 서버가 보낸 중간 인증서, 클라이언트 신뢰 목록 | 서버 fullchain 또는 클라이언트 CA 설정 확인     |

중간 CA 누락과 신뢰 루트 누락은 비슷한 검증 오류로 보일 수 있습니다. “unable to get local issuer certificate”라는 예시 문구만 보고 무조건 CA를 설치하거나 무조건 fullchain을 바꾸지 않습니다. 양쪽 자료를 비교해야 합니다.

## 2. 브라우저에서 성공한 것은 그 환경의 증거

브라우저, 호스트의 curl, Python Requests, 컨테이너 앱은 서로 다른 신뢰 설정을 사용할 수 있습니다. 어떤 curl은 OS의 저장소를 사용하고 어떤 빌드는 파일 기반 CA 모음을 사용합니다. Requests는 일반적으로 certifi의 CA 모음을 사용하며 별도의 경로를 지정할 수도 있습니다. 실제 설치·배포판·옵션을 확인해야 합니다.

브라우저에 중간 인증서 캐시가 있어 서버의 누락이 드러나지 않는 경우도 있습니다. 다른 클라이언트가 같은 자료를 갖고 있다고 가정하면 안 됩니다. 따라서 브라우저 성공만으로 서버가 올바른 체인 전체를 보낸다고 결론 내릴 수 없습니다.

컨테이너는 호스트에 설치한 CA를 자동으로 모두 물려받지 않습니다. 그 이미지와 앱이 실제로 어떤 CA 파일을 사용하는지 확인해야 합니다. 이번 장은 이런 경계만 설명하고 이미지 생성·배포 방법은 Docker 장에서 이어갑니다.

## 4. 어디서 무엇을 관찰하는 명령일까?

다음은 가상 도메인과 문서용 IP를 사용하는 진단 예시입니다. 실패하는 클라이언트와 같은 위치에서 실행해야 비교가 의미 있습니다. 실제 토큰이나 쿠키가 담긴 상세 로그는 공유 전에 가립니다. 명령은 이 페이지에서 실행되지 않습니다.

  <div className="note">
    <strong>클라이언트에서 · URL 이름을 유지하고 연결 IP만 지정</strong>

```sh
curl -v --connect-timeout 5 \
  --resolve app.example.test:443:192.0.2.10 \
  --cacert ./approved-root-ca.pem \
  https://app.example.test/report
```

직접 접속 기준입니다. URL의 이름을 유지하므로 SNI와 인증서 이름 검증도 그 이름을 사용하면서 DNS 주소 선택만 지정할 수 있습니다. Host 헤더만 바꾸는 것과 다릅니다. HTTP(S)\_PROXY 등 프록시가 개입하면 경로가 달라질 수 있으니 환경도 함께 확인하세요.

  </div>
  <div className="note">
    <strong>클라이언트에서 · 서버가 보낸 인증서와 검증 결과 관찰</strong>

```sh
openssl s_client -connect 192.0.2.10:443 \
  -servername app.example.test \
  -verify_hostname app.example.test \
  -verify_return_error \
  -CAfile ./approved-root-ca.pem -showcerts </dev/null
```

<code>-servername</code>은 SNI, <code>-verify_hostname</code>은 기대한 이름
검증입니다. <code>-showcerts</code>는 서버가 보낸 인증서 목록을 보여 주며 그
자체로 검증 완료된 체인이라는 뜻은 아닙니다. CONNECTED만 보지 말고 검증 결과와
종료 상태를 확인하세요.

  </div>

<code>approved-root-ca.pem</code>은 승인된 관리 경로로 받은 CA를 가리키는 예시
파일명입니다. 실패한 서버에서 추출한 인증서를 출처 확인 없이 신뢰 기준으로 넣는
절차가 아닙니다.

## 5. Requests의 CA 설정은 Requests에서 확인

```python
import requests

response = requests.get(
    "https://app.example.test/report",
    verify="/path/to/approved-ca-bundle.pem",
    timeout=(5, 30),
)
```

예시의 verify 경로는 서버의 개인키나 서버 fullchain 파일을 넣는 자리가 아닙니다. 이 클라이언트가 검증에 사용할 CA 모음을 지정합니다. 명시적으로 파일을 지정하면 해당 호출이 그 모음을 사용하므로 필요한 신뢰 CA가 포함되어 있는지 확인합니다. 환경 변수 <code>REQUESTS_CA_BUNDLE</code>도 사용할 수 있지만 앱의 호출 방식과 설정 반영 여부를 확인해야 합니다.

<code>verify=False</code>나 curl의 <code>-k</code>는 검증 문제의 해결이
아닙니다. 상대의 신원을 검증하는 보호를 생략하여 오류가 보이지 않게 만드는
것입니다. 이 교과서는 이를 통과 버튼으로 제공하지 않습니다.

## 6. 브라우저 → 프록시 → 앱: 검증하는 사람이 바뀐다

브라우저가 프록시의 인증서를 검증하는 구간과, 프록시가 HTTPS 백엔드의 인증서를 검증하는 구간은 별개입니다. 두 번째 구간의 클라이언트는 프록시입니다. 브라우저에 CA를 설치해도 프록시의 upstream 신뢰 설정이 바뀌지 않습니다.

NGINX에서는 <code>proxy_pass https://...</code>만으로 upstream 인증서 검증까지 켜졌다고 볼 수 없습니다. 공식 문서상 <code>proxy_ssl_verify</code>의 기본값은 off입니다. 검증 활성화, 신뢰 CA, upstream SNI와 검증 이름을 함께 설계해야 합니다. 다음 리버스 프록시 장에서 전체 배치와 설정으로 연결합니다.
